줄이려고 좋은 케이스를 버릴 이유가 없다.

## 어떻게 만들었나

**기존 13건을 한 글자도 고치지 않고 이어받고**(GS-002~GS-102) 137건을 더했다(절대 원칙 8).
새 항목은 `GS-2xx`(B) · `GS-3xx`(C-1~C-4) · `GS-4xx`(C-5) · `GS-5xx`(C-6) 번호대를 쓴다.

**지식베이스를 먼저 늘려야 했다.** 20조항으로는 상위 5건이 코퍼스의 25%라 Recall@5 가
성립하지 않고, 필요서류를 다루는 조항이 `TERM-2.2`·`TERM-4.1` 둘뿐이라 서류 케이스 30건을
넣어도 정답이 두 ID 로 몰린다. **98조항으로 늘린 뒤**에 이 골든셋을 썼다
([w3-kb-dasan-expand](/backlog/w3-kb-dasan-expand/)).

## 새 필드 두 개

| 필드 | 왜 |
|---|---|
| `source` | `aihub` = AI Hub 다산 전사 **원문 그대로**(12건) · `authored` = 팀이 관찰된 문체로 쓴 발화 |
| `context_utterances` | 이 발화 앞에 오간 말. **검색 질의를 만들 때 함께 넣는다**(11건) |
| `call_guard` | C-6 고객 폭언·위기 신호. `insult` / `threat` / `sexual` / `distress` |

**`context_utterances` 를 넣은 이유**가 이번 확장의 가장 큰 발견이다. AI Hub 다산 실제
전사에서 서류 문의를 뽑아 보니 상당수가 `"필요한 서류가 있나요?"` · `"어떤서류가
필요한가요?"` · `"서류는 어디서 발급받죠?"` 처럼 **그 문장만으로는 무엇을 묻는지 알 수 없는
중간 턴**이다. 발화 하나만 질의로 쓰면 검색이 실패하는 것이 당연해지고, 우리가 재는 것이
「검색 성능」이 아니라 「발화가 자족적인가」가 된다. `decisions/201` 이 B 를 *"대화 맥락으로
절차를 판정"* 이라고 정의한 그대로다.

## AI Hub 원문을 12건만 쓴 이유

`data/README.md` 가 적어 둔 대로 **AI Hub 데이터에는 재배포 금지 조항이 있고 이 저장소는
공개**다(CLAUDE.md §8 — 커밋이 곧 발행). GS-101·GS-102 가 이미 원문을 싣고 있어 전례는
있지만, 2건과 90건은 규모가 다르다.

그래서 **짧은 질문 12건만 원문으로 쓰고**(전부 개인정보 없음) 나머지는 그 문체를 보고
직접 썼다. `source` 필드로 갈라 뒀으므로 **두 집단의 지표를 따로 낼 수 있다** —
[미결 항목](/open-items/)의 *"골든셋 문체와 실제 전사의 분포 차이"* 가 요구한 측정이
이제 가능하다. ⚠ **팀 확인이 필요하다**: 원문 인용 범위를 넓혀도 되는지, 아니면 12건도
바꿔 써야 하는지.

## 출제 규약 — 같은 내용이 지침과 매뉴얼에 짝으로 있을 때 (2026-09-21, `_project/decisions/123`)

지식베이스에는 **같은 규칙을 시민 안내용 지침(`DASAN-TERM-*`)과 상담원용 매뉴얼(`DASAN-MANUAL-*`)에 짝으로 적은 조항**이 있다.
그 짝이 걸린 항목은 이렇게 출제한다.

> **시민이 묻는 말이면 지침(`TERM`) 쪽이 정답이고, 같은 내용의 매뉴얼(`MANUAL`) 조항은 `distractor_doc_ids` 에 넣는다.**

지금 해당하는 항목은 둘이다 — `GS-204`(`TERM-1.3` ↔ `MANUAL-3.2`) · `GS-216`(`TERM-2.9` ↔ `MANUAL-3.4`).
전에는 이 규약이 항목 메모에만 있었다.

⚠ **이 규약은 검색기가 알 수 없는 기준이다.** 두 조항 본문에는 「시민용 / 상담원용」 표지가 없어, 검색기도 사람도
본문만으로는 가르지 못한다. 그래서 이 2건의 오답은 **「검색기가 틀렸다」가 아니라 「구분 단서가 없는 기준으로 채점됐다」**로 읽는다.
검색 수치를 문서·발표에 옮길 때 이 한계를 함께 적는다. **이 2건을 빼고 다시 계산해 더 높은 수치를 만들지 않는다.**
라벨을 any-of 로 고치지 않은 이유(6주차 판정 직전에 채점 기준을 느슨하게 하지 않는다)와 되돌리는 법은 결정 기록에 있다.

### 작성 원칙

규칙표(`server/apps/closure_gate/domain/value_objects/closure_rule.py`, 조항 **29개**)마다 3건 —

| | evidence | 기대 |
|---|---|---|
| ① | 필수 서류 전부 `true` | `complete` |
| ② | 필수 하나만 `false`(조항마다 다른 자리를 뺐다 — 첫 번째만 빼면 순서가 검증되지 않는다) | `incomplete` + 그 이름 1건 |
| ③ | 아무것도 안내 안 됨 — 빈 dict 와 전부 `false` 를 번갈아 | `incomplete` + 필수 전부, **선언 순서대로** |

여기에 경계 12건 — 조건부 서류만 안내(→ 필수 전부 missing) · **키 이름 불일치**(「신고인 신분증」을 「신분증」으로 넣으면
안내로 세지 않는다 — 4.4·3.5·6.4) · 규칙표에 없는 키가 섞임(무시) · 복수 누락의 출력 순서 · 조건부 서류가 `false` 여도 무관.
합계 **99건**(29 × 3 + 12). 조항별 3~4건.

- **기대값은 규칙표를 읽고 사람이 정했다** — 먼저 조항별 필수 서류 이름을 손으로 옮겨 적은 표 위에서 verdict·missing 을 적고,
  그 다음 `gate.evaluate` 로 대조했다. **어긋남 0건**(옮겨 적기 29조항·케이스 99건 모두).
- `evidence` 키는 규칙표의 `RequiredDocument.name` 과 **글자 그대로** 같다. `f2_case.source` 는 판정 근거 조항(= `procedure`).
- **규칙 없는 조항은 채점 대상이 아니다.** `EXCLUDED` 6조항(1.3·1.4 원칙 조항 · 3.4·3.6·6.5·6.8 조건 분기 조항)은
  `UnknownProcedure` 가 나므로 케이스를 만들지 않았다 — 「판정 못 함」이지 오판정이 아니다. 조건 판정 규칙이 생겨 `RULES` 로
  옮겨지면 그때 3건씩 더한다.

### ⚠ 한계 — 이 수치가 말하는 것

- **상한이다.** 기대값을 규칙표 자체에서 정했으므로, 하네스의 `accuracy 1.0` 은 「코드가 규칙표를 그대로 따르는가」를 잰 것이지
  「상담원 안내가 실제로 충분했는가」나 「규칙표가 조항을 올바르게 옮겼는가」를 잰 것이 아니다. 규칙표 작성자(장민석)와
  케이스 작성자(류준)는 다르지만 **같은 표를 보고 적은 것**이라 교차검수의 효과는 제한적이다 — 위 C-6 자기충족 주의와 같은 결이다.
- **자동 판정(상담원 발화 키워드 → evidence)은 여기서 재지 않는다.** 케이스의 `evidence` 는 이미 채워진 bool 이다. `decisions/305` 가
  적은 「부정 문맥을 모른다」 한계는 `detection.py` 몫이고, 그 정확도는 발화가 붙은 별도 케이스가 있어야 잰다(없다).
- 경계 케이스 하나(GS-694 지방세 감면 — 사유별 구체 증명서 이름만 안내)는 **실제 안내로는 충분할 수 있는데 `missing` 이 난다.**
  게이트가 evidence 키로만 판정한다는 한계를 드러내려고 일부러 넣었다.

## D-5 통화 온도 케이스 형식 (2026-09-21, 아직 0건)

하네스가 D-5 를 `call_temperature` 섹션으로 채점하게 배선했다(`w3-call-temperature`). **표본은 0건이다** —

코드 변경 없이 채점된다. **통화 1건·화자 1명 = 항목 1건.**

```json
{
  "id": "GS-501", "module": "D-5", "domain": "dasan",
  "call_temperature": {
    "speaker": "customer",
    "utterances": [
      {"segment_id": 0, "audio": "../data/processed/call-temperature/golden/call-001/customer-00.wav"},
      {"segment_id": 1, "audio": "../data/processed/call-temperature/golden/call-001/customer-01.wav"}

    "source": "aihub-<데이터셋명>"
  },
  "notes": "발화 10·11 은 조금 격앙된 애매한 턴 — 어느 라벨에도 넣지 않는다"
}
```

| 필드 | 뜻 |
|---|---|
| `speaker` | `customer` / `agent`. 기준선은 이 화자의 발화만으로 만든다 |
| `utterances[].segment_id` | 발화 키. `voice_signal` 의 `SegmentOutlier.segment_id` 와 같다. 겹치면 로더가 거부한다 |
| `utterances[].audio` | 발화 오디오 경로 — **이 JSON 파일이 있는 디렉터리 기준 상대경로.** 음성은 `data/`(gitignore) 아래 |
| `expected_outliers` | 사람이 **듣고** 「튀었다」고 붙인 발화 |
| `calm` | 「튀면 안 된다」고 붙인 발화. 둘 다에 없는 발화는 애매한 턴으로 채점에서 뺀다 |

- 특징값(F0·에너지)은 싣지 않는다 — 우리 추출기가 낸 값을 정답에 적으면 추출기를 고칠 때마다 정답이 낡고, 추출기가 채점 밖으로 빠진다.
- 기준선을 만들려면 화자당 발화 **8건 이상**이 필요하다(`MIN_BASELINE_UTTERANCES`). 그 아래면 「판정하지 않음」으로 따로 센다 — 0 점이 아니다.
- 오디오는 저작권·개인정보가 해결된 출처(AI Hub 등)뿐이다(절대 원칙 7). 자체 녹음은 쓰지 않는다.
- 어댑터는 `ai/apps/voice_signal/adapter/outbound/wav_voice_outlier_adapter.py`(`WavVoiceOutlierAdapter`, 2026-09-21)다 — WAV 경로 → F0 중앙값 → `segment_outliers`. `scripts/run_eval.py` 에 꽂혀 있어 항목을 넣으면 바로 채점된다. 지금은 0건이라 「측정 불가 — 골든셋에 채점 대상이 없다」다.

| dense(KoE5) | 0.630 / 0.780 / 0.909 | 0.588 / 0.646 / 0.761 | **0.630 ~ 0.761 — 겹친다** |
| dense + rerank | −9.53 / 0.69 / 6.62 | −10.69 / −7.59 / −3.05 | **−9.53 ~ −3.05 — 겹친다** |

**세 계열 모두 문턱 하나로 깨끗이 못 가른다.** 문턱 `t`(1순위 점수 < t 면 「관련 문서 없음」)를 옮겨 가며 「정답 있음을 몇 건 잃고 정답 없음을 몇 건 걸러 내는가」:

| 계열 | 정답 0건 잃는 최대 t | 걸러냄 | 정답 1건 잃는 t | 걸러냄 | 정답 없음 전부 거르는 t | 그때 정답 잃음 |
|---|---|---|---|---|---|---|
| BM25 | 4.66 | 3 / 24 | 5.36 (GS-233) | 5 / 24 | 14.52 | 33 / 80 |
| dense | 0.630 | 6 / 24 | 0.671 (GS-218) | **15 / 24** | 0.762 | 37 / 94 |
| dense + rerank | −9.53 | 6 / 24 | −7.15 (GS-218) | **15 / 24** | −3.00 | 22 / 94 |

dense `t = 0.671` 에서 유형별로 걸러지는 것: 잡담 **4/4** · 시 범위 밖 **2/2** · 지식베이스 공백 2/3 · 타 기관 소관 **7/15**.
남는 9건(여권·종합소득세·전기요금·도시가스·택배·실업급여·자동차 보험·통장·혼인신고)은 전부 「요금·신고·서류·지원금」 어휘가 겹치는 하드 네거티브다 —
**어휘가 가까운 오답은 점수로 못 가른다.** 잃는 GS-218(「집에서 시청까지 어떻게 가는 게 제일 빠른가요」)은 1순위가 이미 오답(2.12)이고 정답 2.11 이 상위 5 안에 있는 항목이다.

### 문턱 제안 (팀 결정 사항 — 코드에 넣지 않았다)

- **BM25(지금 운영)에는 문턱을 권하지 않는다.** 정답 1건을 잃으면서 걸러 내는 것이 5/24 뿐이고, raw 점수가 질의 길이에 따라 커져 값 하나가 의미를 갖지 않는다.
- **임베딩이 켜지면(`decisions/121` GPU EC2) dense 0.67 안팎이 후보다** — 정답 손실 1/94 로 정답 없음 15/24 를 거른다. 리랭커 −7.15 도 같은 손실에 같은 15/24 라 리랭커가 문턱을 더 잘 세우지는 않았다.
- ⚠ **이 값은 같은 24건으로 골라서 같은 24건에 잰 것이다** — `decisions/206` 이 RRF k 를 골든셋에서 고르지 않은 것과 같은 이유로 그대로 박으면 표본에 맞춘 값이 된다.
  채택하려면 **새 정답 없음 케이스**(고르는 데 안 쓴 것)로 다시 재서 손실·걸러냄이 유지되는지 본다.
- 문턱이 못 가르는 나머지(어휘가 겹치는 타 기관 소관)는 점수가 아니라 **다른 신호**가 필요하다 — 예: 「소관 안내」 조항을 검색 가능하게 두거나(지금은 MANUAL-2.2 가 거의 안 뜬다), 생성 단계의 근거 대조(`decisions/207`)가 서류 이름을 못 찾으면 카드를 접는 것. 어느 쪽이든 판정은 규칙이 한다(절대 원칙 9).

### 한계

- **표본 24건이다.** 유형별로는 2~15건이라 유형별 수치는 경향일 뿐이다.
- 케이스와 문턱 후보를 **같은 사람(류준)이 같은 날** 만들었다 — C-6·F-2 와 같은 자기충족 주의.
- 점수 분포는 **로컬 값**이다. 운영 ES·모델이 같으면 값도 같아야 하지만(결정적 계산) 운영에서 다시 잰 적은 없다.
- 「관련 문서 없음」이 **맞는 답인지**는 여기서 재지 않았다 — 타 기관 소관 문의에 「소관 안내」가 더 나은 답일 수 있다(위 MANUAL-2.2 주의).
