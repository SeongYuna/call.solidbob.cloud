## 기능 블록 코드 미리 보기 (A~J)

아래 세 파트 전체에서 "B(검색)", "C-5(마스킹)" 같은 코드가 설명 없이 계속 나온다.
파트 C에서 각 블록의 진화 과정을 자세히 다루지만, 먼저 **각 코드가 정확히 뭘 가리키는지만**
여기 미리 정리해 둔다 — 파트 A·B를 읽다가 코드가 나올 때마다 이 표로 돌아오면 된다.

| 코드 | 무엇을 하는 기능인가 |
|---|---|
| **A-1~A-4** | 실시간 음성인식(STT) 4단계 — 스트리밍 전사, 화자(고객/상담원) 분리, 상담원 화면 전달, 발화 구간(문장이 끝난 시점) 검출. 이게 안 되면 뒤의 모든 실시간 기능이 입력을 못 받는다 |
| **A-5** | 외국인 고객 지원(동시 통번역) — 08-28에 1차 범위를 **한국어가 서툰 고객 발화의 정확한 전사(ⓑ)**로 좁혔다. 외국어→한글 번역·상담원→고객 모국어 TTS(ⓐ)는 여유 시 확장. 이 프로젝트의 차별점 |
| **B** | 필요서류 자동 제시 — 고객 용건에 맞는 절차의 구비서류 조항을 검색해 카드로 띄운다. RAG 구조의 검색 단계가 돌아가는 메인 기능(문장 생성 단계 B-4~6은 아직 폴백) |
| **C-1~C-4** | 컴플라이언스 감지 — **상담원이** 하면 안 되는 말(단정적 안내, 규정 밖 약속 등)을 실시간 탐지 |
| **C-5** | 개인정보 실시간 마스킹 — 전화번호·주민번호 등을 자막·저장 데이터 양쪽에서 자동으로 가린다. 애매하면 무조건 가린다(재현율 우선) |
| **C-6** | 콜 가드 — C-1~C-4와 반대 방향으로, **고객의** 욕설·폭언과 위기 신호를 탐지해 상담원을 보호(위기 신호는 끊지 않고 전문 기관 연결) |
| **D** / **D-5** | 통화 후 처리(요약·유형분류, 아직 미구현) 및 D-5(통화 온도 — 화자별 평소 톤 대비 목소리가 튀는 구간 표시. **감정 추정이 아니다**, `decisions/203`) |
| **E** | 평가 하네스 — 다른 기능들의 성능을 사람 손 없이 재현 가능하게 자동 채점하는 내부 도구(골든셋 156문항 사용) |
| **F-2** | 필요서류 체크리스트 — B가 카드를 띄운 것과 별개로, 통화 종료 전 필수 서류 안내를 빠뜨리지 않았는지 최종 확인 |
| **G·H·I / 에스컬레이션** | 아직 설계하지 않은 확장 기능(예: 복잡한 상담을 사람 관리자에게 넘기는 것). 코어가 안정돼야 착수 |
| **J** | 진상고객(블랙리스트) 전환·라우팅 — C-6에서 심각한 폭언이 감지되면 상담원이 전환을 요청하고, 관리자 승인 후 그 고객의 이후 통화를 베테랑 상담원에게 우선 배정. 기획서에 없던 신규 기능(09-09 추가) |

**이 스프린트 최대 사건은 08-28에 시작해 스프린트 경계를 넘어 이어진 "다산 단일 도메인

43건·지식베이스 82조항을 통째로 삭제하는 방식이었음에도 "이건 리팩터링이 아니라 같은
인프라 위에 다른 제품을 올린 것"이라 판단해 승인했다. **같은 리뷰에서 버그 하나를 발견했다**:
채점 표본이 0건일 때 평가 하네스가 "통과"로 잘못 보고하는 구조적 결함 — F-2 케이스가
16건→0건이 됐는데 리포트는 "통과"라고 말하고 있었다. 그 자리에서 `NO_SAMPLES`(측정 불가)
상태를 새로 만들어 고쳤다.

**09-09는 이번 스프린트에서 가장 영향도가 큰 하루**였다 — ⚠ 로그 "건수"로는 09-04(그날 로그
26건 중 25건이 조서희의 랜딩페이지 반복 수정)가 더 많다. 09-09가 특별한 건 볼륨이
아니라 **4명 전원이 걸쳐 신규 기능 3종·지식베이스·스키마를 동시에 건드린 날**이라서다:

- 지식베이스 **20조항 → 98조항** 확장
- 골든셋 **13건 → 156건** 재확장 + 재측정(Recall@5 0.833·MRR 0.659)
- **C-6(콜 가드)·D-5(통화 온도)·J(블랙리스트) 세 기능이 하루 만에 신규 구현**
- DB 스키마 QA — 키 결함 2건 수정 + 신규 테이블 5개
- C-5(마스킹) 절대 규칙이 **처음으로 뚫린 것도 이날 발견**됐다(P6 인명 2건 누락) — 표본을

**AWS 인프라가 실제로 뜬 날은 2026-09-08**이다(`jekyll/_logs/2026-09-08-05-seongyun.md`) —

로그 원문: *"배포가 코드를 실제로 실어 날랐다는 증거 — `/openapi.json`의 `CardSchema`가
`score`→`similarity_score`로 바뀌었다. 함께 실린 것: `95d930f`(계약 수정) · `dd63ffd`(CORS
개방)."* ⚠ 커밋으로 확인하면 **필드명 수정(`95d930f`, 12:42)은 정성윤 본인 커밋**이고
**CORS 개방(`dd63ffd`, 14:51)이 장민석 커밋**이다 — 두 변경이 파이프라인을 타고 함께 올라가
라이브 API 스펙이 실제로 바뀐 걸 확인하는 방식으로 **배포 파이프라인(GitHub Actions
OIDC+SSM)이 진짜로 동작한다는 걸 증명**했다. 파이프라인 커밋은 `f243a9e`(15:00)이고,
OIDC 인증 실패를 세 번 잘못 진단한 끝에 원인(GitHub `sub` 클레임의 ID 포함 형식)을 찾아
해결한 뒤 진단 단계를 걷어낸 것이 `64cac40`(17:11)이다.
⚠ 다만 관련 티켓(`w3-cicd-release-pipeline`)은 09-10까지도 `in-progress`로 남아 있다 —
핵심 배포는 검증됐지만 자동 중지 cron 등 나머지 범위가 아직 안 끝났다는 뜻이다.

**⚠ 그런데 그 뒤 두 번의 머지는 운영에 올라가지 않았다(2026-09-11 GitHub Actions 기록으로 확인).**
`release.yml` 실행 결과: PR #57(09-09 16:52)·#58(17:18)은 성공, **PR #59(18:13)·#61(09-10 22:35)은
실패**다. 코드가 바뀌었는데 이미지 태그를 올리지 않아, 파이프라인이 일부러 멈추는 설계(`f243a9e` —
"코드가 바뀌었는데 태그가 그대로면 실패시킨다")에 걸려 새 이미지를 굽는 `plan` 단계에서 멈췄다. 그 뒤
`deploy` 단계는 성공해 **옛 `0.1.1` 이미지를 그대로 다시 적용했다** — 즉 "배포가 안 됐다"가 아니라 "새 코드가
안 실렸다"다. 태그는 `e9e4444`(09-09 16:26) 이후
`0.1.1` 그대로다. 그래서 **운영은 09-09 17시대 이미지**이고, 류준의 09-09 저녁 커밋과 09-10 서버
변경(통화 시작 API·문자열 응답·`DATABASE_URL` 수정·트리거 연결)은 운영에 없다.

**그런데도 09-10에 장민석이 이 배포 서버 대신 로컬 서버+ngrok 터널로 우회한 진짜 이유는
"배포가 안 돼서"가 아니라 "운영 서버에 데이터가 안 들어가 있어서"였다.** 09-10 로그 원문:
*"목표는 하나였다 — 정성윤 부재 중에 조서희가 내 백엔드 API를 받게 하는 것.
**운영 서버는 ES 적재가 안 돼 있어**, 내 로컬 서버(Neon + 로컬 ES)를 ngrok으로
내보내기로 했다."* 즉 **서버는 떠 있었지만 운영 Elasticsearch에
지식베이스(검색용 문서)가 아직 안 들어가 있어서** `/hub/search`·`/hub/recommendations`가
정상 응답을 못 하는 상태였다 — 그래서 프론트에 당장 넘길 API로는 로컬 쪽을 택한 것이다.
이 과정에서 배포 서버의 또 다른 잠재적 결함도 찾아냈다: *"커넥션 팩토리가 `DATABASE_URL`을
안 읽었다... **운영에서 저장이 된 적이 있는지 확인이 필요하다**"* — `/health`상으로는
정상이었던 운영 서버가 실제로 DB에 저장을 하고 있었는지는 그 시점까지 아무도 확인하지
못한 상태였다(09-10에 장민석이 코드를 고쳤지만, 그 수정은 위에서 본 대로 아직 운영에 배포되지 않았다).

**조서희의 09-09 기록도 모순이 아니라 시점 차이다.** 같은 날 조서희의 로그(`bcf00d2`, 15:41
커밋)는 CORS 동작을 로컬에서 실제로 호출해 검증한 뒤, 마지막 줄에 *"운영 서버 재배포(CORS·카드
필드명 수정이 아직 라이브에 안 올라감 — `server.solidbob.cloud`는 여전히 405/구 필드명)"*라고
남겼다 — 커밋 시각으로 보면 **정성윤의 파이프라인 검증(`e9e4444` 16:26 → `64cac40` 17:11)보다
먼저** 쓰인 기록이라, 확인한 시점엔 아직 반영 전이었을 뿐이다.

**09-10엔 프론트가 실제 서버에 처음 붙었다 — 다만 AWS가 아니라 장민석의 ngrok 터널이었다.**
장민석이 09-10 낮(조서희가 14:08 커밋에서 이미 터널로 확인하기 전)에 로컬 서버를 ngrok 임시 주소로
열었고(`2026-09-10-02-minseok.md`), 조서희가 그 주소로 붙자마자 `segment_id` 타입 문제가 드러나
서버가 먼저 그 필드만 문자열로 바꿨고, 오후에 사용자 결정으로 **모든 응답 필드**로 넓혔다(커밋은
저녁 19:29 `7396275`에 몰아서). 조서희는 파서 경계에서 문자열을 원래 타입으로
되돌리고 타입이 틀리면 즉시 알리는 검증 게이트를 넣은 뒤, **"실서버(ngrok) 재테스트로
transcript·recommendation(카드 포함) 모두 alert 없이 정상 파싱되는 것 확인"**했다(`e2c0208`,
14:08). 이것이 이 프로젝트의 **첫 프론트↔서버 실연동**이다. 터널 주소는 임시라 ngrok을
재시작하면 바뀌고(고정 도메인 아직 없음), 배포된 데모 화면은 여전히 mock 모드다.

**류준(`ai/`)의 09-09 작업은 배포 상태와 무관하게 로컬/CI에서 진행됐다.** `ai/` 코드는 별도
배포 표면이 없는 라이브러리라 `server` 이미지에 함께 실리지만(`decisions/024·105`), 류준의 로그에
배포 관련 작업은 없다 — 그리고 그 09-09 저녁 커밋들(PR #59)은 위에서 본 대로 운영에 반영되지 않았다.

**정리**: 09-08 AWS 배포 성공 → 09-09 오후 자동배포 파이프라인 검증 완료 → 09-10 장민석의 로컬
우회는 **운영 ES에 지식베이스가 안 실려서**였다. 그리고 2026-09-11에 배포 기록을 보니 **09-09 저녁
이후 머지 두 건은 이미지 태그를 안 올려 새 코드가 운영에 실리지 않았다(옛 이미지 재적용).** 그러니 "서버가 안 떴다"는 사실이
아니지만, "`main`이 곧 운영이다"도 지금은 사실이 아니다. 남은 과제는 셋이다 — **이미지 태그를
올려 09-10 변경을 운영에 반영**, **운영 ES 지식베이스 적재**, **운영 DB에 실제로 저장되는지 확인**.

18건이 됐다. 08-28 다산 전환 뒤엔 P4·P6·P7 6건만 남아 "0건"의 근거가 더 얇아졌다. **3주차(09-09) 골든셋을
156건으로 확장하며 처음으로 절대 규칙이 뚫렸다** — 인명(P6) 2건 누락, n=28. 채점기
자체의 버그(다른 패턴으로 마스킹된 걸 "누락"으로 오판정)도 같은 날 발견해 고쳤다.
**표본을 늘린 게 숨어 있던 결함을 드러낸 것**이라는 해석이 가능하지만, 지금 이 순간
규칙이 뚫려 있다는 사실 자체는 그대로 남는다. 담당은 2주차 초입에 정성윤에서
장민석으로 이관됐고(`decisions/019`), 지금 막힌 부분(NER)은 류준(`ai/`) 소관이다.

### C-6. 콜 가드 (고객 폭언 탐지)
**08-28 다산 전환 재편 때 새로 추가된 기능**이다(`decisions/201`). 3주차(09-09)에
하루 만에 구현됐다(4분류: 욕설·협박·성희롱·정신적고통). 재현율·정밀도 둘 다 1.0(n=15)을
냈지만 **자기충족적 지표**(자기 규칙이 만든 표본을 같은 규칙으로 채점)다 — 류준은 커밋에
"교차검수 전까지 「목표 달성」으로 인용하지 않는다"고 적었다. 위기 신호(`distress`)는 폭언과
대응이 정반대라(끊지 않고 전문 기관 연결) 먼저 따로 판정하게 설계했다. 09-10에 조서희가 통화
종료 시 상담원이 직접 고르는 "블랙컨슈머 수동 분류" 카드를 붙였지만, 서버 쪽 HTTP 연결(API)은
아직 없다 — 판정 로직과 DB 테이블(`call_guard_flag`)만 있고, 그 테이블에 저장하는 코드도 아직
없다(`w4-c6-d5-persistence`, todo).

### D. 통화 후 처리 (요약·유형분류·품질평가)
D-1~D-3(요약·유형분류·공백 리포트)은 3주 내내 `server/apps/postcall/` 디렉터리가
만들어지지 않아 미착수 상태다(허브 쪽 엔드포인트·배선만 08-27에 있고, 스포크가 없어 지금은 501을 낸다). **D-5만 3주차(09-09)에
방향 전환을 거쳐 구현됐다** — 원래 "전사 텍스트 감정분석"이 전제였는데, 상담사 톤이 일정해
변별력이 없고 텍스트는 이미 C-1~C-4·C-6이 보고 있어서 **"음성 톤 이상 구간 탐지(통화 온도)"로
바꿨다**(`decisions/203`). 이름에서도 「감정분석」을 뺐다 — 심리 상태를 판정한다고 주장하는
말이라서다. 구현 뒤 다산콜DB에서 상담사 톤 흔들림이 민원인보다 크게 나왔는데, 류준은 이를
「이 데이터로는 못 잰다」(연기된 정상 시나리오)로 적었다. 측정 도구가 대상을 깎아먹던 버그
(배음·옥타브 스냅)도 발견해 고쳤다. 저장 테이블(`voice_outlier`)은 있지만 저장하는 코드는
아직 없고, 원본 오디오를 남기지 않으므로 저장 전에 통화가 끝나면 다시 계산할 수 없다.

### E. 평가 하네스 (사수 대상)
**이 프로젝트에서 가장 먼저(1주차) 착수된 기능**이다 — "미구현은 측정 불가로 정직하게
보고한다"는 설계 원칙이 코드 한 줄 없던 시점부터 들어가 있었다. 2주차(08-27)에 처음
실제 수치(C-5·F-2)를 냈고, 08-28 다산 전환 이후 골든셋 재구축을 겪으며 계속 갱신됐다.
현재 156건짜리 골든셋으로 검색·마스킹·콜가드를 채점하고 있고, "표본 0건일 때 거짓
통과로 보고하는" 자체 결함을 08-28에 발견해 고쳤다(`NO_SAMPLES` 상태 신설).

### F-2. 필요서류 체크리스트 (종결 게이트)
