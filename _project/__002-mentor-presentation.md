## 0. 발표 흐름 (발표자 메모)

1장 팀·용어 → 2장 문제 → 3장 솔루션 → 4장 아키텍처(어떻게 짰나) → 5장 진행 상황(정직하게) →
**5.5장 지난 멘토 피드백을 어디까지 반영했나** →
6장 우리가 잘하고 있다고 생각하는 것(프로세스) → 7장 막혀 있는 것 → 8장 다음 계획 →
**9장 멘토에게 묻고 싶은 것**(이 발표의 실질적 목적). 7·9장이 제일 중요하다. 5.5장은 멘토가
직접 준 피드백이라 질문이 가장 먼저 나올 곳이다 — 「반영 완료」라고 말하지 않는다.

### 먼저 풀고 갈 용어

이 발표에서 반복해서 나오는 말들이다.

| 용어 | 쉬운 설명 |
|---|---|
| **STT** | 음성을 텍스트로 바꾸는 기술(Speech-to-Text). 이 프로젝트는 Google Cloud STT를 쓴다 |
| **RAG** | 질문이 들어오면 관련 문서를 먼저 검색하고, 그 문서를 근거로 답을 만드는 방식. "서류 추천" 기능(B)이 이 구조인데, 지금은 **검색 단계까지만** 붙어 있고 카드에는 검색된 조항 문장을 그대로 보여준다(문장을 새로 쓰는 생성 단계는 아직 없다) |
| **NER** | 문장 안에서 사람 이름·주소 같은 고유명사를 찾아내는 AI 기술 |
| **재현율(recall)** | "있어야 할 걸 놓치지 않는 비율". 우리 개인정보 마스킹은 이걸 최우선으로 삼는다 — 확신이 안 서면 일단 가린다 |
| **허브-스포크 구조** | 우리 코드의 설계 방식. `server/`가 "허브"로서 입출력 규격만 정하고, 실제 판정 로직("스포크")은 따로 붙는다. 스포크가 아직 안 붙은 기능을 호출하면 서버가 대개 "구현 안 됨"(HTTP 501)이라고 정직하게 답한다 |
| **스프린트/골든셋/CI** | 스프린트=1주 단위 작업 묶음. 골든셋=정답이 미리 달린 평가 문제집. CI=코드를 푸시할 때마다 자동으로 테스트를 돌려 깨진 걸 잡는 장치 |
| **결정 기록(decision record)** | 우리 프로젝트를 크게 바꾸는 선택을 할 때마다 "왜 이렇게 했는지, 무엇을 포기했는지, 되돌리려면 어떻게 하는지"를 문서로 남기는 방식. 지금까지 39건 있다 |

## 2. 문제 정의 — 왜 이걸 만드는가

- 국내에 체류 중인 외국인이 **287만 명**이다(2026-06-30 기준, 정부는 연내 300만 명을 넘길 것으로
  본다). 이 중 상당수는 한국어가 서툰 채로 관공서에 민원 전화를 건다.
- 서울시 120 다산콜센터는 이미 **사람 통역으로 외국어 상담을 운영 중**이다 — 즉 "외국인이 민원
  전화를 걸고, 그걸 도와줄 통역이 필요하다"는 수요가 실제로 검증돼 있는 채널이다.
- 그런데 AI 콜센터(AICC) 시장은 이미 대기업들이 장악하고 있다. **"우리가 대기업과 뭐가 다른가"**를
  스스로에게 먼저 물었고, 그 답이 다음 장의 솔루션이다.

## 3. 솔루션 — 무엇을 만드는가

한 줄로: **다산콜센터 상담 중에, 통화 음성을 실시간으로 들으면서 세 가지를 한다.**

1. **구비서류 자동 제시(B, 메인 기능)** — 고객이 "이런 일로 전화했어요"라고 말하면, 그 절차에
   필요한 서류 목록을 상담원 화면에 자동으로 띄운다. 실제 다산 고객 질문 6,697건 중 서류를 묻는
   질문 146건(2.18%)이 **64가지 서로 다른 민원 의도**에 흩어져 있다(류준 09-09 재측정, `0d9116b`)
   — 상담원이 전부 외울 수 있는 규모가 아니다.
   ⚠ 결정 기록 `201`은 같은 값을 174건(2.60%)·69종으로 적고 있다. 09-09 재측정에서 146건·64종이
   나왔고, 원래 질의를 복원하지 못해 차이의 원인은 확정되지 않았다. 발표에선 최신 재측정값을
   쓰고, 질문이 나오면 두 값이 있다는 사실을 그대로 말한다.
2. **외국인 고객 지원(A-5, 차별점)** — 1차 목표는 **한국어가 서툰 외국인 고객의 발화를 정확히
   받아 적는 것**이다(08-28 `decisions/201`에서 범위를 이렇게 정했다). 외국어→한글 번역과 상담원
   답변을 고객 모국어 음성(TTS)으로 들려주는 것은 폐기가 아니라 여유가 생기면 하는 확장이다.
   음성인식 API가 가장 약한 지점이 바로 '서툰 한국어'라서 **우리 기여가 실제로 생기는 자리**이고,
   이게 대기업 제품과 구분되는 지점이다.
3. **실시간 보호 장치** — 컴플라이언스 위반(상담원이 하면 안 되는 말)·개인정보 노출·고객의
   욕설/폭언을 실시간으로 탐지하고, 개인정보는 화면과 저장 데이터 양쪽에서 가린다.

### 왜 "다산콜센터 하나"로 좁혔나

원래는 금융보험·쇼핑·질병관리본부·다산콜센터 4개 분야를 다 지원하려 했다. 2026-08-28에
**다산 하나로 좁혔다.** 근거는 세 가지 실측이다:

1. **음성 데이터를 가진 유일한 분야** — 다산콜DB 6,614건(12.7시간)이 있다. 나머지 3개는
   텍스트 데이터뿐이라 STT(음성인식) 성능을 아예 측정할 수 없었다.
2. 서류 문의 상위 단어 순위에 **"여권"이 4위**로 나온다 — 외국인 관련 맥락이 이미 데이터
   안에 있다는 뜻이다(금융 데이터엔 이런 게 없었다).
3. 위에서 말했듯 사람 통역 수요가 이미 검증된 채널이다.

**이건 "겁먹고 줄인 것"이 아니라 "측정할 수 있는 데이터가 있는 쪽으로 좁힌 것"이라고 본다.**
나머지 3개 분야는 STT 관련 지표를 잴 방법 자체가 없어서, 거기에 시간을 쓰면 "측정하지 않은
수치를 기록하지 않는다"는 원칙과 충돌했을 것이다.

### 기능 블록 전체 지도

기능은 알파벳 코드로 관리한다(A, B, C-1처럼). 아래는 전체 지도다.

| 코드 | 내용 | 우선순위 |
|---|---|---|
| A-1~A-4 | 실시간 음성인식(스트리밍·화자 구분·발화 구간 검출) | 필수 |
| **A-5** | **외국인 고객 지원** — 1차는 서툰 한국어 전사, 번역·TTS는 확장 | 필수 — **차별점** |
| **B** | **필요서류 자동 제시** | **사수 — 메인 기능** |
| C-1~C-4 | 상담원 발화의 컴플라이언스 위반 탐지 | 필수 |
| **C-5** | **개인정보 실시간 마스킹** | **사수 — 코어** |
| C-6 | 고객 욕설·폭언·위기 신호 탐지("콜 가드") | 필수 |
| D | 통화 후 요약·유형분류(D-1~D-3) + 통화 온도(D-5 — 음성 톤 이상 구간, 감정 추정 아님) | 필수 |
| **E** | **평가 하네스**(자동 채점 시스템) | **사수** |
| F-2 | 필요서류 체크리스트(B의 판정 담당 부분) | B에 종속 |
| G·H·I, 에스컬레이션 | 확장 기능 | 여유 시 — 6주차에 코어를 통과해야 착수 |
| J | 진상고객(블랙리스트) 전환·라우팅 | 기획서 외 확장(09-09 신규 추가, `decisions/204`) |

**"사수"라고 표시한 B·E·C-5 세 개는 이 프로젝트가 무슨 일이 있어도 끝까지 완성하기로 스스로
정한 것이다.** 나머지(F·G·H·I)는 6주차 종료 시점에 저 세 개가 기준을 통과해야만 손을 댄다 —
범위를 스스로 제한해서 핵심을 지키는 쪽을 택했다.

### 각 블록이 정확히 뭘 하는지 (상세)

- **A-1~A-4. 실시간 음성인식** — 상담원 전화기에 들어오는 음성을 실시간으로 텍스트로
  바꾸는 기초 작업 4단계다. A-1(스트리밍: 통화가 끝나야 결과가 나오는 게 아니라 말하는
  중에 조금씩 텍스트가 뜨는 것), A-2(화자 분리: "고객이 말했는지 상담원이 말했는지"
  구분), A-3(그 결과를 상담원 화면까지 실시간으로 전달), A-4(한 문장이 끝난 시점을
  판단 — 다음 기능들이 "이제 이 발화를 처리해도 되는가"를 아는 근거가 된다). 이 넷이
  안 되면 뒤의 모든 실시간 기능(B·C-5·C-6·A-5)이 애초에 입력을 못 받는다 — 그래서
  "필수" 등급이다.
- **A-5. 외국인 고객 지원(동시 통번역)** — 1차 범위(ⓑ)는 **한국어가 서툰 외국인 고객이
  한국어로 말할 때 그 발화를 정확히 받아 적는 것**이다. 그래서 1차 지표도 번역 품질이 아니라
  음성인식 정확도(WER/CER)다. 고객이 모국어로 말하면 한글로 번역하고 상담원 답을 모국어
  음성(TTS)으로 들려주는 것(ⓐ)은 여유 시 확장이다 — 구글 API가 이미 잘하는 영역이라 우리가
  더할 게 적다고 판단했다(`decisions/201`). 이게 **대기업 AICC 제품과 구분되는 이 프로젝트의
  차별점**이다.
- **B. 필요서류 자동 제시** — 상담원이 고객의 용건을 듣는 동안, 그 절차(예: "전입신고",
  "여권 재발급")에 필요한 서류 목록을 검색해서 화면에 카드 형태로 띄워주는 기능이자 메인
  기능이다. RAG 구조 가운데 **검색 단계가 실제로 돌아가는 곳**이다 — 지금 카드 문장은 검색된
  조항을 그대로 보여주고, 문장을 새로 쓰는 생성 단계(B-4~6)는 아직 폴백(스니펫 그대로)이다.
  서류를 묻는 질문이 64가지 서로 다른 민원 의도에 흩어져 있어(09-09 재측정) 상담원이
  전부 외울 수 없기 때문에 필요하다.
- **C-1~C-4. 컴플라이언스 감지** — 상담원이 하면 안 되는 말(예: 확인 안 된 정보를
  단정적으로 안내하기, 규정에 없는 약속하기)을 실시간으로 탐지해 경고하는 기능. "상담원의
  실수를 잡아주는" 방향이다.
- **C-5. 개인정보 실시간 마스킹** — 고객이 전화번호·주민등록번호·주소 같은 개인정보를
  말하면, 그 부분을 상담원 화면 자막과 DB 저장 양쪽에서 자동으로 가리는 기능. **애매하면
  무조건 가린다**(재현율 우선)는 원칙이라 "코어"로 분류했다 — 개인정보 유출은 이 서비스가
  절대 일으키면 안 되는 사고 유형이기 때문이다.
- **C-6. 콜 가드** — C-1~C-4와 정반대 방향으로, **고객의** 욕설·협박·성희롱을 탐지해
  상담원을 보호하는 기능. 네 번째 갈래인 **위기 신호**(정신적 고통)는 폭언과 대응이
  정반대라(통화를 끊지 않고 전문 기관으로 연결) 따로 판정한다. ⚠ 지금 화면에 뜨는 경고
  배너는 프론트 mock이 자체적으로 판정한 것이고, 서버 판정기(`ai/apps/call_guard/`)는 아직
  HTTP로 연결되지 않았다.
- **D. 통화 후 처리** — 통화가 끝난 뒤 자동으로 요약을 만들고 어떤 유형의 민원이었는지
  분류하는 기능(D-1~D-3, 아직 미구현). 여기에 **D-5 「통화 온도」**가 붙는다 — 각 화자의
  평소 목소리 톤을 기준선으로 삼아 목소리가 튀는 구간을 찾아 표시한다. ⚠ **감정을
  추정하는 기능이 아니다** — 팀은 「감정분석」이라는 말을 쓰지 않기로 했고(`decisions/203`,
  심리 상태를 판정한다고 주장하는 말이라서), 화면에 점수도 내지 않는다. 대체할 이름은 아직
  확정 전이고, 대시보드 시연 화면에는 옛 문구가 남아 있다(5.5장 ⑥).
- **E. 평가 하네스** — 이 프로젝트의 다른 모든 기능이 "정말 잘 되고 있는지"를 자동으로,

## 4. 어떻게 만들고 있나 (설계·프로세스)

### 코드 구조 — 허브-스포크 + 3계층

- `server/apps/hub`(장민석 담당)가 **"허브"** 다. 상담원 화면·게이트웨이와 주고받는 데이터
  형식(계약)만 정의하고, **판정 로직 자체는 갖지 않는다.**
- 실제 판정은 **"스포크"** 에서 한다 — 개인정보 마스킹은 `server/apps/masking`, 검색은
  `ai/apps/retrieval`, 콜 가드는 `ai/apps/call_guard`처럼 기능별로 분리돼 있다.
- 스포크가 아직 안 붙은 기능(예: 컴플라이언스 판정)을 호출하면 **거짓으로 통과시키지 않고
  "구현 안 됨"(HTTP 501)을 정직하게 돌려준다** — 이게 이 프로젝트가 데이터를 지어내지 않는
  방식의 코드 버전이다.
- 각 기능 내부는 다시 3겹으로 나뉜다: **domain**(순수 판정 규칙, 다른 것에 의존 안 함) →
  **app**(포트·유스케이스, "무엇을 할지"만 정의) → **adapter**(HTTP·데이터베이스 등 바깥세상과의
  실제 연결). 안쪽 계층은 바깥 계층이 뭔지 모른다 — 이렇게 해야 나중에 DB를 바꾸거나 API
  형식을 바꿀 때 판정 로직까지 건드리지 않아도 된다.
- **판정은 규칙, 설명만 AI** — "이 발화가 개인정보를 포함하는가", "이 상담을 종결해도 되는가"
  같은 판정은 재현 가능한 규칙(정규식·조건문)으로 하고, AI 모델(LLM)은 판정에 관여하지 않는다.
  이유: LLM은 같은 입력에도 다른 답을 낼 수 있어 "재현 가능한 평가"가 안 된다.

### 팀 운영 프로세스

- **결정 기록 39건** — 방향을 크게 바꿀 때마다 "맥락/선택지/결정/근거/되돌리는 법"을 문서로
  남긴다. 예: 도메인을 4개→1개로 줄인 결정, 데이터베이스를 PostgreSQL로 바꾼 결정.
- **절대 원칙 10가지**를 규칙으로 정해 두고 지킨다(코드 구조 규칙은 CI가 강제하고, 기준선 미달을
  CI 실패로 만드는 게이트는 아직 할 일이다 — `w2-baseline-gate`) — 그중 두 개만 소개하면:
  "측정하지 않은 수치를 기록하지 않는다", "실패를 지운 기록은 기록이 아니다"(안 된 실험도
  숨기지 않고 그대로 남긴다). 이 발표의 5·7장이 그 원칙을 실제로 지킨 결과다.
- **09-10에 담당 구역을 다시 나눴다** — 원래는 `server/`는 장민석만, `ai/`는 류준만 고칠 수
  있었는데, 기능 하나가 이 두 영역에 걸쳐 있는 경우가 많아서 "각자 자기 몫은 끝냈는데 서로
  연결이 안 되는" 문제가 반복됐다. 그래서 `server/`·`ai/`·`infra/`(배포) 세 영역을 세 사람
  누구나 고칠 수 있게 풀었다. **프론트엔드(조서희 담당)만 예외로 전담을 유지한다.**
  이걸 09-10에 바꾼 건 "일찍 실패를 인정하고 구조를 고친 것"이라고 본다.

## 6. 우리가 의도적으로 지키고 있는 것

"그냥 열심히 했다"보다 설득력 있는 건 **왜 이렇게 설계했는가**다.

- **절대 원칙을 실제로 지킨다** — 특히 "측정하지 않은 수치를 기록하지 않는다", "실패를 지운
  기록은 기록이 아니다". 위 5장의 C-5 ❌, F-2 측정불가
  표시가 그 증거다. 좋게 보이려고 숨기지 않았다.
- **방향을 바꿀 때마다 이유를 기록한다** — 도메인 축소, 데이터베이스 전환, 검색 순위 계산
  방식 변경, 담당 구역 재편까지, 전부 "왜"가 문서로 남아 있다.
- **코드 구조 규칙을 자동으로 강제한다** — 예를 들어 "서버(요청 경로) 코드는 AI 쪽 코드나
  torch·transformers 같은 모델 라이브러리를 import하면 안 된다" 같은 규칙을 사람이 리뷰로 잡는 게
  아니라 CI가 자동으로 깨지게 만들었다(`server/.importlinter`).
- **팀 작업 기록을 파일 단위로 쪼갰다** — 원래 진행 기록을 한 파일(`progress.markdown`)에 네
  명이 같이 썼더니, 그 파일을 건드린 커밋 37건 중 16건이 git 충돌(같은 파일을 동시에 고쳐서
  병합이 안 되는 상황) 처리였다. 항목 1건을 파일 1개로 쪼개 구조적으로 해결했다(`decisions/016`).
  상태 문서(`STATE.md`)도 같은 문제(커밋 63건 중 머지 커밋 19건)가 있어, 각자 자기 줄만 덮어쓰는
  표로 바꿨다(`decisions/101`).

## 9. 멘토에게 묻고 싶은 것

- **C-5처럼 절대 규칙이 뚫린 상태를 팀 스스로 먼저 발견하고 그대로 공개하는 방식**이 맞는
  방향인지 — 아니면 발표 전에 먼저 고쳐서 가져오는 게 나을지. 지금은 "안 된 것도 그대로
  남긴다"는 원칙을 일관되게 택했다.
- 지원 분야를 4개에서 1개(다산콜센터)로 좁힌 판단이 적절한 범위 관리였는지, 아니면 너무
  보수적으로 자른 것인지.
- 담당 구역을 프로젝트 도중(09-10)에 다시 나눈 것처럼, 팀 프로세스를 진행 중에 바꾸는 게
  이 단계에서 리스크가 큰 판단인지 — 우리는 "구멍이 반복돼서 바꿨다"고 보고 있다.
- 실시간 음성인식(A, 필수 블록)이 아직 0줄인 상태에서 나머지 핵심 기능(B·C-5·E)에
  먼저 집중한 우선순위 판단이 맞는지.
- 측정 결과가 "측정 불가"로 많이 남아 있는 게(F-2, 컴플라이언스 등) 발표에서 감점 요인이
  될지, 아니면 정직함으로 평가받을 수 있는지.
- **(지난 피드백 ⑤) 베테랑이 없을 때 일반 상담원에게 넘기는 폴백**이 괜찮은지 — 피드백은
  「베테랑만」이었는데, 우리는 "전화를 아예 못 받게 하는 것이 더 나쁘다"고 보고 폴백을 두되 그
  건수를 센다(5.5장).
- **(⑤) 「베테랑」 기준을 어디서 가져오면 되는지** — 지금 「근속 3년」은 피드백 때 나온 예시를
  그대로 쓴 값이라 우리 쪽 근거가 없다.
- **(①②③) 통화 단위 음성 데이터를 구할 곳이 있는지** — 가진 음성이 발화 단위 클립뿐이라 통화
