# 119. 레이턴시는 «구간을 쪼개» 합성 통화에서 잰다 — 브라우저 렌더는 재지 않는다

- 날짜: 2026-09-20
- 작성: 정성윤
- 상태: 채택 (설계 — 구현은 `w7-latency-budget`)
- 관련: `plan.md` 4.3절(레이턴시 예산) · `decisions/209`(합성 통화 — 「STT 미경유 상한」) · `w4-trigger-arrival-time`(도착 시각) · 절대 원칙 2·10
- 티켓: `w7-latency-budget`

## 맥락

7주차 목표가 「4.3절 예산이 실제로 지켜지는가」인데, **지금 구조로는 7주차에 가도 숫자가 안 나온다.**
2026-09-20 에 코드를 전수 확인한 결과는 이렇다.

| 구간 | 지금 | 누가 아는가 |
|---|---|---|
| ① 발화 종료 → STT 최종 도착 | ✅ 잰다 — `received_at_ms − utterance_end_ms` | 콜 미디에이터(`call_registry.ts`) |
| ② 트리거 판정 | ✅ 실시간 경로는 **측정값**(`trigger_at_ms`) | 서버 |
| ③ 검색 | ❌ **없다** — ②③④가 한 덩어리 | 서버 |
| ④ 생성 | ❌ **없다** — 위와 같다 | 서버 |
| ②+③+④ 합 | ✅ `internal_latency_ms` 로 재고 DB 에 저장한다 | 서버(`recommendation_interactor.py`) |
| ⑤ 전송(서버 → 방송) | ❌ 없다 | 콜 미디에이터 |
| ⑥ 브라우저 렌더 | ❌ 없다 | 대시보드 |

**`e2e_latency_ms` 는 컬럼·DTO 가 있는데 아무도 값을 넣지 않는다**(전수 grep — 스키마·INSERT 만 있고
대입이 없다). 즉 지금까지 **항상 NULL** 이었다. 서버가 자기가 모르는 값을 지어내지 않은 것이라
**그 자체는 옳다** — 다만 채울 주체를 정한 적이 없다.

## 결정 — 넷

**① `internal_latency_ms` 의 뜻을 코드 쪽으로 고정한다.**
기획서 4.3 은 내부 처리를 「트리거 발동 → **카드 표시**」로 적었지만, 코드가 재는 것은
**「트리거 판정 → 카드 완성(서버)」**이다(⑤⑥이 빠져 있다). **이름이 같은 두 수를 섞지 않는다** —
문서·발표에서는 이 값을 **「서버 내부 처리」**로 부르고, 화면까지의 값은 따로 적는다.
p95 ≤ 1,000ms 판정은 **이 값**에 건다(통제 가능한 구간이다).

**② ③④를 쪼갠다.** 예산표는 검색 150ms·리랭킹 200ms·생성 500ms 로 쪼개져 있는데 실제로는
합(`internal_latency_ms`) 하나만 남아 **「어디가 느린지」를 못 짚는다.** `w7-latency-budget` 의
완료 조건(「느리다가 아니라 어디가 느리다」)이 요구하는 것이 바로 이것이다.
→ 인터랙터가 `retrieval_ms`·`generation_ms` 를 따로 재어 **방송 메시지와 로그에 싣는다.**

**③ 저장은 나중, 측정은 지금.** 두 값을 DB 컬럼으로 만들면 **운영 마이그레이션이 사람 손으로** 따라붙는데
(런북 17장), **운영 `recommendation` 은 지금 0행**이라 당장 쌓일 데이터가 없다.
그래서 **1단계는 스키마 변경 없이** 방송·로그에만 싣고, 운영 통화가 쌓이기 시작하면 컬럼으로 승격한다.
`e2e_latency_ms` 는 **콜 미디에이터가 방송 직전에 계산**해 채운다(`방송 시각 − utterance_end_ms`) —
서버는 그 시각을 모른다.

**④ 숫자는 골든셋이 아니라 «합성 통화」에서 나온다.** 골든셋에는 시계가 없어
**평가 하네스는 계속 「측정 불가」로 보고한다**(절대 원칙 10 — 지금 그렇게 하고 있고 바꾸지 않는다).
지연 수치는 이미 24건을 왕복시키는 `scripts/persona_sim/e2e_check.py` 보고서가 낸다.

## 재지 않기로 한 것 — ⑥ 브라우저 렌더

대시보드가 카드를 화면에 그린 시각은 **재지 않는다.** 재려면 프론트에 계측을 심고 그 값을 서버로
되돌리는 경로(새 엔드포인트)가 필요한데, `apps/` 는 조서희 님 전담이고 남은 기간에 그 왕복을 새로 만들
만큼 값이 크지 않다. 기획서도 E2E 를 **「통제 밖이라 목표를 걸지 않되 구간을 분리한 사실을 성과로」**
적었다. 그 취지대로 **「어디까지 쟀고 무엇을 안 쟀는지」를 명시**하는 쪽을 택한다.

## ⚠ 합성 통화로 재면 ①이 빠진다

재생기는 **STT 를 거치지 않고 글자를 바로 넣는다** — 그래서 ①(발화 종료 → STT 최종 도착)이 **0** 이다.
따라서 합성 통화에서 나온 E2E 는 **실제보다 짧다.** 보고할 때 규칙은 `decisions/209` 와 같다.

- 합성 수치에는 **`source: synthetic` + 「STT 미경유」** 를 붙인다.
- ①은 **V4 실측 346ms** 가 따로 있으므로 **더해서 「추정 E2E」로 적되, 합산이 추정임을 같은 줄에 쓴다.**
- 운영 통화가 생기면 ①까지 실측으로 대체한다.

## 되돌리는 법

- ③을 되돌리려면(= 처음부터 DB 에 남기려면) `db/generate_schema_docs.py` 의 `TABLES` 에
  `recommendation.retrieval_ms`·`generation_ms` 를 넣고 `schema.sql` 을 다시 만든 뒤 **운영 마이그레이션**을 한다.
- ④를 되돌리려면(= 하네스가 재게 하려면) 골든셋 항목에 도착 시각을 넣어야 한다 —
  **작성 골든셋에 시계를 지어 넣는 것**이라 절대 원칙 2 에 걸린다. 권하지 않는다.
- ⑥을 되돌리려면 프론트 계측 + 되돌리는 엔드포인트가 필요하다(조서희 님 협의).
