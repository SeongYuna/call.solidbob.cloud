# 220 — F-3 을 「통화 수신 전 고객 브리핑」으로 되살린다: 사실은 규칙이 모으고, 통화 목적 추정과 세 줄 브리핑만 모델이 쓴다

- 날짜: 2026-10-06
- 작성: 류준 (`2xx` 번호대) — **사용자(류준) 지시. 팀 회의 합의 없음**
- 상태: **채택(설계) — 구현 전.** 화면 카드는 조서희(`w8-f3-briefing-card-ui`), 나머지는 류준(`w8-f3-customer-briefing`)
- 관련: `plan.md` F-3(「통화 간 고객 식별이 없어 보류」) · `304`(발신 번호 HMAC 고객 식별) · `320`(교환기가 연결 전에 부른다 — 시연은 미디에이터 대리) · `322`(읽기 문) · `146`(운영 요약 모델 kanana · 판정은 규칙, 설명만 모델) · `209`(합성 통화) · `132`(F-1·G·H·I 미착수 — **F-3 은 대상이 아니다**) · `138`(동결 — 시연 화면에 닿는 변경 예외) · `129`(10-15 부터 새 기능 금지)

## 맥락

상담원은 지금 **전화를 받고 나서야** 고객이 누구인지, 전에 무슨 일로 전화했는지 알 수 있다. 「통화받기」 모달에는 고객 정보가 하나도 없다(`apps/call/src/components/AgentCallBox.tsx`).
재상담 이력 카드(`CustomerHistorySummaryCard`)는 mock 으로만 있고, 실서버 모드에서는 null 이다 — **브라우저가 현재 통화의 `customer_id` 를 알 방법이 없어서**다(`apps/call/src/mock/customerHistory.ts` 주석). 그것은 의도된 설계다(`304`·`322` — 고객 HMAC 을 화면에 내보내지 않는다).

`plan.md` 의 **F-3(동일 고객 반복 문의 연결)은 「다산 데이터에 고객 ID 가 없다」는 이유로 보류**됐다. 그 이유는 `304`(2026-09)로 사라졌다 — 발신 번호 HMAC 으로 `call.customer_id` 가 쌓이고 있고, 고객별 통화 목록 API(`GET /hub/calls?customer_id=`)도 있다. `132` 가 착수하지 않기로 한 것은 F-1·G·H·I 이고 **F-3 은 거기 들지 않는다.**

사용자 요구(10-06): 「통화받기를 누르기 전에, 단순 RAG 가 아니라 AI 가 고객의 전 통화 내역·이전 문의·컴플레인을 파악해 **통화 목적을 유추**하고, 가능한 선에서 통화 목적 안내와 고객 정보를 자동으로 보여준다. 지금 목업 대본에 맞게 고객을 만들어 기능을 완성한다 — 필요하면 대본을 더 만든다.」

## 선택지

- **A. 서버가 브리핑을 만든다** — `call_id` → 고객 → 지난 통화 사실을 규칙으로 모으고, 모델은 목적 추정과 세 줄만 쓴다. 화면은 `call_id` 로 받아 그린다
- B. 화면이 지난 통화 목록을 받아 브라우저에서 조합한다 — 브라우저가 고객 ID 를 알아야 해 `304`·`322` 와 부딪힌다. **불가**
- C. 규칙만 — 「지난 통화 유형 = 이번 목적」. 결정적이지만 요구(「AI 가 유추」)와 다르다

## 결정

**A.** C 는 모델이 실패하거나 검사에 걸렸을 때의 **폴백**으로 둔다.

### 1. 사실은 규칙이 모은다 (판정 없음)

서버가 이번 통화의 `call.customer_id` 로 **이번 통화보다 앞선** 통화를 최근순 최대 5건 읽는다. 브리핑 재료는 이것뿐이다 —

| 재료 | 출처 |
|---|---|
| 지난 통화 수 · 날짜 · 유형(D-2) | `call` |
| 확정된 요약(없으면 초안 — 화면에 「초안」 표시) | `call.summary_text`·`summary_confirmed_at` |
| 마치지 않은 후속조치 | `follow_up_action`(status `draft`·`confirmed`) |
| 지난 통화의 필요서류 미완료 절차 | `closure.verdict = 'incomplete'` 의 `procedure` |
| 고객 쪽 콜 가드 범주 | `call_guard_flag.category` (문구는 싣지 않는다) |
| 블랙리스트 적용 중 여부 | `blacklist_entry` (사실만 — 「위험 고객」 같은 말을 만들지 않는다) |

- **상담원 컴플라이언스 위반(`compliance_flag`)은 싣지 않는다** — 고객 정보가 아니라 상담원 기록이다.
- 지난 통화가 0건이면 모델을 부르지 않고 `first_contact`. 고객을 식별하지 못했으면(키·번호 없음) `unidentified`.

### 2. 모델이 쓰는 것은 둘뿐이다 (설명)

운영에 이미 있는 요약 모델(`146` — kanana-1.5-2.1B, Ollama, `POSTCALL_MODEL`)을 그대로 쓴다. 입력은 1절의 사실(마스킹본)만이다.

- **추정 목적** — 정해진 목록 중 하나: `재문의` · `후속 확인` · `서류 보완` · `컴플레인` · `신규 문의`. 목록 밖이면 규칙 폴백.
- **브리핑 세 줄** — 지난 통화를 상담원이 3초 안에 읽을 수 있게.

모델 출력은 규칙이 검사한다(`summary_problems` 와 같은 규칙 — 재료에 없는 숫자 · 금지 표현(부록 A-1: 「위험」·점수·「확실」 등) · 길이). **걸리면 규칙 브리핑으로 내려간다** — 규칙 폴백은 가장 최근 통화의 유형·미완료 후속조치·미완료 절차로 목적을 고르고(우선순위 `서류 보완` > `후속 확인` > `컴플레인` > `재문의`) 사실을 줄로 나열한다.

「목적」은 판정이 아니라 **설명**이다(절대 원칙 9) — 화면에 반드시 **「추정」** 으로 표시하고, 근거가 된 지난 통화를 같이 보여 준다. 상담원의 행동을 막거나 배정을 바꾸지 않는다.

### 3. API 계약 — `GET /hub/calls/{call_id}/briefing`

인증은 다른 통화 읽기와 같다(`require_reader`, `322`). **고객 ID(HMAC)·발신 번호·`display_hint` 를 싣지 않는다.**

```json
{
  "call_id": "syn-brief-a-03-…",
  "status": "ready",                       // ready | first_contact | unidentified
  "prior_call_count": "2",
  "purpose": {
    "category": "서류 보완",                 // 재문의 | 후속 확인 | 서류 보완 | 컴플레인 | 신규 문의 | null
    "text": "지난 통화에서 안내한 위임장을 준비하다 막혀 다시 건 것으로 보입니다",
    "source": "model"                        // model | rule
  },
  "briefing_lines": ["…", "…", "…"],
  "evidence": [
    {"call_id": "…", "started_at": "2026-10-05T14:02:00+09:00", "inquiry_type": "일반행정",
     "summary_confirmed": "true", "incomplete_procedures": ["DASAN-TERM-4.1"]}
  ],
  "signals": {"open_follow_ups": "1", "call_guard_categories": ["insult"], "blacklisted": "false"},
  "generated_at": "2026-10-06T…"
}
```

- 없는 통화 404. `first_contact`·`unidentified` 는 `purpose: null`, `briefing_lines: []`.
- 결과는 `call_id` 별로 서버 메모리에 캐시한다 — **모델은 통화당 한 번만** 부른다. 모델 시간 상한 10초, 넘으면 규칙 폴백.
- 화면은 콜 미디에이터의 `started`(이미 방송 중, `{call_id}`)를 받으면 이 API 를 부른다. 새 WS 메시지는 만들지 않는다.

### 4. 「누르기 전」 — 시연 경로에서 만든다

상담원 마이크 경로는 「통화받기」를 눌러야 통화가 생기고 발신 번호도 없다. 「누르기 전」이 있는 경로는 **교환기(완성본, `320`)** 와 **대본 재생기(시연)** 다. 이번 범위는 재생기다.

- 재생기(`services/call-mediator/scripts/replay_persona_call.ts`)에 **`--ring-seconds N`**: 채널을 열어 통화를 만들고(`started` 방송) N초 동안 발화를 보내지 않는다 = 벨이 울리는 시간. 그동안 화면이 브리핑을 받는다.

### 5. 대본 고객 — 지난 통화를 실제 파이프라인으로 쌓는다

새 묶음 `scripts/persona_sim/dasan-briefing/` — 고객 셋, 각자 **지난 통화 1~2건 + 이번 통화 1건**, 고객마다 같은 가짜 발신 번호(실존 불가 번호, `209`):

| 고객 | 지난 통화 | 이번 통화 | 정답 목적(라벨) |
|---|---|---|---|
| A | 위임 등본 발급 문의 — 위임장·신분증 안내(필요서류 일부 미안내) | 「서류 하나 빠졌다고 반려됐는데요」 | 서류 보완 |
| B | 단수 민원 — 처리 지연에 대한 불만(톤 `raised`, **욕설·폭언 없음** — `209` 4항) · 후속조치 「담당 부서 회신」 | 「그때 연락 준다더니」 | 컴플레인 |
| C | 여권 재발급 문의(외국인 고객, `4.23`) · 후속조치 「접수 결과 확인 안내」 | 「접수한 거 어떻게 됐어요」 | 후속 확인 |

- **지난 통화는 DB 에 직접 쓰지 않는다.** 재생기로 실제 파이프라인(마스킹 → 검색 → 필요서류 → 콜 가드 → 통화 후 요약)을 태워 쌓는다 — 그래야 「AI 가 쌓인 이력을 읽는다」가 사실이 된다.
- 기존 SYN-006→007(같은 번호 재인입)도 그대로 브리핑 대상이 된다.

### 6. 측정 — 지어내지 않는다

- 대본마다 **정답 목적을 브리핑 출력을 보기 전에** 라벨로 적는다(위 표 + 기존 재인입 대본). 채점은 범주 글자 일치(규칙).
- 결과는 「`source: synthetic` · 대본 n건 · 상한」으로만 기록한다 — 대본을 쓴 사람이 정답도 쓴 값이다.
- **일반 성능은 「측정 불가」** — 실제 재상담 골든셋이 없다. 숫자를 지어내지 않는다(절대 원칙 2·10).
- 모델 출력이 같은 입력에도 달라질 수 있다(`146` 갱신 절) — 몇 번 돌려 범주가 바뀌는지 같이 적는다.

### 7. 담당

| 무엇 | 누구 | 티켓 |
|---|---|---|
| 서버 슬라이스(`briefing`) · 모델 어댑터(`ai/`) · 재생기 `--ring-seconds` · 대본 · 채점 | 류준 | `w8-f3-customer-briefing` |
| 「통화받기」 모달의 브리핑 카드 | **조서희** | `w8-f3-briefing-card-ui` |

## 근거

- **원칙 9**: 사실(이력)을 고르는 것은 규칙, 모델은 그 사실로 «왜 전화했을까» 를 **설명**만 한다. 목적이 틀려도 상담원 행동·배정은 바뀌지 않는다.
- **`304`·`322`**: 고객 ID 는 서버 안에서만 쓴다. 화면이 받는 것은 브리핑 문장과 지난 통화 날짜·유형뿐이다.
- **비용·지연**: 통화당 모델 1회, 캐시. 운영 c7i.2xlarge 에서 같은 모델 요약이 2.5~8초(`146`) — 벨 시간 안에 들어온다.
- **`138` 예외**: 시연 화면에 닿는 변경이다(`146` 과 같은 근거). **`129` 마감(10-15) 전에 넣는다.**

## 알고 가는 것

- 시연 경로(재생기)에서만 「누르기 전」이 성립한다. 상담원 마이크 경로와 실제 교환기 연동은 이번 범위가 아니다.
- 모델 목적 추정의 정확도는 대본 상한만 잴 수 있다.
- 동명이인·번호 공유(가족이 같은 번호) 같은 고객 식별의 한계는 `304` 그대로다 — 브리핑이 다른 사람의 이력을 보여줄 수 있다. 화면에 「같은 번호로 걸려 온 지난 통화」라고 쓴다(「이 고객의」라고 단정하지 않는다).

## 되돌리는 법

- **모델만 끈다**: 브리핑은 새 설정 키를 만들지 않고 요약과 같은 `OLLAMA_URL` + `POSTCALL_MODEL` 이 있을 때만 모델을 쓴다. 둘이 없으면 처음부터 규칙 브리핑만 나간다(`/health` `spokes` 에 `briefing` 은 있고 `briefing_model` 은 없다).
- **기능 전체를 뺀다**: `server/main.py` 의 브리핑 라우터 등록 한 줄을 지우고 화면 카드를 숨긴다(화면은 404 를 「브리핑 없음」으로 그린다).
- 대본 묶음은 지우지 않는다(`209` — 실패도 기록).
