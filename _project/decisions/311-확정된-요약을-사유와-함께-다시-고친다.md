# 311 — 확정된 요약을 사유와 함께 다시 고치고, 고치기 전 값을 남긴다

**날짜**: 2026-09-15
**작성**: 장민석 (브랜치 `server`)
**관련**: `decisions/310`(요약 확정 — 「확정 후 수정 경로가 없다」 가 남는 것 첫 줄) · 부록 A-1 · 절대 원칙 8

## 맥락

`decisions/310` 은 확정을 한 번으로 못 박았다. 잘못 확정하면 DB 수작업 말고는 고칠 길이 없었다. 사용자 지시로 재수정 경로를 만든다.

## 결정 (사용자 지시, 2026-09-15 — 설계는 권고안대로)

- `POST /hub/calls/{call_id}/summary-revision {summary_text, reason, inquiry_type?, follow_up_actions[]}` · `GET /hub/calls/{call_id}/summary-revisions`
- **확정된 요약만** 고친다 — 확정 전이면 409(확정을 먼저). 확정(310)은 여전히 한 번이고, 그 뒤 바꾸는 것은 이 경로다
- **사유 필수** · 요약·유형·후속조치·사유 모두 저장 전 마스킹 · **상담원 토큰 필수, 누가 고쳤는지는 저장 안 함**(310 과 같은 이유)
- 새 테이블 **`call_summary_revision`** — 고치기 **전** 요약·유형 + 사유 + 시각. 새 값은 `call` 에
- 이전 확정 후속조치는 **지우지 않고 `superseded`** 로, 새 것은 `confirmed` 로
- `summary_confirmed_at` 은 **처음 확정 시각 그대로** — 고친 시각은 이력의 `revised_at`

## 근거

- 틀린 확정을 고친 흔적이 사라지면 «처음부터 맞았던 기록» 처럼 보인다 — 절대 원칙 8 의 방향. 그래서 덮어쓰기가 아니라 이력이다
- 사유를 받는 이유는 블랙리스트 만료 변경(309)과 같다 — 확정된 기록을 바꾸는 행위라 왜 바꿨는지가 남아야 한다

## ⚠ 남는 것

- 이력의 사유·이전 요약도 무기한 보관된다 — 보존 기간(312)은 블랙리스트만 다룬다
- 누가 고쳤는지 모르므로 «같은 사람이 계속 고치는가» 는 볼 수 없다 — 부록 A-1 을 택한 대가다
- 운영 DB 마이그레이션 필요(`db/migrations/2026-09-15-summary-revision-app-setting.sql`, 27 → 28)

## 되돌리는 법

`main.py` 에서 `summary_revision_router`·`summary_revision_list_router` 를 빼면 닫힌다. 완전히 지우려면 `summary_revision_*` 슬라이스와 생성기의 테이블을 지우고 운영에서 `DROP TABLE "call_summary_revision"`.
`superseded` 로 바뀐 후속조치는 그대로 남는다(되돌리지 않는다).
