# 318 — 화면에 나가는 판정은 기록 실패로 막지 않는다 · 저장이 목적인 경로는 5xx 그대로

**날짜**: 2026-09-22
**작성**: 장민석 (브랜치 `server`)
**관련**: 09-18 컴플라이언스 「저장 실패는 로그, 응답 그대로」 · 09-20~21 콜 가드 같은 규칙(`0.1.19`) · 09-22 사후 검토(`w5-server-change-review`) · 티켓 `w6-store-failure-policy`

## 맥락

기록이 **우리 쪽 사정(DB 흔들림)으로** 실패할 때 경로마다 달랐다 — 콜 가드·컴플라이언스는 「200 + 로그」, 추천·필요서류 판정은 500.
500 이면 **상담원 화면의 카드·체크리스트가 기록 실패 때문에 같이 사라진다.** 콜 가드가 09-21 에 같은 이유로 「200 + 로그」로 바뀌었다.
또 필요서류 판정 저장소는 없는 통화(호출자 실수)를 원시 FK 오류(500)로 올리고 있었다.

## 결정 — 한 줄 규칙

**결과가 상담원 화면에 나가는 판정 경로는 기록이 실패해도 결과를 돌려주고 경고 로그를 남긴다. 저장 자체가 목적인 경로는 5xx 를 낸다. 호출자 실수(없는 통화·없는 전사 구간)는 어느 쪽이든 4xx 다.**

| 경로 | 기록 실패(DB) | 호출자 실수 |
|---|---|---|
| 콜 가드 · 컴플라이언스 (기존) | 200 + 로그 | 404 |
| **추천**(`/hub/recommendations`) — 이번 | 200 + 로그, `card_id` 는 null(카드 피드백만 못 남긴다) | 404 |
| **필요서류 자동 판정 · 체크리스트 판정** — 이번 | 200 + 로그 | **404**(전엔 500 — 저장소가 FK 위반을 `CallNotStartedError` 로 올리게 고쳤다) |
| 전사 저장 · 통화 시작 · 요약 확정·재수정 · 블랙리스트 · 통화 종료 | **5xx 그대로** | 4xx |

로그에는 예외 **타입 이름만** 싣는다 — 메시지에 접속 정보가 들어갈 수 있다(SEC-2).

## 근거

- 판정 경로에서 기록은 **부산물**이다 — 상담원이 지금 봐야 하는 것은 카드·체크리스트이고, 그것이 DB 한 번 흔들림으로 사라지면 기능 자체가 멈춘 것처럼 보인다
- 전사 저장·요약 확정은 **저장이 곧 기능**이다 — 조용히 200 을 주면 「저장됐다」로 오해해 데이터가 사라진다. 전사는 마스킹본 저장이 SEC-1 의 앞단이기도 하다
- 호출자 실수를 삼키면 연동 오류가 숨는다 — 콜 미디에이터가 `POST /hub/calls` 를 빠뜨린 것을 아무도 모르게 된다

## ⚠ 남는 것

- 삼킨 기록 실패는 **로그에만** 남는다 — 「운영에서 한 번도 저장 안 됨」이 조용히 이어질 수 있다(09-20 미결이 짚은 것과 같다). 운영 로그를 보는 사람이 있어야 한다
- 추천이 저장되지 않은 카드는 `card_id` 가 null 이라 그 카드의 「사용 표시」는 서버에 남지 않는다(화면은 이미 null 카드를 거른다)

## 되돌리는 법

세 인터랙터(`recommendation_interactor`·`required_docs_detection_interactor`·`closure_check_interactor`)의 `try/except` 를 걷는다. 저장소의 FK → `CallNotStartedError` 변환은 되돌리지 않아도 된다(500 → 404 는 그 자체로 맞다).
