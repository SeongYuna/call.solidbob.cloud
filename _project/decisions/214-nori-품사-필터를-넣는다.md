## 맥락

ES 분석기 `korean` 은 `kb_nori` 토크나이저 뒤에 `nori_readingform`·`lowercase` 만 있었다 — **품사 필터(`nori_part_of_speech`)가
없었다.** 그래서 조사·어미·접사가 전부 토큰으로 색인·질의되고, 내용어가 적은 발화에서는 그것들이 BM25 순위를 정했다.

GS-205(「이건 시에서 결정해주시는 건가요」)가 그 경우다. 내용어는 `결정` 하나인데, 2026-09-22 `_analyze` 로 본 토큰은 —

| 분석기 | 토큰 |
|---|---|
| 필터 없음(이전) | 이건 · 이거 · ㄴ · 시 · **에서** · 결정 · **해 · 하 · 아** · 주 · 시 · **는** · 건가요 · 것 · 이 · **ᆫ가요** |
| 품사 필터(nori 기본값) | 이건 · 이거 · 시 · 결정 · 주 · 건가요 · 것 · 이 |

`해지` 를 쪼갠 `해` 가 `해주시는` 의 `해` 와 맞아 「신청·해지」 조항이 상위 5를 채웠고, 정답(TERM-1.2)은 BM25 26위였다.

09-22 오전의 임시 인덱스 실험(골든셋 옛 판, BM25 만)에서 필터를 넣으면 GS-205 가 2위로 오르고 Recall@5 가 올랐지만 GS-206·241 을
잃었다. 그때는 **「골든셋 한 번으로 고르는 것」이라 채택하지 않고 미결로 뒀다.** 이 결정은 그 미결을 닫는다.

## 선택지

| | 내용 | 비고 |
|---|---|---|
| A | 그대로 둔다 | 조사·어미가 순위를 정하는 구조적 결함이 남는다 |
| **B** | **`nori_part_of_speech` 를 nori 기본 제외 품사로 넣는다** | 목록을 우리가 고르지 않는다 |
| C | `stoptags` 를 골든셋 결과를 보며 손으로 고른다(예: `NNB`·`VX` 추가) | 96건에 맞춘 목록이 된다 — `123` 과 같은 이유로 하지 않는다 |

## 결정

**B.** 분석기 `korean` 의 필터를 `["nori_part_of_speech", "nori_readingform", "lowercase"]` 로 바꾼다.

- **제외 품사는 nori 기본값이다** — `stoptags` 를 주지 않는다. 기본값은 E(어미) · IC · J(조사) · MAG · MAJ · MM · SP · SSC · SSO · SC ·
  SE · XPN · XSA · XSN · XSV · UNA · NA · VSV. **미리 정해진 목록이라 골든셋을 보고 움직인 값이 없다.** 테스트가 사용자 정의 필터를 막는다 —
  목록을 바꾸려면 이 결정을 먼저 고친다.
- 순서: 품사 태그는 토크나이저가 붙이므로 품사 필터가 **맨 앞**이다.
- 결정자: 류준(사용자). 근거는 「구조적 결함을 고친다」이고, 아래 수치는 그 근거가 아니라 **부작용이 크지 않은지 확인한 것**이다.

## 근거 — 전후 실측

**조건** — 2026-09-22 · 커밋 `f7a2dd1` + 이 변경(작업 트리) · 로컬 ES 9.5.1(127.0.0.1:9200) · 골든셋 `golden-set/v1-150.json`(판 `v1-150.1`,
모듈 B **n 96**, B-6 **n 24**) · 로컬 CPU(Darwin arm64).
**임시 인덱스 두 개**(`qa-nori-base` 이전 분석기 / `qa-nori-pos` 새 분석기)에 **같은 청크 100개 · 같은 KoE5 벡터**를 넣고 잰 뒤 **둘 다 지웠다.**
운영과 같은 이름인 `callguard-kb-single` 은 건드리지 않았다. 적재는 버리는 스크립트(저장소의 `es_index.build_settings` · `build_mapping` ·
`index_into` 를 그대로 호출, 이전 쪽은 필터 목록에서 품사 필터만 뺐다)로 했다 — `index_knowledge_base.py` 가 인덱스 이름을 받지 않아서다.

```
scripts/compare_retrievers.py --index qa-nori-base --only bm25,dense --embed-model <models/koe5>
scripts/compare_retrievers.py --index qa-nori-pos  --only bm25,dense --embed-model <models/koe5>
scripts/measure_no_answer_threshold.py --only bm25   # SINGLE_INDEX 를 임시 인덱스로 바꿔 끼워 실행
```

| 구성 | 분석기 | Recall@5 | hits | MRR | top1 |
|---|---|---|---|---|---|
| BM25 | 이전 | 0.812 | 78/96 | 0.635 | 48 |
| BM25 | **품사 필터** | **0.844** | **81/96** | **0.682** | **54** |

- **BM25 이전 값(0.812 / 0.635)은 같은 날 기록 DB run_id 4(운영 구성)와 같다** — 임시 인덱스가 운영 인덱스와 같은 조건이라는 확인이다.
- **dense 는 96건 전부 상위 5가 순서까지 같다** — 분석기는 `text`·`title` 에만 걸리고 벡터는 같은 것을 넣었으니 당연한 결과이고, 그걸 확인했다.
- BM25 **얻은 것 5건**: GS-205(없음→2위) · GS-219(없음→2) · GS-225(없음→5) · GS-226(없음→4) · GS-290(없음→1).
  **잃은 것 2건**: GS-206(2위→없음, 「버스 첫차가 몇 시인지」) · GS-241(5위→없음, 「요금이 너무 이상한데 다시 봐주실 수」).
  상위 5 안에서 순위가 바뀐 항목 25건 중 올라간 것 16 · 내려간 것 9.
- 09-22 오전 실험(옛 판)과 얻은·잃은 목록이 조금 다르다 — 그때 얻은 GS-102 가 이번엔 없고 GS-226 이 새로 있다. 사이에 골든셋 질의 14건이
  바뀌었다(`decisions/212`). **잃은 두 건은 두 번 다 같다.**
- **B-6(정답 없음) BM25 1순위 점수**: 이전 중앙값 7.62 · 최대 14.52 → 필터 중앙값 6.36 · 최대 14.27. 정답 있음(상위 5 적중) 최소값과
  겹치는 것은 그대로다 — **문턱 하나로 못 가른다는 결론은 바뀌지 않는다.** 필터 뒤 GS-723(「장롱 버리려면 스티커는 어디서 사요」)은
  BM25 가 **0건**을 돌려준다(남는 토큰이 지식베이스와 하나도 안 맞는다) — B-6 항목이라 옳은 기권이지만, 정답 있는 발화에서도
  같은 일이 생기면 「관련 문서 없음」이 된다. 이번 96건에서는 0건 반환이 없었다.

### 이 수치를 어떻게 읽나 — 정직하게

- **필터 채택의 판단에 같은 골든셋이 쓰였다.** 오전 실험 결과를 보고 정했으므로 위 +0.032 는 독립 검증이 아니다. 대신 제외 품사 목록은
  nori 기본값에서 **한 글자도 움직이지 않았다** — 골든셋이 고른 것은 「넣느냐」 하나뿐이다(`123` 의 취지).
- 차이 3건(81 vs 78)은 표본 96에서 작다. 1회 측정이고(BM25 는 결정적이라 반복해도 같다), 오류 주입 조건은 재지 않았다.
- **운영 품질에 미치는 영향은 작다.** `124` 이후 운영 검색은 **KoE5 dense** 이고, BM25 는 `FallbackRetriever` 가 **dense 가 0건일 때만**
  내려가는 대체 경로다 — 벡터가 적재된 인덱스에서 kNN 이 0건을 내는 일은 드물다. 이 필터가 실제로 효과를 내는 때는
  ① 인덱스에 벡터가 없을 때(재적재를 `--no-embed` 로 했거나 모델 없이 적재) ② `124` ⑥ 에 따라 **p95 가 1,000 ms 를 넘어 임베딩을 끄고
  운영 구성(BM25)으로 판정할 때**다. 즉 **대체 경로와 판정 예비안을 단단하게 하는 변경**이지 운영 수치를 올리는 변경이 아니다.

## 운영 반영 — 재적재가 필요하다 (정성윤)

분석기는 **색인 시점**에 적용된다. 코드만 바뀌고 운영 `callguard-kb-single` 은 옛 분석기 그대로다 — **재적재 전까지 운영에는 효과가 없다.**

1. **이 변경이 든 서버 이미지가 먼저 떠야 한다.** 런북 15-1·`124` ②의 재적재는 `scripts/index_knowledge_base.py` 와 `knowledge-base/` 만
   파드에 풀고, 분석기 설정은 **이미지 안의** `ai/apps/retrieval/adapter/outbound/es_index.py` 에서 읽는다. 옛 이미지에서 돌리면 옛 분석기로
   다시 만들어질 뿐이다. `ai/` 코드가 바뀌었으니 서버 이미지 태그도 올라가야 한다(`tag-check`) — 태그는 중앙에서 올린다.
2. 새 이미지가 뜬 뒤, **모델 벡터 재적재와 같은 명령**(런북 「② 벡터 재적재」, `decisions/124` 4단계):
   ```bash
   $K exec deploy/callguard-server -- python /app/scripts/index_knowledge_base.py --to-es --recreate --embed-model /models/koe5
   ```
   ⚠ **`--embed-model` 을 빼거나 `--no-embed` 로 돌리면 벡터 없는 인덱스가 된다** — dense 가 전부 0건이 되고 모든 검색이 BM25 대체
   경로로 내려간다(조용히). 반드시 벡터와 함께 다시 만든다.
3. 확인: `_analyze`(`analyzer: korean`, 「이건 시에서 결정해주시는 건가요」)에서 `에서`·`는`·`해` 가 사라졌는지 · 문서 수 100 ·
   `embedding` 필드가 `dense_vector` 인지 · `/health` spokes 에 `retrieval_dense`.

## 되돌리는 법

`es_index.build_settings()` 의 필터 목록에서 `"nori_part_of_speech"` 를 빼고 테스트 기대값을 되돌린 뒤, 그 이미지로 위 2단계의
재적재를 한 번 더 한다. 매핑 필드는 바뀌지 않았으므로 다른 코드는 손댈 것이 없다. 이 결정 파일은 지우지 않고 상태만 「철회」로 바꾼다(절대 원칙 8).
