## 맥락

[8주 마일스톤](/docs/08/) 4주차는 「nori 인덱스 · dense_vector · RRF 병합」이고, 기획서·요구사항표(3.1절 B-1~B-3)는
검색을 **「nori + dense_vector + RRF」** 로 적었다. 그래서 암묵적으로 **하이브리드가 최종형**이라고 가정해 왔다.
2026-09-15 에 세 가지를 처음으로 **같은 골든셋·같은 커밋·같은 머신**에서 나란히 쟀다.

```
측정일 2026-09-15 · 커밋 38f2fc3-dirty · 골든셋 v1-150 B 항목 n96 · 지식베이스 98조항
.venv/bin/python scripts/compare_retrievers.py [--device mps]
임베딩 models/koe5 · 리랭커 models/bge-reranker-v2-m3 · Darwin arm64 (로컬)

변형                          Recall@5   hits    MRR   top1 │ p95 CPU   p95 MPS
bm25 (지금 운영)                0.833   80/96  0.659    51  │     4ms      7ms
dense (KoE5 kNN)                0.979   94/96  0.885    78  │    59ms     50ms
hybrid RRF k=60 cand=20         0.927   89/96  0.828    73  │    58ms     39ms
  (k=10 · 30 · 100)            0.927   89/96  0.828~0.835   │
rerank(bm25) cand=5             0.833   80/96  0.795    73  │   494ms    237ms

rerank(hybrid) cand=20          0.979   94/96  0.916    83  │  1844ms   1197ms
```

두 가지가 예상과 달랐다.

1. **RRF 가 dense 를 끌어내린다.** dense 단독 94건 → 하이브리드 89건. BM25 가 놓친 16건 중 **15건을 dense 가
   찾는데**, 병합하면 BM25 쪽 오답이 순위를 나눠 먹어 **그중 6건을 도로 잃는다**(BM25 만 맞힌 `GS-204` 1건을
   되찾아 순감 5건). k 를 10~100 으로 바꿔도 89건 그대로라 k 문제가 아니다.
2. **리랭킹은 MRR 을 확실히 올린다.** 같은 5건을 다시 세우기만 해도(후보 5, Recall 불변을 확인) BM25 0.659→0.795,
   dense 0.885→0.919. 후보를 20 으로 넓히면 품질 차이는 0.002 인데 **지연이 3~4배**다.

## 결정

**D 를 기본 구성으로 한다.** 임베딩이 0건을 내면(인덱스에 벡터가 없을 때) BM25 로 내려간다.

- **RRF 하이브리드(B)는 채택하지 않는다.** 코드(`HybridRetriever`)는 남긴다 — 비교를 다시 돌릴 수 있어야 하고,
  지식베이스가 커지거나 고유명사·번호 질의가 늘면 결과가 달라질 수 있다.
- **리랭커 `BAAI/bge-reranker-v2-m3` 을 새로 들인다.** `decisions/010` 이 리랭커를 고르지 않았으므로
  010 을 덮는 것이 아니라 **빈칸을 채운다.** 다국어(한국어 포함) 크로스 인코더 · Apache-2.0 · 568M(≈2.2GB).
  **대조군을 재지 않았다** — 한국어 전용 리랭커와 붙여 본 적이 없다.
- 후보 수(5)·RRF k(60)는 설정으로 둔다. **k 를 골든셋에서 고르지 않았다** — 96건에서 가장 좋은 값을 박으면
  골든셋에 맞춘 것이 된다. 값은 관례 그대로다.

## 근거

- 채점은 하네스와 같은 함수(`retrieval_query` · `aggregate_recall_mrr`)다. 규칙 기반이다(절대 원칙 1).
- CPU·MPS 두 장치에서 **품질 수치가 소수점 셋째 자리까지 같다** — 장치에 따른 비결정성이 결과를 바꾸지 않았다.
- **ES 9.5 가 1024차원 `dense_vector` 에 기본으로 `bbq_hnsw`(1비트 양자화 + 재채점)를 건다**(매핑에 적지 않았는데 붙었다).
  양자화 손실을 의심해 같은 벡터로 `bbq_hnsw` · `hnsw`(float) · `flat`(전수) 세 인덱스를 따로 적재해 쟀다 — **셋 다 0.979 / 0.885 로 같다**(98조항 규모).
  지식베이스가 수천 건으로 커지면 다시 잰다
- 출처별로 갈라 봐도 방향이 같다: 팀 작성(`authored`) 84건 BM25 69 → dense 82, **AI Hub 실제 전사 12건** BM25 11 → dense 12.

## 남는 것 — 이 결정이 보장하지 않는 것

1. **골든셋은 팀이 쓴 문장이 84/96 이다.** 실제 전사는 12건뿐이라 «실제 통화에서도 dense 가 이긴다» 는 말은
   못 한다. 5주차 오류 주입 곡선(`w5-error-tolerance-curve`)이 첫 번째 반례 시험이다.
2. **지연은 로컬 값이다.** 운영은 T4 한 장을 Ollama 와 나눠 쓴다(런북 11장). 운영 p95 는 **미측정**이다.
   런북 22장대로 측정 인스턴스를 분리해 다시 잰다.
3. **운영에는 아직 안 켜졌다.** 서버 이미지에 torch·transformers·모델(KoE5 2.2GB + 리랭커 2.2GB)이 없고,
   운영 ES 인덱스에는 벡터가 없다(서버 파드에서 torch 없이 적재 — 런북 15-1). 켜려면
   ① 이미지에 모델 의존성을 넣을지 볼륨으로 붙일지 ② 벡터 적재를 어디서 돌릴지를 인프라와 정해야 한다.
   그 전까지는 `RETRIEVAL_EMBED_MODEL_DIR` 을 비워 **BM25 단독**이 그대로 돈다.
4. 남은 오답 2건(`GS-204` · `GS-205`)은 원인 미분석이다.

## 되돌리는 법

- 운영: `RETRIEVAL_EMBED_MODEL_DIR` 을 비운다 → BM25 단독. 리랭킹만 끄려면 `RETRIEVAL_RERANK_MODEL_DIR` 만 비운다.
- 하이브리드로 가려면 `ai/provider.py` `build_model_retriever` 에서 `EsDenseRetriever` 자리에
  `HybridRetriever([bm25, dense])` 를 넣는다. 비교는 `scripts/compare_retrievers.py` 로 다시 돌린다.
- 이 결정 자체를 뒤집는 근거는 **같은 스크립트의 새 측정값**이어야 한다.
