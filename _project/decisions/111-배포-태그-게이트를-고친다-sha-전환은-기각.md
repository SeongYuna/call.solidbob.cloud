# 111. 배포 태그 게이트를 고친다 — `sha-<커밋>` 전환은 기각

- 날짜: 2026-09-14
- 작성: 정성윤
- 상태: 채택
- 관련: `decisions/024`(스포크는 조용히 501) · `decisions/105`(한 컨테이너·한 도메인) · `decisions/108`(설정됨 ≠ 연결됨)

---

## 맥락

`release.yml` 의 `plan` 잡이 **「이미지에 들어가는 코드가 바뀌었는데 `kustomization.yaml` 의
`newTag` 가 그대로면 실패」** 를 건다. 파드가 `imagePullPolicy: IfNotPresent` 라, 같은 태그로
다시 구워도 노드가 캐시된 옛 이미지를 계속 쓰기 때문이다.

이 게이트가 자주 걸린다는 문제 제기에서 출발했다. 실측 — **릴리스 실패 5건 중 4건**이
이것이었다(`#55`·`#59`·`#61`·`#73`. 나머지 `#54` 는 `deploy` 잡의 OIDC 실패로 무관하다).
`#73` 은 frontend 브랜치 PR 이 `server/apps/admin_auth/` 44개 파일을 가져오면서 태그를 안 올린 것이다.

게이트 자체는 옳게 동작하고 있었다. 문제는 **언제 걸리는가**와 **조용히 사라지는 경로**였다.

## 선택지

### A. `newTag` 를 유지하고 게이트의 결함을 고친다 ← **채택**

### B. 배포 태그를 `sha-<커밋>` 으로 바꾸고 `plan` 잡과 판정 로직을 통째로 없앤다 ← **기각**

`sha-` 태그는 이미 굽고 있었다(`release.yml` 의 `tags:` 둘째 줄). 커밋마다 고유하므로
「태그가 이미 있다」가 성립하지 않고, 판정·레지스트리 조회·태그 올리기가 **대상과 함께**
사라진다. 손으로 관리하는 공유 자원(오늘 0.1.4 를 두 사람이 동시에 집었다)도 없어진다.
검토 초기에는 이쪽이 유력했다.

## 결정

**A 를 택한다.** `newTag` 를 배포 태그로 유지하고, 게이트의 결함 넷을 고친다.

## 근거

### B 를 기각한 이유 — `infra/systemd/converge.sh` 가 저장소를 직접 읽는다

부팅 시 자동 수렴 스크립트는 **main 의 tarball 을 받아 `kubectl kustomize` 로 직접 렌더하고,
그 결과로 `/opt/callguard/current.yaml` 을 덮어쓴다**(`converge.sh:35-44`). 캐시는 폴백이
아니라 **갱신 대상**이다. 즉 **인스턴스가 저장소의 `newTag` 를 스스로 읽는다.**

`sha-` 로 가면:

1. CI 가 `sha-X` 로 렌더·적용 → 클러스터는 `sha-X`
2. 인스턴스 부팅 → `converge.sh` 가 main 을 렌더 → 저장소의 `newTag` 를 읽음
3. **클러스터가 그 값으로 되돌아간다.** CI 배포가 사라진다.

**그리고 이건 드문 일이 아니다.** 런북 21-1 이 `0 2 * * * /sbin/shutdown -h now` 를 걸어두고
7-5 의 종료 동작이 「중지」라, 인스턴스는 **매일 새벽 2시에 멈추고 작업 시작 때 다시 켜진다.**
`converge.sh` 는 **업무일마다 돈다.** 증상은 「어제 배포했는데 오늘 옛 코드가 돈다」 —
이 프로젝트가 계속 싸워온 그 부류의 침묵 실패이고, 24시간 안에 모든 배포가 조용히 되돌아간다.

**우회로는 있으나 값이 비싸다.** `converge.sh` 가 GitHub Actions API 로 「release 의 마지막
성공 실행의 `head_sha`」를 받아 쓰면 피해 갈 수 있다(main HEAD 를 쓰면 안 된다 — 문서만 고친
머지는 release 가 안 돌아 그 sha 의 이미지가 없다). 그러나 `converge.sh` 는 `set -euo pipefail`
로 도는 **부팅 경로**이고 설계 원칙이 「git 안 씀 · 의존 최소 · 실패하면 캐시」다. 여기에
네트워크 호출 + JSON 파싱 + 「성공 실행이 아직 없음」 분기를 더하면 **부팅 실패 경로가 늘어난다.**
클러스터가 안 뜨는 위험을 태그 자동화와 바꾸는 것은 손해다.

> **`release.yml` 주석 ①(「버전은 저장소가 정한다」)은 취향이 아니라 하중을 받는 구조였다.**
> 검토 중 「① 의 세 이유 중 *이번 머지가 배포인가가 눈에 보인다* 는 이미 작동하지 않는다」는
> 지적이 나왔고, **사람이 읽는 표식** 층위에서는 그 말이 맞다(안 올리면 «배포 안 함»이 아니라
> «CI 실패»라 선택지가 없다). 하지만 결정을 좌우한 것은 그 층위가 아니라 `converge.sh` 를 통한
> **기계적 하중**이었다. 층위를 잘못 고르면 맞는 분석으로 틀린 결정을 한다.

### A 에서 고치는 것 넷

| | 무엇이 문제였나 | 고침 |
|---|---|---|
| ① | 레지스트리 조회 실패를 **전부 「태그 없음」으로 접었다**(fail-open). 레이트 리밋·5xx·비공개 저장소(2026-09-11 게이트웨이가 실제로 그랬다)면 게이트가 **조용히 통과**하고 같은 태그를 덮어 구운 뒤, 태그가 그대로라 `kubectl apply` 가 no-op 이 되어 **롤아웃조차 일어나지 않는다.** 레지스트리와 노드가 갈라진 채 남고 스모크는 통과한다 | **200=있음 / 404=없음 / 그 외=판정 불가**로 가르고 판정 불가면 죽는다. 인증 조회로 빈도도 낮춘다 |
| ② | 게이트가 **머지 후에만** 걸렸다. 태그를 안 올린 것을 머지하고 나서야 알고, 되돌리려면 PR 을 하나 더 내야 한다 | PR 시점에 도는 **`tag-check.yml`** 을 따로 둔다 |
| ③ | `fetch-depth: 2` + 조용한 폴백(`2>/dev/null \|\| git diff HEAD~1 HEAD`). 룰셋이 **rebase 머지를 허용**하므로 3커밋 PR 에서 `before` 가 얕은 클론에 없어 첫 비교가 실패하고, 폴백이 **마지막 커밋 1개만** 보고 통과한다(재현: exit 128 → 폴백 exit 0). 앞 커밋에 `server/` 변경이 몰리면 게이트가 통째로 무력화된다 | `fetch-depth: 0` + **폴백 제거** |
| ④ | job 이름 `deploy` 가 `pages.yml` 의 `deploy` 와 겹쳤다(한 커밋에 `deploy` 둘). 룰셋은 context 이름으로만 매칭한다 | **`k3s-deploy`** 로 개명 |
| ⑥ | 레지스트리 검사가 **아직 없는 태그를 두 브랜치가 동시에 집는 경우**를 못 본다 — 양쪽 다 `exists=false` 라 통과하고, 나중에 머지하는 쪽이 릴리스에서 터진다. **2026-09-14 하루에 두 번 났다**(`0.1.4` 정성윤↔장민석 · `0.1.5` 장민석이 15:12 에 `origin/server` 로 선점) | 다른 원격 브랜치의 `kustomization.yaml` 을 읽어 같은 태그를 쓰는 곳이 있으면 **경고**한다. 실패시키지 않는다 — 저쪽이 머지 안 될 수도 있고 먼저 머지하는 쪽은 잘못이 없다. 머지를 타고 따라온 값은 계보(ancestor) 검사로 걸러 오탐을 없앴다 |
| ⑤ | `git diff --name-only` 이 **비ASCII 경로를 `"…\352\264\200…"` 로 이스케이프**해서 내보낸다. 그러면 `^(server/|ai/|…)` 정규식이 안 맞아 «코드 변경 없음»으로 읽힌다 — **①과 같은 부류의 fail-open** 이다. 지금 `server/`·`ai/` 에 비ASCII 파일은 없지만(실측 0건) 그걸 막는 규칙도 없다(§4 의 한글 파일명 금지는 `jekyll/_backlogs/` 에 대한 것이다) | 두 워크플로의 diff 를 **`git -c core.quotePath=false`** 로 |

### `tag-check.yml` 을 별도 워크플로로 만든 이유

`release.yml` 의 `on:` 에 `pull_request` 를 더하는 것으로는 **안 된다.**
`image`·`gateway-image`·`k3s-deploy` 에 이벤트 가드가 없어 같이 도는데, same-repo PR 이라
DOCKERHUB 시크릿이 붙는다 → **머지되지 않은 PR 코드가 Docker Hub 에 push 된다.** 게다가 그 PR 이
머지되면 `plan` 이 「태그가 이미 있다」를 보고 **정상 PR 을 스스로 막는다.** `concurrency: group:
release` 도 공유해 PR 검사가 실제 배포 뒤에 줄을 선다.

그래서 판정만 하는 워크플로를 따로 둔다 — **이미지를 굽지 않고 AWS 를 건드리지 않는다.**
이 제약이 그 파일의 존재 이유다.

> ⚠ **필수 통과 검사로 걸 워크플로에 `paths:` 필터를 쓰지 않는다.** 경로가 안 걸린 PR 에서는
> 검사가 **생성되지 않아** PR 이 영원히 pending 이 된다. 필터 없이 모든 PR 에서 돌리고 안에서 판단한다.

### 판정을 스크립트 한 벌로 뺀 이유

`scripts/check_release_tags.py`. 같은 판정을 두 워크플로가 쓰는데 복사해 두면 조용히 어긋난다 —
이 저장소는 브랜치·job·룰셋 이름을 따로 고치다 **두 번** 어긋난 이력이 있다(`CLAUDE.md` §7).

**같은 이유로 `newTag` 파싱도 스크립트 한 곳에만 둔다.** 처음엔 `release.yml` 이 태그를 인라인
파이썬으로 따로 읽어 image 잡에 넘겼는데, 그러면 같은 정규식이 두 벌이 되어 kustomization 형식이
바뀔 때 한쪽만 고치게 된다 — 이 결정이 막으려던 바로 그 모양이다. 스크립트가 `--emit-build` 에서
`tag`·`gateway_tag` 까지 함께 내주고, 인라인 스텝은 지웠다.

### 「두 사람이 같은 태그를 집는」 경우

룰셋이 `strict_required_status_checks_policy: true` 라 두 번째 PR 은 base 갱신이 강제되고,
그때 첫 머지가 이미 그 태그를 레지스트리에 올려둔 상태라 재실행되는 PR 검사에서 걸린다.
**단, 첫 PR 의 이미지 빌드가 끝나기 전에 두 번째가 base 를 갱신하면** 그 시점엔 `exists=false` 라
통과하고, 종전대로 머지 후에 걸린다. 레이스 창이 남는다.

**그리고 양쪽이 아직 머지되지 않았으면 레지스트리는 아무것도 모른다** — 이게 오늘 두 번 난 실제 모양이다.
그래서 ⑥(다른 브랜치의 `newTag` 를 읽어 경고)을 더했다. 경고는 레이스 창도 같이 덮는다.

## 되돌리는 법

- **④만 되돌리기**: `release.yml` 의 `k3s-deploy` → `deploy`. 룰셋에 등록된 이름이 아니라 영향 없다.
- **②만 되돌리기**: `.github/workflows/tag-check.yml` 삭제 + 룰셋에서 `tag-check` 제거.
- **전부 되돌리기**: 이 커밋을 revert 하면 `release.yml` 이 예전 셸 `decide()` 로 돌아간다.
  단 ①(fail-open)과 ③(조용한 폴백)이 같이 살아난다 — 그 둘은 되살릴 이유가 없다.
- **B 를 다시 검토하려면**: 먼저 `converge.sh` 가 저장소의 태그를 읽지 않게 만들어야 한다.
  그게 선행 조건이고, 그 비용이 위에 적혀 있다.
