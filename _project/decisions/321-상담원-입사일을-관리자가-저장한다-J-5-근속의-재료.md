# 321 — 상담원 입사일을 관리자가 저장한다 — J-5 근속의 재료

**날짜**: 2026-09-22
**작성**: 장민석 (브랜치 `server`)
**상태**: 채택 — 서버 구현됨(배포 전). 관리자 화면 입력란은 조서희 님께 요청(`w6-admin-agent-hired-on-ui`)
**관련**: `decisions/204`(J-5 — 근속 3년 이상 · 입사일을 둔다) · `313`(판정 API) · `320`(시연 호출자) · `314`(관리자 행) · `406`(이름만으로 상담원을 만든다)
**티켓**: `w6-agent-hired-on-api`

---

## 맥락

J-5 판정은 `agent.hired_on`(입사일)으로 근속을 센다 — 없으면 0년(`postgres_agent_routing_adapter.py`). `204` 가 「연수가 아니라 입사일을 둔다」고 정했다.
그런데 **입사일을 넣는 코드가 저장소 어디에도 없었다.**

- 상담원 행은 관리자가 토큰을 발급할 때 이름만으로 만들어진다(`406`, `resolve_or_create` — `agent_id`·`display_name`·`role` 만)
- 관리자 행(`314`)도 마찬가지 · 관리자 화면에 입사일 입력란이 없다

그래서 **운영의 모든 상담원이 근속 0년이고, J-5 는 베테랑을 한 명도 고를 수 없었다.** `320` 으로 시연 호출을 붙인 뒤
코드를 대조하다 드러났다 — 페르소나 대본 SYN-007(기대값 `routing: veteran`)은 이대로면 늘 「일반 배정으로 떨어짐」이 된다.

## 선택지

| | 판단 |
|---|---|
| **관리자 API 로 입사일을 넣는다** | 운영에서 사람이 넣을 수 있다 · 새 클러스터에서도 같은 길 · 화면은 조서희 님 몫이 따로 남는다 |
| 운영 DB 에 SQL 로 직접 넣는다 | 빠르다. 사람이 기억해야 하고 기록이 안 남는다 · 새 클러스터마다 다시 |
| 토큰 발급 때 입사일도 받는다 | 발급과 등록이 더 엉킨다 — `w7-agent-registration`(정식 등록 경로)에서 다룰 일이다 |

## 결정

**관리자 API — 사용자 선택(2026-09-22).**

- `PUT /admin/agents/{agent_id}/hired-on` `{hired_on: "YYYY-MM-DD" | null}` — 관리자 로그인. `agent_auth` 스포크(상담원 목록·등록과 같은 곳)
  - 상담원(`role='agent'`)만 — 관리자 행은 배정 후보가 아니라 404 · 없는 상담원 404
  - **오늘보다 뒤는 422**(근속이 음수가 된다) · `null` 이면 지운다(0년으로 돌아간다)
  - 판정하지 않는다 — 베테랑 여부는 블랙리스트 도메인 `route()` 몫이다. 여기는 입력 범위만 본다(근속 기준 0.5~40년 검사와 같은 자리)
- `GET /admin/agents` 목록에 `hired_on` 을 싣는다(없으면 `null`) — 화면이 지금 값을 보여 줄 수 있게. 필드 추가라 기존 파서는 영향 없다
- 스키마·마이그레이션 없음 — `agent.hired_on` 은 09-09 부터 있었다

## 근거

- `204` 가 입사일을 J-5 의 재료로 정해 놓고 넣는 길을 만들지 않았다. 재료가 없으면 판정 규칙이 맞아도 결과는 늘 같다
- 입사일은 사람(관리자)이 아는 사실이다 — 근속 **기준값**(`313`)처럼 관리자가 넣는 자리가 맞다
- ⚠ 입사일 자체의 근거는 조직 인사 기록이다. 시연에서 넣는 값은 페르소나 설정(예: A03 근속 7년)에 맞춘 **시연용 값**이고 측정값이 아니다(절대 원칙 2)

## 되돌리는 법

라우터 한 개(`agent_hired_on_router.py`)를 `main.py` 에서 빼고 목록 스키마의 `hired_on` 을 지운다. 이미 넣은 입사일은 `agent` 행에 남는다 — 지우려면 `UPDATE "agent" SET "hired_on" = NULL`.
