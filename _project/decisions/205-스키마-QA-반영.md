## 맥락

`204` 로 J 블록을 넣고 ERD 를 재생성한 뒤, 스키마를 **네 관점으로 나눠 감리**했다 —
정규화 · 역정규화/성능 · 요구사항 커버리지 · 개인정보/보안. 서로 다른 관점이
**독립적으로 같은 결함 두 개를 짚었고**, 그중 하나는 이 저장소에서 **재현까지 됐다.**

재현 기록 (2026-09-09, 로컬 PostgreSQL 17):

```sql
INSERT INTO transcript_segment(segment_id, call_id, text, …) VALUES (1,'c_001','등본 발급 문의드려요',…);
INSERT INTO transcript_segment(segment_id, call_id, text, …) VALUES (1,'c_002','수도요금이 왜 이래요',…)
  ON CONFLICT ("segment_id") DO UPDATE SET "text" = EXCLUDED."text";

 segment_id | call_id |         text
          1 | c_001   | 수도요금이 왜 이래요     ← c_001 의 발화가 사라졌다
```

**두 번째 통화가 시작되는 순간 첫 번째 통화의 자막이 덮어씌워진다.** 오류가 없다.

---

## 결정 — 다섯 가지를 고친다

### ① `transcript_segment` 의 키를 `(call_id, segment_id)` 로 바꾼다 【치명】

`segment_id` 는 **게이트웨이가 통화 안에서 매기는 순번**이다(§7.3 예시 `"seg_0031"`,
프론트 mock 도 통화마다 1부터). 전역 유일이라는 규칙은 **어디에도 적혀 있지 않은데**
PK 는 그것을 전제하고 있었다. `masking_event`·`compliance_flag`·`knowledge_gap` 의
FK 도 `(call_id, segment_id)` 로 따라간다.

리포지토리의 `ON CONFLICT ("segment_id")` 도 함께 고쳐야 한다 — **스키마만 고치면
UPSERT 가 터진다.** `server/` 는 장민석 담당이라 스키마·생성기까지만 하고 어댑터는
넘긴다(아래 「인수인계」).

### ② `blacklist_entry` 를 「고객」이 아니라 「등록 에피소드」로 잡는다 【치명】

PK 가 `customer_ref` 인데 `released_at` 이 있다 — **해제 후 재등록이 불가능하다.**
INSERT 는 PK 위반, UPDATE 는 첫 등록 이력을 지운다. 컬럼 주석이 *"행을 지우지 않는다
— 지우면 「왜 풀렸는지」가 사라진다"* 라고 적어 둔 바로 그 일이 UPDATE 로 일어난다.

서로게이트 `entry_id` + **부분 유니크 인덱스** `UNIQUE (customer_ref) WHERE released_at IS NULL`.
이 인덱스가 그대로 J-5 인입 조회가 타야 할 인덱스이기도 하다.

**해제 감사가 반쪽이었다** — 행을 남겨도 `released_by`·해제 사유 컬럼이 없어 어차피
「왜 풀렸는지」가 기록되지 않았다. 둘을 더한다.

### ③ `customer_ref` 를 평문 전화번호로 두지 않는다 【높음】

**C-5 가 자막에서 지운 값(P4)을 옆 테이블에 평문 PK 로 두고 있었다.** 마스킹을 앞단에
둔 의미가 여기서 사라진다. 관리자 화면이 그 값을 전체 표시하므로 **화면 캡처 한 장이
폭언 신고된 시민의 전화번호 목록**이 된다.

배정·조회에 필요한 것은 **동등 비교뿐**이므로 —

```
customer_ref  = HMAC-SHA256(정규화된 전화번호, 서버 비밀키)   # .env, SEC-2 관례
display_hint  = 뒤 4자리                                      # 화면 표시 전용
```

`customer.customer_id` 가 「해시/난수」인 것과 **체계가 같아진다** — 지금까지 FK 를 못
걸던 이유가 함께 사라진다.

`routing_log.customer_ref` 는 **삭제한다.** 이 테이블의 목적은 `fell_back` 을 세는 것이고
거기에 고객 식별자가 필요 없다. 그대로 두면 **특정 번호의 민원 이력**이 쌓이는데,
그건 F-3(반복 문의 연결)을 폐기했던 이유를 뒷문으로 되살리는 것이다.

### ④ `distress_count` 를 저장하지 않는다 【높음 — 민감정보】

자해·극단적 선택 암시 건수는 **정신건강에 관한 정보**다. 그것이 전화번호와 **같은 행**에,
반려·해제 뒤에도, 무기한 남는다 — *"이 번호의 사람이 자해를 N회 암시했다"* 는 레코드다.

**설계 의도와 정반대다.** `204` 는 `distress` 를 *"블랙리스트 사유가 아니다"* 로 못 박고
`abuse_total` 에서 뺐는데, 정작 DB 에는 건수를 영구 저장하고 있었다. 화면 경고에 필요한
것은 **요청 시점의 불리언 하나**이고 프론트가 이미 `hasDistress()` 로 그렇게 쓴다.

**컬럼을 지운다.** 요청 화면은 C-6 플래그로 즉석 계산해 경고만 띄운다.
운영 지표(전문기관 연결 건수)가 필요하면 **고객 식별자 없는 일별 집계**로 센다.
같은 이유로 **`CallGuardFlag` 를 고객 식별자에 묶어 저장하는 테이블을 만들지 않는다** —
지금 없고, 그 상태를 지킨다.

### ⑤ 자유 입력에 마스킹 관문을 세우고 보존 기간을 둔다 【높음】

- **`reason`·`note`·`knowledge_gap.description`** 은 마스킹을 거치지 않는 자유 입력이다.
  버튼의 placeholder 가 *"관리자가 통화를 다시 듣지 않고 판단할 수 있게"* 라 상담원이
  자연스럽게 이름·번호를 적게 돼 있었다. **저장 직전에 `MaskingPort` 를 통과시킨다.**
- **`blacklist_entry.note` 가 `reason` 의 사본이었다** — 같은 개인정보가 두 벌이 된다.
  `request_id` 로 조인하면 되므로 **관리자 승인 메모**로 용도를 한정한다.
- **`context_excerpt` 를 클라이언트에게서 받지 않는다.** 서버가 `call_id` 로
  `transcript_segment`(이미 마스킹본)에서 직접 잘라 넣는다 — **원문이 들어갈 입력 자체를
  없앤다.** 지금은 프론트가 맞게 보내고 있지만, 그것을 보장하는 것이 주석뿐이었다.
- **보존 기간.** `blacklist_entry.expires_at` 을 두고 J-5 는
  `released_at IS NULL AND expires_at > now()` 만 본다. 연장은 **새 요청 + 새 근거**로만.
  반려된 요청은 결정 후 일정 기간 뒤 `context_excerpt`·`reason` 을 비운다 —
  **조치 대상이 아닌 사람이 가장 상세한 기록을 갖는 상태**를 두지 않는다.

> ⚠ **절대 원칙 8 의 범위를 분명히 한다.** *"실패를 지운 기록은 기록이 아니다"* 는
> **실험·지표의 실패를 지우지 말라**는 것이지 **시민의 전화번호를 영구 보관하라**는
> 원칙이 아니다. 두 뜻이 섞여 있었다. `closure`·`eval_*` 의 append-only 는 유지한다 —
> 그쪽이 절대 원칙 8 의 진짜 대상이다.

## 함께 잡은 것

- **`eval_result.module` 에 `call_guard` 가 섹션명 그대로 들어갔다.** `_MODULE_ID` 매핑에
  C-6 이 없어서다. 다른 행은 `B-2`·`C-5` 인데 이것만 섹션명이고, **10자라 우연히
  `VARCHAR(10)` 에 맞아** 에러가 안 났다. 매핑에 `"call_guard": "C-6"` 을 넣고,
  **매핑에 없는 섹션이 오면 실패하는 테스트**를 둔다(다음에 조용히 넘어가지 않게).
- **`call` 행을 만드는 프로덕션 코드가 없다.** 감리 중 실제로 FK 위반을 만났다 —
  전사 인입이 첫 통화에서 실패한다. 인입 어댑터가 같은 트랜잭션에서
  `INSERT INTO call … ON CONFLICT DO NOTHING` 을 먼저 쳐야 한다(장민석).
- **`transcript_segment.is_final` 은 DB 에서 항상 참이다** — 리포지토리가 interim 을
  저장 전에 버린다. 정보 없는 열이라 `CHECK` 를 걸거나 뺀다.

## 되돌리는 법

1. ①②는 `db/generate_schema_docs.py` 의 `Table.primary_key`·`unique`·`partial_unique`
   지원을 되돌리고 컬럼 정의를 옛 모양으로 두면 된다. **다만 재현된 데이터 손상이
   함께 돌아온다** — 되돌릴 이유가 생기기 어렵다.
2. ③은 `customer_ref` 에 평문을 넣으면 그대로 옛 동작이다(해시는 저장 시점 함수일 뿐
   스키마 모양이 같다). 되돌리면 위 위험도 함께 돌아온다.
3. ④는 컬럼을 다시 더하면 된다. **되돌리기 전에 민감정보 저장 근거를 먼저 쓴다.**

## 남는 위험

- **①은 스키마와 어댑터를 함께 고쳐야 한다.** 한쪽만 반영하면 UPSERT 가 깨진다 —
  이 결정 기록이 인수인계 문서를 겸한다.
- **③의 HMAC 키를 잃으면 기존 등록을 조회할 수 없다.** `.env` 관리 대상에 들어간다(SEC-2).
- **QA 는 페르소나 넷이 봤지 사람이 본 것이 아니다.** 여기 적힌 판단 중 팀이 다르게
  볼 수 있는 것은 ④(민감정보 판단)와 ⑤(보존 기간 길이)다 — [미결](/open-items/)에 올린다.
