# 406 — 상담원 토큰 발급을 이름으로만 한다 (없으면 그 자리에서 만든다)

**날짜**: 2026-09-21
**작성**: 조서희 (브랜치 `frontend`)
**관련**: `decisions/307`(상담원 전용 토큰) · `jekyll/_logs/2026-09-15-04-seohee.md`(이름으로 고르게 한 첫 조치)

## 맥락

`decisions/307`로 상담원 토큰 발급 화면(`apps/admin` `SettingsTab.tsx`)이 생겼고, 2026-09-17 사용자
지적으로 `GET /admin/agents`가 추가돼 `agent.agent_id`를 직접 타이핑하지 않고 **드롭다운에서
이름으로 고르게** 했다(`server/apps/agent_auth/adapter/inbound/api/v1/agent_directory_router.py`).

그런데 `agent` 테이블에 애초에 행이 하나도 없다 — 상담원을 만드는 화면·API가 어디에도 없다
(`db/schema.sql`의 `agent` 테이블은 있지만 INSERT 하는 코드가 없다). 그래서:

1. `GET /admin/agents`가 빈 배열을 돌려주고
2. 화면이 "목록을 불러오지 못했다 — agent.agent_id 직접 입력" 입력창으로 빠지고
3. 관리자가 그 입력창에 **상담원 이름**("최효원")을 타이핑하면
4. 서버는 그것을 `agent_id`로 해석해 `agent_token.agent_id` FK 위반 → 404
   `"상담원이 없습니다: 최효원"`.

즉 "이름으로 고르게 한다"는 2026-09-17 조치는 목록이 있을 때만 동작했고, 목록이 원천적으로
비어 있는 지금(테스트 단계) 무의미했다.

## 결정

`POST /admin/agent-tokens`의 대상 지정 값(`agent_id` 필드, 값은 그대로 자유 문자열)을
**`agent_id` 또는 `display_name` 어느 쪽으로 와도** 받는다. 서버가:

1. 그 값과 일치하는 `agent_id` 또는 `display_name`을 `agent` 테이블에서 찾고
2. 없으면 새 `agent_id`(`agent-{12자리 hex}`)로 그 이름의 상담원을 그 자리에서 만들고
3. 그 상담원에게 토큰을 발급한다

**상담원 목록 관리 화면은 만들지 않는다** — 지금 필요한 것은 "테스트할 상담원 하나에게 토큰을
쥐여주는 것"이지 상담원 인사 정보 관리가 아니다. 화면은 드롭다운(있으면)+이름 입력창
하나로 단순화했다 — `agent.agent_id` 개념을 관리자에게 노출하지 않는다.

## 근거

- 실사용자(조서희) 지적: "우리가 만들었던 건 이름을 치면 토큰이 나오는 것이었는데 안 된다.
  목록이 없어서 테스트 단계니 그냥 이름으로만 되게 해달라."
- 상담원 CRUD 화면을 새로 만드는 것은 이 시점에 과한 투자다 — 8주 스크럼에 그런 화면은
  기획서 어디에도 없고, 필요한 건 "발급 대상 상담원이 존재하게" 하는 최소 동작뿐이다.
- `agent_id`는 여전히 FK·PK로 남는다 — 이름 중복이 걱정되면(예: 동명이인) 나중에
  `agent_id`를 직접 지정하는 경로를 열면 된다(이번 변경이 막지 않는다 — `agent_id`로
  와도 그대로 찾는다).

## 바뀐 것

- `server/apps/agent_auth/app/ports/output/agent_directory_port.py` — `resolve_or_create` 추가
- `server/apps/agent_auth/adapter/outbound/postgres/agent_directory_repository.py` — 구현
- `server/apps/agent_auth/app/use_cases/issue_agent_token_interactor.py` — 발급 전 상담원을
  찾거나 만든다(`AgentDirectoryPort` 의존 추가)
- `apps/admin/src/components/admin/SettingsTab.tsx` — 입력창 라벨·안내문을 "이름"으로 고치고,
  목록이 있으면 `<datalist>`로 자동완성만 거든다(별도 `<select>`를 없앴다)

## ⚠ 남는 것

- **이름 중복을 막지 않는다** — 같은 이름을 두 번 치면 첫 번째는 새로 만들고, 두 번째부터는
  같은 상담원(같은 `agent_id`)의 토큰을 추가 발급한다(찾기가 이름으로 먼저 걸리므로). 동명이인이
  생기면 관리자가 다른 이름으로 구분해서 넣어야 한다 — 테스트 단계라 감수한다.
- **상담원 정보(팀·역할·입사일)는 여전히 채울 방법이 없다** — `role`은 항상 `'agent'`로
  고정해서 만든다. J-5 베테랑 배정(`hired_on` 필요)에는 이 경로로 만든 상담원을 쓸 수 없다.
- 상담원 관리 화면이 실제로 필요해지면(운영 전환 시점) 이 자동 생성 경로는 걷어내고
  정식 등록 API로 바꾼다.

## 되돌리는 법

1. `IssueAgentTokenInteractor`를 `tokens: AgentTokenPort`만 받게 되돌리고
   `agent_id = command.agent_id.strip()`로 바로 `tokens.save`를 부른다
2. `AgentDirectoryPort.resolve_or_create`·`PostgresAgentDirectoryRepository.resolve_or_create` 삭제
3. `use_case_providers.get_issue_agent_token_use_case`에서 `agents` 의존성 제거
4. `SettingsTab.tsx`의 `AgentTokenIssuer`를 이전 커밋으로 되돌린다(드롭다운/실패 시 ID 입력)
