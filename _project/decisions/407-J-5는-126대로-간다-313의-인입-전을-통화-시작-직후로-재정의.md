# 407. J-5 는 126 대로 간다 — 313 의 "인입 전"을 "통화 시작 직후·기록 목적"으로 재정의한다

- 날짜: 2026-09-22
- 작성: 조서희
- 상태: 채택 — **313 의 「시점」 항목을 철회하고 126 을 정본으로 확정**. 구현(콜 미디에이터 호출 배선)은 여전히 `w7-j5-routing-caller`(정성윤) 몫으로 남는다 — 이 결정은 방향만 정한다
- 관련: `decisions/313`(J-5 인입 전 배정 판정 API) · `decisions/126`(배정 판정은 미디에이터가 통화 시작 직후 부른다) · `w7-j5-routing-caller`
- 티켓: `w7-j5-routing-caller`(구현, 정성윤 — 그대로 유지)

---

## 맥락

- **313**(2026-09-15, 장민석)은 J-5를 **「인입 전 배정 판정 API」**로 열면서 **「통화 시작 때 판정해 기록만」을 대안으로 놓고 명시적으로 기각했다.** 근거 둘 — ① 부를 자리가 없다(교환기가 없다, `POST /hub/calls`는 이미 연결된 뒤 온다) ② 후보 상담사를 모른다(서버에 대기 상태 정보가 없다).
- **126**(2026-09-21, 정성윤)은 "아무도 안 부른다"는 문제를 풀려고 **콜 미디에이터가 `POST /hub/calls` 성공 직후 `POST /hub/routing-decisions`를 부르기로** 결정했다 — 시점만 보면 313이 기각한 대안과 같다. 126 본문은 313의 기각 사유를 다시 짚지 않았고, "후보 상담사 목록을 어디서 얻는가"를 "구현할 때 정할 것"으로 **미해결로 남겼다** — 313이 댔던 바로 그 이유다.
- `apps/call`을 확인한 결과 **상담원 화면엔 애초에 인입 큐가 없다.** 상담원이 대기화면(`AgentStandbyScreen`)에서 스스로 "통화받기"를 눌러 시작한다(`useCallMediatorSession.startCall`). "누구에게 넘길지 고르는" 단계도, 대기 상태를 서버에 알리는 경로도 없다. 즉 **지금 프론트 구조에는 313이 전제한 "연결 전에 배정을 정하는 순간" 자체가 존재하지 않는다.**
- 서버 API(`routing_decision_router.py`)는 313 설계 그대로 만들어져 있다 — 요청이 후보를 받고, `call_id`로 통화를 조회하고, 판정을 `routing_log`에 남기고, `call.agent_id`는 안 건드린다. 인증만 313 원안("인증 없음")이 아니라 126대로 서비스 토큰(`_INGEST_ONLY`, `main.py:438`)이 걸려 있다.
- **실제로 이 API를 부르는 쪽(콜 미디에이터)은 아직 없다**(`services/call-mediator` 전체 grep 0건, `w7-j5-routing-caller` status: todo, `w5-ingest-auth-fail-closed` 대기 중). 구현 전이라 지금 방향을 정해도 되돌릴 코드가 없다 — 가장 싼 시점이다.
- `apps/call`·`apps/admin`의 안내 문구(`BlacklistRequestButton.tsx`·`EntriesTab.tsx`)는 **"완성형 인입 전 배정"**("바뀌는 것은 누구에게 배정되는가")을 전제로 쓰여 있다. 126대로 가면(연결은 이미 끝난 뒤 판정) 이 문장은 정확하지 않다 — 지금 당장도 아무것도 안 불러 정확하지 않다.

## 결정

1. **313의 「시점」 항목을 철회하고 126을 따른다.** J-5 배정 판정은 콜 미디에이터가 `POST /hub/calls` 성공 직후 부른다. "인입 전 배정"이 아니라 **"통화 시작 직후 판정 · 기록(감사 로그) 목적"**으로 J-5의 의미를 다시 정의한다.
2. **313의 나머지는 그대로 유지한다** — 요청 모양(`{call_id, candidates[]}`, 후보는 부르는 쪽이 넘긴다), `routing_log`에 남기는 것, `call.agent_id`를 안 건드리는 것, 판정 실패가 통화를 막지 않는 것(126이 이미 명시).
3. **화면 문구는 실제 동작에 맞게 고친다** — "바뀌는 것은 누구에게 배정되는가" 류의 사전 배정 주장을 없앤다. 구현(콜 미디에이터 호출)이 아직 없으므로 지금은 "정상적으로 받는다"만 남기고 배정 관련 주장은 뺀다 — 구현되면 "이후 통화부터 배정 판정이 기록에 남는다" 식으로 다시 채운다.
4. **진짜 "인입 전" 배정(대기 상담원 중 실시간 오퍼)을 원하면 별도 스코프다.** 상담원 대기화면에 오퍼/큐 개념을 새로 만드는 것은 이번 스프린트 밖이다 — 필요해지면 새 결정으로 연다.

## 근거

- 시연에서 J-5가 보이고 `routing_log`에 숫자가 쌓이는 것이 126의 실질적 동기(`decisions/126`이 인용한 09-16 해결표 8번)이고, 지금 스프린트 안에서 진짜 인입 큐를 새로 만들 여유가 없다(`204`가 J-5를 "얇은 필터"로 제한한 것과 같은 이유).
- 313이 기각한 이유(후보 불명)는 지금도 안 풀렸다 — 그걸 근거로 313을 고수하면 J-5는 시연에서 영원히 0으로 남는다. 대신 스코프를 **"기록 목적"**으로 좁히면, 후보 목록을 미디에이터 설정값(126이 이미 제안한 방식)으로 임시로 채워도 정직하다 — "배정을 실제로 바꾼다"고 더 이상 주장하지 않기 때문이다.
- 근거 없는 주장을 화면에 남기지 않는 것(절대 원칙 2)은 126을 따르기로 한 것과 별개로 필수다 — 구현 여부와 무관하게 지금 문구는 이미 틀렸다.

## 구현할 때 정할 것 (그대로 남음, 126에서 인계)

- 후보 상담사 목록 출처 — 126이 제안한 "미디에이터 설정의 후보 목록"을 시연 범위에서 쓴다
- 발신 번호 없는 테스트 콜은 항상 "블랙리스트 아님" — 시연하려면 등록된 번호로 걸어야 한다
- 판정 결과를 상담원 화면 어디에 보일지 — 구현 시점에 조서희와 다시 맞춘다(3번 결정이 먼저 적용된 뒤)

## 되돌리는 법

이 결정을 철회하고 313을 그대로 복원하면 된다 — 그러면 콜 미디에이터는 J-5를 부르지 않고(313의 "부를 자리가 없다" 그대로 남김), 화면 문구도 고칠 필요가 없어진다. 서버 API(`routing_decision_router`) 자체는 313 설계 그대로라 이 결정과 무관하게 남는다. 콜 미디에이터 호출 배선을 만들 때(`w7-j5-routing-caller`)는 이 결정의 "통화 시작 직후" 시점을 그대로 구현하면 된다.
