# 113 — 보존 정리는 사람이 누른다. 크론잡을 만들지 않는다

**작성일**: 2026-09-15
**작성**: 정성윤
**상태**: 확정 (사용자 결정)
**갱신 대상**: `jekyll/open-items.markdown` · 관리자 화면(`apps/admin`, 조서희 — 버튼 하나)
**관련**: `decisions/312`(보존 기간 180일 · 실행은 관리자 API — 이 결정이 그 「누가 부르나」를 닫는다) ·
`403`(관리자 로그인) · `112`(관리자 화면 배포)

## 맥락

`POST /hub/blacklist-retention/purge` 는 **엔드포인트가 이미 있다.** `312` 가 실행 방식을
「관리자 API」로 정하면서 k8s CronJob 을 대안으로 적어 뒀지만, **누가 그 API 를 부르는지**는
비어 있었다. 2026-09-15 조서희 님이 프론트 점검에서 이 공백을 짚었다 —
*"관리자가 수동으로 누른다로 정해지면 버튼 하나 추가. CronJob 자동화면 프론트는 할 일 없음."*

**여기서 코드를 열어 보고 찾은 것이 결정을 갈랐다** —
`blacklist_retention_purge_router.py:20` 이 `dependencies=[Depends(require_admin)]` 이다.
**이 엔드포인트는 관리자 로그인을 요구한다.**

## 선택지

| | 방법 | 좋은 점 | 나쁜 점 |
|---|---|---|---|
| **A** | **관리자 화면에 버튼 — 사람이 누른다** | 지금 인증 구조를 하나도 안 건드린다. 버튼 하나면 끝난다. **누가 언제 눌렀는지가 사람에게 남는다** | 아무도 안 누르면 안 돈다 |
| B | k8s CronJob 이 HTTP 로 호출 | 잊지 않는다 | **들 수 있는 토큰이 없다.** access 5분 / refresh 10분이고(`403`) 장기 토큰은 설계에 없다. 서비스 계정 토큰을 새로 만들면 「관리자 = 사람」 전제가 깨진다 |
| C | CronJob 이 파드 안에서 유스케이스를 직접 호출 | 인증이 필요 없다 | 같은 로직의 진입점이 HTTP·배치 두 벌이 된다. 지금 얻을 것에 비해 크다 |

## 결정

**A — 관리자 화면에 버튼을 둔다. CronJob 을 만들지 않는다.**

- 버튼 위치·문구는 조서희 님 판단이다. 응답의 네 값(`retention_days`·`cutoff`·비운 건수 둘)을
  **그대로 보여 준다** — 「정리됨」 같은 뭉뚱그린 문구로 덮지 않는다.
- **여러 번 눌러도 안전하다**(`312` — 이미 비운 행은 다시 세지 않는다). 확인 모달을 굳이 두지 않아도 된다.
- `infra/k8s/base/` 에 CronJob 매니페스트를 추가하지 않는다.

## 근거

- **보존 정리는 하루 이틀 늦어도 아무 일도 일어나지 않는다.** 180일 지난 문장을 비우는 일이라
  자동화가 주는 값이 작다. 반면 B 는 **장기 토큰이라는 새 비밀**을 만들어야 하고, 그것은 이 저장소가
  지금까지 피해 온 것이다(`403` 이 access 5분·refresh 회전으로 설계한 이유가 탈취 노출을 줄이는 것이었다).
- **`312` 가 이미 「행을 지우지 않는다 — 문장만 표시로 바꾼다」로 설계했다.** 되돌릴 수 없는 삭제가
  아니라 마스킹에 가깝고, 사람이 누르는 것과 궁합이 맞는다.
- **C 는 지금 필요 없다.** 두 진입점을 유지하는 비용이 자동화 이득보다 크다. 정리를 자주 돌려야 할
  만큼 데이터가 쌓이면 그때 C 로 간다 — 그때는 이 결정을 다시 쓴다.

## 되돌리는 법

버튼을 남겨 둔 채 C 를 더하면 된다 — 서로 배타적이지 않다. CronJob 이 필요해지면
`infra/k8s/base/` 에 매니페스트를 추가하고 `retention.py` 의 규칙을 그대로 호출한다
(규칙은 이미 도메인에 있다, `312`). **B 로 가려면 토큰 설계부터 새로 정해야 한다** —
그 경우 `403` 을 고치는 결정이 먼저다.
