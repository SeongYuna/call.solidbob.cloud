## 결정

### 1. 도메인을 **다산콜센터 하나로** 줄인다

나머지 셋(금융보험·쇼핑·질병관리본부)의 지식베이스·골든셋·코드 분기를 **전부 지운다.**

**다산을 고른 이유** (실측 근거)

| | 다산 | 금융 | 질병 | 쇼핑 |
|---|---|---|---|---|
| **음성 데이터** | **6,614건 (12.7h)** | 없음 | 없음 | 없음 |
| 서류 문의 비율 | 2.60% (174건) | 4.11% (435건) | 0.34% | 0.00% |
| 서류가 걸린 서비스 수 | 69종 | 145종 | 34종 | 0 |
| 외국인 맥락 | **`여권` 이 서류 상위 4위** | 상위 8위 밖 | — | — |

**금융보험이 서류 지표는 더 높다.** 그런데도 다산을 고른 이유는 셋이다.

1. **음성 데이터를 가진 유일한 도메인**이다. 통번역 프로젝트에서 음성이 없으면 시작할 수 없다.
2. **외국인 맥락이 데이터에 이미 있다** — 다산 서류 문의 상위 단어에 `여권(11)` 이 있고
   금융에는 없다. 여권을 서류로 요구하는 상황이 곧 외국인 응대다.
3. **수요가 증명돼 있다** — 120이 사람 통역으로 이미 하고 있다. "필요할까"를 논증할 필요가 없고,
   주장이 *"사람 통역사는 언어 수와 운영 시간이 제한된다"* 로 바뀐다.

| 블록 | 내용 | 상태 |

> ### ⚠ C-6 범위 축소 — 제안 원문에서 둘을 뺐다 (2026-08-28 명시)
>
> 출처 제안서의 C-6 은 *"욕설, 폭언, **비정상적인 음성 톤** 실시간 감지 및 **자동 차단**/경고"* 다.
> **둘 다 이번 범위 밖이다.** 티켓(`w3-c6-call-guard`)이 「욕설·폭언 탐지」로만 적어 조용히 빠져
> 있었으므로 여기에 남긴다 — 제안한 쪽은 그대로 기대한다.
>
> | 뺀 것 | 이유 |
> |---|---|
> | **비정상적인 음성 톤** | 텍스트가 아니라 **오디오 신호(prosody) 분석**이다. 우리 파이프라인은 STT 이후 `TranscriptEvent`(텍스트)만 다루고 C-6 은 `ai/` 텍스트 스포크에 잡혀 있다. 하려면 A 블록(오디오, 정성윤)에 붙어야 하고 그건 별도 결정이다 |
> | **자동 차단** | **통화를 우리가 끊을 수 없다.** F-2 에서 차단을 뺀 것과 같은 이유다 — *"통화는 상담원이 끊으면 끝난다"*. C-6 도 **경고만** 한다 |
>
> 되살릴 근거가 생기면 결정 기록으로 되돌린다. **줄인 것을 적어두지 않으면 왜 줄었는지가 사라진다.**

**컴플라이언스는 둘 다 둔다**(사용자 결정). C-1~C-4 는 상담원이 잘못 말하는 것을,
C-6 은 고객이 폭언하는 것을 잡는다 — 방향이 반대이지 대체가 아니다.

**에스컬레이션은 보류한다**(사용자 결정). 이미지의 그림은 **AI 콜봇이 먼저 응대**하는 구조인데
우리에게 콜봇이 없다. 만들면 스트리밍 STT·대화 관리·응답 생성·인계 판단이 함께 들어와
6주에 다른 기능과 병행할 수 없다.

**TTS 는 고객 쪽에 쓴다**(사용자 결정). 상담원 화면은 텍스트, 고객에게는 모국어 음성 —
양방향 통번역이 완성된다. ⚠ 지연이 누적되고 **오역 리스크가 고객에게 직접 간다.**

### 3. F-2 를 필요서류 체크리스트로 전용한다

`knowledge-base/dasan/policy/POLICY.md` 는 *"다산은 정보 안내형이라 F-2 가 적용되지 않는다"* 고
적고 있다. 그런데 **필요서류 안내는 구조가 F-2 와 같다** — 필수 항목을 규칙으로 정의하고
빠진 것을 `missing` 으로 돌려준다. 서류 하나를 빠뜨리면 고객이 헛걸음하므로 **재현율 우선**도 같다.

`server/apps/closure_gate/` 가 이미 구현돼 있으므로 **판정 대상만 바꾼다.**

### ⚠ 골든셋 11건은 평가가 성립하지 않는 크기다

56건 중 다산은 11건뿐이다. **이 상태로는 어떤 지표도 의미 있게 잴 수 없다** —
B-0 에서 이미 겪었듯 n=14 로는 목표 0.95 를 판정조차 못 했다.

**3주차 골든셋 150건 확장을 다산 단일 도메인으로 다시 잡는다.** 그때까지의 모든 수치는
**표본 부족을 명시**해서 기록한다. 이건 이 전환의 가장 큰 비용이고, 숨기지 않는다.

### B-0 분류기는 버리지 않고 **언어 판별로 돌린다** *(2026-08-28 보류 — 부록 A ⓑ 결정)*

도메인이 하나면 도메인 라우팅은 필요 없다. 그런데 **어느 언어로 말하는지 판별하는 문제**가
새로 생겼고 **구조가 같다**(입력 → 다중 클래스 분류 → 경로 선택).
`ai/apps/training/` 과 `retrieval` 의 라우터 구조를 그대로 쓰되 라벨만 바꾼다.

⚠ 다만 **학습 데이터가 또 없다** — AI Hub 민원 데이터는 전부 한국어 화자다.
B-0 에서 겪은 것과 같은 문제이므로 **데이터부터 확인하고 시작한다.**

**2026-08-28 보류.** 1차 범위가 ⓑ(어눌한 한국어)로 정해지면서 **입력 언어가 한국어 하나**가
됐다 — 판별할 언어가 없다. Chirp 3 에 자동 언어 감지가 내장돼 있으므로, ⓐ로 확장할 때도
직접 만들 이유가 먼저 있어야 한다.

## 남은 위험 — 착수 전에 확인할 것

1. ~~**외국인 화자 데이터가 0건이다.**~~ → **2026-08-28 해소. 아래 부록 A 참고.**
   AI Hub 에 외국인 화자 한국어 음성이 **있다**(505: 4,302시간 · 71479: 1,500시간).
   보유분에 없었을 뿐 확보 경로가 없던 것이 아니다 — **찾아보지 않고 0건이라고 적었다.**
2. **대화 맥락을 포트로 넘길 방법이 없다.** `RetrievalPort.retrieve(utterance, top_k)` 는
   발화 하나만 받는다. 실제 데이터가 `"그럼 등본을 띄어보면 알 수 있나요?"` 처럼
   앞 대화를 받는 형태라 **계약 변경이 필요하다.**
3. **번역 품질을 어떻게 채점하나.** 절대 원칙 1이 "LLM 을 채점자로 쓰지 않는다"인데
   번역 평가는 보통 LLM·BLEU·COMET 을 쓴다. **원칙을 조정할지 정해야 한다.**
   ⚠ 범위를 ⓑ로 좁히면서(부록 A) **1차 지표는 번역 품질이 아니라 STT 정확도(WER/CER)가 됐다.**
   WER 은 규칙 기반이라 절대 원칙 1과 충돌하지 않는다. 번역 채점은 ⓐ 확장 시점으로 미뤄진다.
4. **지연 예산.** 내부 처리 p95 ≤1,000ms 에 번역·TTS 왕복이 더해진다. 다시 짜야 한다.

## 부록 B — ID 정정: 동시 통번역은 `A-3` 이 아니라 `A-5` 다 (2026-08-28)

**이 문서 초안이 통번역에 `A-3` 을 붙인 것은 잘못이다.** 기획서의 `A-3` 은 이미
「브라우저 실시간 전달(WebSocket)」이고 `A-4` 는 발화 구간 검출이다.
한 ID 가 두 뜻을 가지면 추적성 규칙(`rfp-harness §1.3` — 코드 상단 `# Requirement: <ID>`)이
깨진다. **새 번호 `A-5` 를 준다.**

기존 A-3·A-4 를 밀지 않은 이유: 둘은 공개 사본 `docs/plan-rev4.1.md` 와 사이트 2절에 이미
실려 있어 재번호가 더 많은 곳을 건드린다. **코드에 `# Requirement: A-3` 이 하나도 없을 때
잡아서 비용이 거의 들지 않았다.**

> `부록 A-3` 등 부록 A 의 절 번호는 **다른 이름공간**이다. 항상 `부록` 을 붙여 쓴다.

## 부록 A — 외국인 화자 데이터 확인 (2026-08-28 추가)

사용자 지시로 확보 가능성을 실제로 조사했다. **위 「위험 1」의 "0건"은 틀렸다** —
보유분에 없다는 사실을 확보 불가로 넘겨짚었다.

### 확보 가능한 것

| 데이터셋 | 규모 | 쓸모 |
|---|---|---|
| AI Hub `dataSetSn=505` 외국인 한국어 발화 음성 (2021) | **4,302시간** | 베트남·영어·일본·중국·태국어 모어 화자. 대본읽기+질문답변, wav + JSON 전사 |
| AI Hub `dataSetSn=71479` 교육용 아시아어 사용자 한국어 음성 (2022) | **1,500시간** | **숙련도 4등급 라벨**(Beginner/Intermediate/Advance/Fluent) + 발음오류 태깅 |
| AI Hub `dataSetSn=71469` 교육용 영어 모국어 사용자 한국어 음성 | — | 같은 계열 |

셋 다 **내국인만 신청 가능** — 우리는 해당된다(AI Hub 5종 기수령).

**71479 의 숙련도 등급이 핵심이다.** 등급별로 나누지 않으면 WER 하나로 뭉개져
"외국인 한국어 인식률 0.7" 같은 해석 불가능한 숫자가 된다.

### 한계 — 수치에 반드시 함께 적는다

- **전화 음성이 아니다.** 위 데이터는 44.1kHz 스튜디오/온라인. 우리 실제 통화는 **8kHz 협대역**이다
  (실측: `seoul-minwon-audio` 8000Hz/2ch, `aihub-lowquality-phone` 8000Hz/1ch).
  **8kHz 로 다운샘플링해서 재야 실제와 맞는다.**
- **민원 대화가 아니다.** 낭독·질문답변이라 어휘가 다르다.
- **따라서 이 데이터로 낸 수치는 상한이다** — 실제 통화에서는 더 나쁘다. 이 문장 없이 숫자만
  옮기면 절대 원칙 10 위반이다.

### API 를 쓰면 데이터가 필요 없는가 — 아니다 (사용자 질문)

| 용도 | 필요 여부 |
|---|---|
| 모델 학습·파인튜닝 | **불필요.** Chirp 3 이 85개 이상 언어(베트남어·한국어) · 스트리밍 · 자동 언어감지 · 화자분리 지원 |
| **성능 측정** | **필요.** 정답 전사가 붙은 외국인 화자 음성이 없으면 A-5 가 되는지 안 되는지 말할 수 없다 |

**API 는 "만들 데이터"를 없애지 정 "잴 데이터"를 없애지 않는다.** 다만 규모가 크게 줄어든다 —
4,302시간이 아니라 **정답 전사 붙은 발화 수십~수백 건**이면 WER/CER 이 나온다.
리스크가 "출처 없음"에서 "샘플링 작업"으로 내려갔다.

### 범위 결정 — ⓑ 어눌한 한국어 우선 (사용자 결정)

이 문서 안에 **서로 다른 두 시나리오가 섞여 있었다.** 58줄은 "고객 외국어 → 한글"(ⓐ),
25·120줄은 "한국어가 어눌한 채로"(ⓑ)다. **둘은 다른 기능이고 필요한 데이터가 다르다.**

| | ⓐ 고객이 모국어로 말함 | **ⓑ 고객이 어눌한 한국어로 말함** |
|---|---|---|
| 기술 | STT(vi) → 번역(vi→ko) | STT(ko) 억양 내성 |
| 상용 API | 대체로 됨 | **가장 못하는 지점** |
