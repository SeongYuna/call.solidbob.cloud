# 131. 배포 태그가 다른 브랜치와 겹치면 경고가 아니라 오류다

- 날짜: 2026-09-22
- 작성: 정성윤
- 상태: 채택
- 관련: `decisions/111`(릴리스 태그 게이트) · `114`(필수 검사 다섯) · `022` ④(결정 기록 번호 — 같은 병)
- 티켓: `w6-release-tag-reservation`(이 결정으로 닫음)
- 영향: `scripts/check_release_tags.py`(경고 → 오류) · 런북 19장

---

## 맥락

`newTag` 는 브랜치 사이의 공유 자원인데 선점 장치가 없다. 09-22 하루에 server 태그가 세 번 겹쳤다 —
`0.1.28`(#114·#117) · `0.1.29`(`server` 브랜치 선점) · `0.1.31`(#119). `tag-check` 의 ⑥ 「다른 브랜치가 선점」은
**경고**라 PR 은 통과하고, 나중에 머지하는 쪽이 레지스트리 검사에서 막혀 되돌아온다. 사고는 아니지만 PR 마다 한 번씩 반복된다.

## 선택지

| | 안 | 판단 |
|---|---|---|
| ① | 브랜치별 번호대(패치 자리 대신 빌드 번호) | 태그가 버전이 아니게 된다. `converge.sh` 가 저장소 `newTag` 를 그대로 읽어 매일 적용하므로 번호 크기 순서가 의미를 잃으면 「어느 게 최신인가」를 사람이 못 읽는다 |
| ② | 머지 시 `release.yml` 이 채번, `newTag` 는 «올려야 함» 표시만 | `kustomization.yaml` 이 정본이라는 전제(`111`, `converge.sh`)가 깨진다. 워크플로가 main 에 커밋을 하나 더 만들어야 하고 룰셋이 그것을 막는다 |
| ③ | 지금대로 두고 ⑥ 경고를 **오류**로 격상 | ✅ 채택 — 코드 몇 줄. 「열린 브랜치 어디에도 없는 새 번호」가 규칙이 된다 |

## 결정

**`check_release_tags.py` 의 ⑥ 을 오류로 올린다.** PR 의 `newTag` 가 **다른 원격 브랜치가 새로 집은 값과 같으면 `tag-check` 가 실패한다.**
물려받은 값(merge-base 와 같은 값)은 지금처럼 걸리지 않는다.

- 규칙은 한 줄이다 — **새 태그는 레지스트리에도, 열린 브랜치 어디에도 없는 번호여야 한다.** 겹치면 큰 쪽보다 하나 더 올린다.
- 「먼저 손댄 쪽이 산다」(§4)는 그대로다 — 늦게 검사받는 쪽이 올린다. 먼저 머지된 쪽은 레지스트리 검사가 이미 지킨다.
- 오늘 09-22 처럼 같은 날 세 PR 이 열려 있으면 **셋 다 서로 다른 번호**를 쓰게 된다. 번호가 듬성해지는 것은 감수한다(태그는 순서만 뜻한다).

## 근거

- 경고는 아무도 읽지 않았다 — 09-22 세 번 모두 경고가 떴고 세 번 모두 머지 단계에서 되돌아왔다. 검사가 잡는 것을 사람이 읽기를 기대하는 대신 검사가 막는다.
- ①·② 는 `111` 이 세운 「저장소의 `newTag` 가 정본」을 흔든다. `sha-<커밋>` 전환을 기각한 이유와 같다.

## 되돌리는 법

`warn_tag_taken_elsewhere` 의 반환값을 `failed` 에 넣지 않고 다시 `::warning::` 으로 낸다. 이 파일의 상태 줄을 「철회」로 고친다.
