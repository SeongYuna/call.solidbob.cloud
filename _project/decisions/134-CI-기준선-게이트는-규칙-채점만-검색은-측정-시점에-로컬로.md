# 134. CI 기준선 게이트는 규칙 채점만 막는다 — 검색 기준선은 측정 시점에 ES 가 있는 곳에서 본다

- 날짜: 2026-09-22
- 작성: 정성윤
- 상태: 채택
- 관련: 절대 원칙 4·5 · `decisions/124`(운영 검색은 KoE5 dense) · `131`(태그 겹침 오류) · `w1-eval-ci`(1단계)
- 티켓: `w2-baseline-gate`(이 결정으로 닫음) → `w6-core-baseline-check` 의 선행 조건이 풀린다

---

## 맥락

절대 원칙 5 는 「기준선 미달은 CI 실패」다. 기준선 검사 스크립트 `scripts/check_baseline.py` 는 main 에 들어왔지만 CI 에 붙지 않아,
품질이 기준선 아래로 떨어져도 PR 이 초록으로 통과했다. 막힌 이유는 **검색 점수를 재려면 검색 엔진(ES + nori) 과 지식베이스 색인이 필요한데
CI 러너에 둘 다 없다**는 것 하나다. 개인정보 마스킹(C-5)·필요서류 판정(F-2) 채점은 규칙만 쓰므로 ES 가 필요 없다 —
09-22 에 ES·DB 없이 `run_eval.py` 가 0.25 초에 돌아 두 절대 규칙을 채점하는 것을 확인했다.

## 선택지

| | 안 | 판단 |
|---|---|---|
| A | CI 러너에 ES(+nori) 를 띄우고 PR 마다 색인해 검색까지 잰다 | 무겁다(이미지 + 색인 수 분). 운영 구성은 KoE5 dense 인데 CI 에 2.2 GB 모델을 올릴 수 없어 **BM25 만** 잰다 — 운영과 다른 값을 게이트로 쓰게 된다 |
| B | CI 에 붙이지 않고 측정할 때 사람이 돌린다 | 비용 0. 그러나 원칙 5 를 지키지 못하고 티켓 완료 조건(미달 시 CI 실패)을 못 채운다 |
| **C** | **CI 는 규칙 채점(C-5·F-2)만 PR 마다 막는다. 검색은 「측정 불가」 경고. 검색 기준선은 측정 시점에 ES 가 있는 곳에서 같은 스크립트로 본다** | ✅ 채택 |

## 결정

**C.** `.github/workflows/test.yml` `server` job 에 한 단계:
`run_eval.py --no-ner --report-json` → `check_baseline.py`. 필수 검사 이름(`server`)은 그대로라 룰셋은 건드리지 않는다.

- **절대 규칙은 1건 단위로 실패한다** — C-5 누락 1건, F-2 판정 오답 1건이면 `server` 가 빨간불이다.
- **검색은 경고다 — 통과로 세지 않는다.** 사유는 「이 실행에 검색 엔진이 없다(모듈은 있다)」로 찍는다. 전에는 같은 상황이 「모듈 미구현」으로 찍혀 검색이 없는 것처럼 읽혔다 — `RETRIEVAL_NO_ENGINE` 으로 바로잡았다.
- **검색 기준선을 사람이 보는 시점** — ① 판정(09-30, `w6-core-baseline-check`) ② 동결 커밋 최종 측정(`w8-final-eval-run`) ③ 그 사이 **검색을 바꾸는 PR**(지식베이스 조항·분석기·검색 코드)을 머지할 때. 명령:

  ```bash
  ELASTICSEARCH_URL=http://127.0.0.1:9200 python scripts/run_eval.py --runs 3 --no-ner --retriever bm25 --report-json r.json
  python scripts/check_baseline.py r.json
  ```

- 하네스가 멈추면(의존성 누락 등) 리포트 파일이 없어 그 단계가 실패한다 — 조용한 초록이 없다(09-22 깨끗한 가상환경에서 numpy 없이 돌려 실제로 실패하는 것을 봤다).

## 09-22 첫 실행 (이 결정의 근거 값)

- **CI 와 같은 조건**(서버 job 패키지 + numpy, ES·DB 없음): C-5 `absolute_rule_passed=True`(뚫린 건 0) · F-2 `True`(뚫린 건 0) · 검색 「측정 불가 — 검색 엔진 없음」 → 통과 2 · 측정 불가 1 · exit 0
- **검색 포함**(이 머신에 ES 9.5.1 + nori 를 직접 띄워 지식베이스 101청크 색인, 커밋 `52cb4e6` + 작업 트리, 골든셋 `v1-150.json`, 3회 최저):
  Recall@5 **0.853** · MRR **0.686**(n 102) — 기준선 0.812 / 0.635 이상 → 통과 4 · 측정 불가 0. 류준 run_id 9 와 같은 값이 재현됐다.
  ⚠ 기록 DB 없이 돌렸다(`run_id` 없음) — 판정용 공식 값은 류준 님 run_id 8·9 다. 이것은 게이트 확인이다.

## 근거

- 가장 위험한 회귀는 개인정보 누락이다 — 09-22 QA 에서도 규칙을 넓히다 이름 끝 글자가 새는 일이 있었다. 그것을 PR 마다 자동으로 막는 것이 게이트의 핵심 몫이다.
- 운영 검색 구성(KoE5 dense)은 어차피 CI 에서 못 잰다. A 는 운영과 다른 값(BM25)으로 막게 되어 게이트의 뜻이 흐려진다.

## 되돌리는 법

`test.yml` 의 「기준선 게이트」 step 을 지운다. ES 를 CI 에 붙이기로 하면(A) 그 step 앞에 ES 서비스 컨테이너와 `index_knowledge_base.py --to-es` 단계를 넣고, 이 파일 상태를 「대체」로 고친다.
