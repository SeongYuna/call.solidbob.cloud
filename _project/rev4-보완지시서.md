# 1. 트리거 허용 창 800ms — 3주차 구현과 충돌한다

## 1.1 문제

기획서의 두 서술이 서로 충돌한다.

| 위치 | 내용 |
|---|---|
| 4.1절 | **"발화 종료 후 0 ~ 800ms 이내 발동을 '적절'로 판정한다"** |
| 6.1절 | 적절 발동률 목표 **≥ 0.85** |
| 8절 3주차 | **"트리거 판정 v1 (침묵 기반)"** |

침묵 기반 트리거는 정의상 **N초의 무음을 기다린 뒤** 발동한다. 발화가 끝난 시점부터 발동까지 최소 N초가 이미 소비된다.

```
발화 종료 (t_gold)
   │
   ├─ 침묵 대기 N ms          ← 침묵 기반 트리거의 고유 지연
   │
   ├─ 트리거 판정 10ms        ← 4.3절 내부 처리 예산
   │
   └─ 발동 (t_fire)

t_fire − t_gold ≈ N + 10ms
```

일반적인 침묵 임계값은 700~1,000ms다. 여기에 판정 지연이 더해지면 **거의 모든 발동이 800ms를 초과**하여 "지연 발동"으로 집계된다.

**결과**: 3주차 v1으로는 적절 발동률 0.85가 구조적으로 달성 불가능하다. 지표가 구현을 평가하는 것이 아니라, 구현 방식을 사전에 배제하는 상태가 된다.

## 1.2 제약 조건

허용 창 상한은 다음 부등식을 만족해야 한다.

```
허용 창 상한  >  침묵 임계값(N)  +  트리거 판정 지연(10ms)
```

침묵 임계값을 700ms로 잡으면 상한은 최소 710ms를 넘겨야 하고, 실용적으로는 여유를 둬야 한다. 1,000ms로 잡으면 상한은 1,000ms 이상이어야 한다.

## 1.3 반영안

### 안 A — 상한을 늘린다 (권장)

```
발화 종료 후 0 ~ 1,500ms 이내 발동을 "적절"로 판정한다.
  1,500ms 초과 → 지연 발동
  발동 없음     → 미발동
```

근거: 침묵 대기(≤1,000ms) + 판정·큐잉 여유(500ms). 침묵 기반·종결어미 기반·하이브리드 모두 이 창 안에서 경쟁할 수 있다.

### 안 B — 침묵 임계값을 먼저 정하고 창을 역산한다

1주차에 침묵 임계값 N을 실측으로 정하고(AI Hub 음성의 발화 간 간격 분포 확인), `허용 창 = N + 500ms`로 고정한다. 더 정확하지만 1주차 작업이 하나 늘어난다.

### 어느 안이든 함께 넣을 것

> **트리거 지연시간 분포(p50/p95)를 별도로 기록한다.**
> 허용 창은 합격/불합격 판정선일 뿐이고, 개선 과정을 보여주는 것은 분포다.
> "v1 침묵 기반은 p50 920ms였고, 종결어미 하이브리드로 p50 610ms까지 줄였습니다" — 이 문장이 지표 하나보다 강하다.

## 1.4 수정 위치

| 위치 | 수정 |
|---|---|
| 4.1절 "적절한 시점의 정의" | 0~800ms → **0~1,500ms** (또는 안 B 적용) |
| 6.1절 트리거 행 | 허용 창 값 동기화 + **"트리거 지연시간 분포(p50/p95) 기록"** 행 추가 |
| 8절 1주차 | "골든셋 스펙 확정"에 **"침묵 임계값 N 결정 및 허용 창 역산"** 포함 |

# 2. GPU 미확보 시 생성 경로에 폴백이 없다

## 2.1 문제

기획서는 생성 모델을 다음과 같이 확정했다.

> 3.1절: **"별도 상용 API를 도입하지 않는다. HuggingFace Transformers로 소형 한국어 오픈 모델을 로드해 카드 요약을 생성한다. GPU 가용 여부는 1주차에 확인한다."**
> 5.6절: **V2 — GPU 가용 여부** (미확인 시 영향: 생성 모델 크기 및 레이턴시 예산)

**V2가 "GPU 없음"으로 나왔을 때의 경로가 문서에 없다.**

- 상용 API는 이미 배제되어 있다
- CPU 추론으로 4.3절의 **첫 토큰 500ms**는 소형 모델이라도 달성이 불확실하다
- 6주차에 가서야 이 사실이 드러나면 코어 마감선에서 대응할 시간이 없다

## 2.2 반영안 — 폴백 모드를 명시한다

3.1절 생성 모델 항목 아래에 다음을 추가한다.

> **생성 단계 폴백 (V2 결과에 따라 발동)**
>
> GPU를 확보하지 못하거나 첫 토큰 500ms를 맞추지 못하는 경우, **생성 없이 검색 결과 스니펫을 그대로 카드에 표시하는 모드**를 기본값으로 전환한다.
>
> | 모드 | 카드 내용 | 레이턴시 |
> |---|---|---|
> | 생성 모드 | 근거를 2~3문장으로 요약 | 검색 + 리랭킹 + 생성 |
> | **폴백 모드** | **검색된 원문 스니펫 + 출처** | 검색 + 리랭킹 (생성 단계 제거) |
>
> 폴백 모드에서도 B-5(출처 표시)와 B-6("관련 문서 없음")은 그대로 동작한다. 상담원이 얻는 핵심 가치인 **"찾아주는 것"**은 유지된다.

## 2.3 이것이 리스크 대응이자 실험 조건이다

폴백을 미리 만들어두면 6주차에 다음 비교가 가능해진다.

```
카드 유용성 비교
  A) 검색 스니펫만 표시
  B) 생성 요약 카드 표시

→ 생성 단계가 실제로 얼마나 기여하는지 수치로 말할 수 있다
→ 토큰 비용 대비 효용을 논할 근거가 생긴다
```

대부분의 프로젝트는 "LLM을 썼다"에서 멈춘다. **"LLM을 뺐을 때와 비교했다"**는 한 단계 위의 서술이다. 10절 차별화 포인트에 한 항목으로 넣을 만하다.

## 2.4 수정 위치

| 위치 | 수정 |
|---|---|
| 3.1절 생성 모델 주석 | 폴백 모드 표 추가 |
| 5.6절 V2 행 | "미확인 시 영향"에 **"폴백 모드 전환 판단 불가"** 추가 |

| 8절 6주차 | (여유 시) **"생성 모드 vs 폴백 모드 카드 유용성 비교"** 추가 |
| 10절 | (선택) 차별화 항목으로 추가 |

# 3. F-2의 순환 검증 문제가 누락되어 있다

## 3.1 문제

기획서의 세 서술을 나란히 놓으면 문제가 드러난다.

| 위치 | 내용 |
|---|---|
| 5.1절 | **"응대 매뉴얼과 내부 처리 규정은 팀이 직접 작성한다"** |
| 5.3절 | 골든셋에 **"(F-2 케이스) 처리 유형 + 근거 필드 충족 상태 + 기대 판정"** 포함 |
| 6.1절 | **F-2 종결 요건 판정 정확도 100% — 절대 규칙** |

즉 **팀이 만든 규정을, 팀이 만든 게이트가, 팀이 만든 골든셋으로 검증한다.** 100%가 나오는 것은 설계상 당연하며, 이 수치는 "게이트가 잘 작동한다"가 아니라 **"규칙 엔진에 버그가 없다"** 정도만 의미한다.

**같은 문서가 다른 기능에 대해서는 이 문제를 정확히 지적하고 있다.**

| 기능 | 순환 검증 지적 | 위치 |
|---|---|---|
| C-5 | 있음 — "실제 통화의 개인정보 발화 패턴 확보 불가" | 5.5절 |
| F-1 / G-1 | 있음 — "측정 불가" | 5.5절 |
| H-1 | 있음 — "감정 라벨과 폭언 라벨은 다르다" | 5.5절 |
| **F-2** | **없음** | — |

5.5절 한계 표에도, 11절 리스크 표에도 F-2 관련 항목이 없다. **자기 기준을 일관되게 적용하지 않은 유일한 지점이다.**

## 3.2 왜 이것이 중요한가

- 발표·면접에서 **"이 100%는 무슨 의미인가요"**라는 질문이 나오면 답이 있어야 한다
- 문서의 다른 부분이 한계를 정직하게 적고 있어서, 이 한 곳의 누락이 더 눈에 띈다
- 10.8("검증 불가를 명시한다")의 설득력이 이 누락으로 약해진다

## 3.3 반영안

### ① 5.5절 한계 표에 행 추가

| 항목 | 한계 |
|---|---|
| **F-2 판정 정확도** | **규정·골든셋·게이트를 모두 팀이 작성했다. 100%는 "규칙 엔진이 명세대로 동작한다"는 의미이며, "실무 규정을 올바르게 해석한다"는 뜻이 아니다.** |

### ② 완화 조치를 5.1절에 명시

> **규정 문서 작성 시 지킬 것**
>
> 1. **실제 도메인(금융보험·다산콜센터·쇼핑·질병관리본부, [9번 항목](#9-데모-도메인을-실제-데이터-4종금융보험다산콜센터쇼핑질병관리본부으로-한정) 참조)의 QA 라벨에 나타난 카테고리·의도 체계와 표현을 따른다.** 조 번호 체계, 문장 형식, 용어를 실측 데이터의 카테고리·의도 명칭에 맞춘다
> 2. **규정 작성자와 게이트 구현자를 분리한다.** 규정을 쓴 사람이 요건 스키마를 짜면 해석 오류가 드러나지 않는다
> 3. **골든셋의 F-2 케이스는 규정 작성자가 아닌 사람이 만든다.** 같은 사람이 만들면 규정의 빈틈이 그대로 통과된다
> 4. 위 세 가지를 지켰다는 사실을 문서에 적는다

3인 팀에서 1~3번은 실행 가능하다. 규정 작성·스키마 구현·골든셋 라벨링을 세 사람에게 하나씩 배분하면 된다.

### ③ 11절 리스크 표에 행 추가

| 리스크 | 영향 | 대응 |
|---|---|---|
| **F-2 규정을 팀이 작성** | 판정 정확도 100%가 자기충족적 수치가 됨 | 실제 약관 체계에 맞춰 작성. **규정 작성자 / 스키마 구현자 / 골든셋 작성자를 분리.** 5.5절에 한계 명시 |

### ④ 10.8절 문장 보강

기존 문장 뒤에 한 줄 추가.

> F-2의 판정 정확도 100%도 "팀이 만든 규정 안에서의 100%"임을 명시했다. 절대 규칙이라는 표현이 검증 범위까지 절대적이라는 뜻은 아니다.

# 4. C-5 배정을 정규식/NER로 분리한다 *(선택)*

## 4.1 문제

7.2절 부하 완화 조치에서 C-5를 인프라 담당에게 배정하며 근거를 다음과 같이 들었다.

> "전사 직후 처리 지점이라 STT 파이프라인 담당이 자연스럽다. **정규식 중심이라 AI 전문성 의존도가 낮다**"

앞 문장은 타당하다. 뒤 문장은 절반만 맞다.

| 패턴 | 방식 | 성격 |
|---|---|---|
| P1 주민등록번호 | 정규식 | 인프라 담당 가능 |
| P2 카드번호 | 정규식 | 가능 |
| P3 계좌번호 | 정규식 | 가능 |
| P4 휴대전화번호 | 정규식 | 가능 |
| P5 인증번호 (문맥 조건) | 정규식 + 문맥 | 경계 |
| **P6 인명** | **NER** | **HF 모델 로드·튜닝 — AI 작업** |
| **P7 상세주소** | **NER** | **동일** |

추가로 5주차 **마스킹 재현율 곡선**은 오류 주입 스크립트·평가 하네스와 맞물린 작업이다.

## 4.2 반영안

| 범위 | 담당 |
|---|---|
| P1~P5 (정규화 + 정규식) + 파이프라인 배선 | 인프라 담당 |
| **P6~P7 (NER 모델)** | **AI 담당** |
| 5주차 마스킹 재현율 곡선 | AI 담당 (오류 주입 스크립트와 함께) |

부하 완화 효과는 대부분 유지된다. 정규식 5종과 파이프라인 배선이 작업량의 다수를 차지하기 때문이다.

**또는** P6~P7을 **"여유 시"로 내리는 방법도 있다.** 이 경우 C-5 절대 규칙의 범위를 **P1~P5로 한정**하고 그 사실을 6.1절과 5.5절에 반영한다. 3인 팀에서는 이쪽이 더 현실적일 수 있다.

## 4.3 수정 위치

| 위치 | 수정 |
|---|---|
| 7.2절 완화 조치 표 | C-5 배정 행을 P1~P5 / P6~P7로 분리 |
| 6.1절 C-5 행 | P6~P7을 여유 시로 내릴 경우 **"P1~P5 패턴 마스킹 누락 0건"**으로 범위 조정 |

# 5. 아키텍처 "변경 없음" 문구 정정 *(선택)*

## 5.1 문제

3절 서두에 **"rev.3에서 변경 없음"**이라고 적혀 있으나, 실제 다이어그램에는 다음이 추가되었다.

- `C-5 마스킹 모듈` 노드
- `F-2 게이트 모듈` 노드
- MySQL 하위 테이블 5종 (`call` / `transcript` / `recommendation` / `closure` / `eval_result`)

이 추가는 **새 도구·새 저장소를 도입한 것이 아니라 기존 구성요소 내부를 명시한 것**이므로 "스택 불변" 원칙에는 어긋나지 않는다. 오히려 문서로서는 rev.3보다 정확하다.

다만 **"변경 없음"이라는 문구 자체가 사실과 다르다.** 검토자가 대조하면 바로 드러난다.

## 5.2 반영안

> **구성요소 추가 없음.** 새 DB·검색엔진·프로토콜·목록 밖 도구를 도입하지 않았다.
> 단, rev.3 다이어그램에서 생략되어 있던 **C-5 마스킹 모듈, F-2 게이트 모듈, MySQL 테이블 구성**을 명시적으로 표기했다. 이는 기존 FastAPI 코어와 MySQL 내부를 세분화한 것이며 신규 인프라가 아니다.

# 11. 관계형 DB — MySQL → PostgreSQL (2026-08-27)

## 11.1 변경

rev.4 는 투입자원 표·C-5 적용 지점·캐시 전략에서 관계형 DB 를 **MySQL** 로 적었다.
**PostgreSQL 로 바꾼다.** 근거·되돌리는 법: `_project/decisions/018-DB-PostgreSQL-전환.md`.

## 11.2 rev.4 의 어느 서술을 덮는가

| rev.4 위치 | 원래 | 바뀐 것 |
|---|---|---|
| 3.1 투입자원 표 | `MySQL \| 통화 메타·전사·추천·종결·평가 결과 \| 필수` | `PostgreSQL` |
| 2.4 C-5 적용 지점 | "② MySQL 저장 전" | "② PostgreSQL 저장 전" |
| 3.x 캐시 저장소 | "인메모리 LRU + MySQL 영속화" | "인메모리 LRU + PostgreSQL 영속화" |
| F-4 표현 정정 | "MySQL에서 완전한 불변성은…" | "PostgreSQL에서…" — 한계 서술 자체는 그대로 유효하다 |

## 11.3 바뀌지 않는 것

- **벡터 검색은 계속 Elasticsearch 가 한다.** PostgreSQL 로 옮겼다고 pgvector 를 쓰지 않는다 —
  `dense_vector` 와 중복이고, 하이브리드 검색(nori + dense_vector + RRF)은 ES 설계 그대로다.
- 테이블 구성·정규화·FK 는 그대로다. 방언만 바뀐다.
- `CALL`·`RANK` 예약어 문제는 PostgreSQL 에서도 동일하다 — 식별자 인용을 계속 한다.
