## 1. 용어부터 (이 문서를 읽는 데 필요한 최소한)

| 용어 | 뜻 |
|---|---|
| **STT** | Speech-to-Text, 음성을 텍스트로 바꾸는 것. 이 프로젝트에선 Google Cloud STT를 쓴다 |
| **RAG** | Retrieval-Augmented Generation. 검색으로 찾은 문서를 근거로 답을 만드는 방식. B 기능(서류 추천)이 이 구조인데, 지금은 검색 단계까지만 붙었고 문장을 새로 쓰는 생성 단계(B-4~6)는 조항 스니펫을 그대로 보여주는 폴백이다 |
| **NER** | Named Entity Recognition, 문장에서 이름·주소 같은 고유명사를 찾아내는 AI 모델 |
| **BM25 / nori** | BM25는 키워드 검색 점수 계산 방식(전통적 검색엔진 알고리즘). nori는 한국어 형태소 분석기(Elasticsearch 플러그인) — "중도해지수수료"를 "중도/해지/수수료"로 쪼개는 역할 |
| **RRF** | Reciprocal Rank Fusion. 서로 다른 두 검색 결과(예: 키워드 검색 + 의미 검색)의 순위를 합치는 계산법 |
| **골든셋** | 정답이 달린 평가용 문제 세트. "이 질문엔 이 문서가 정답"이라고 사람이 미리 답을 적어둔 것 |
| **Recall@5** | 상위 5개 검색 결과 안에 정답 문서가 들어 있었던 비율 (0~1, 높을수록 좋음) |
| **MRR** | 정답이 몇 번째 순위에 나왔는지의 평균 (1등이면 1.0, 낮아질수록 점수가 준다) |
| **재현율(recall)** | "있어야 할 걸 놓치지 않는 비율". C-5(개인정보 마스킹)는 재현율을 정밀도보다 우선한다 — 애매하면 무조건 가린다 |
| **허브-스포크** | 이 프로젝트의 코드 구조. `server/apps/hub`가 계약(입출력 형태)만 정의하는 "허브"이고, 실제 판정 로직은 `masking`·`retrieval` 같은 "스포크"에 있다. 허브는 스포크가 안 꽂히면 대부분 501(미구현)을 낸다 — 생성(B-4~6)과 도메인 라우팅만 예외로 폴백·None을 쓴다 |
| **헥사고날 아키텍처** | 코드를 domain(순수 판정 로직) → app(포트·유스케이스) → adapter(HTTP·DB 등 바깥세상 연결) 3겹으로 나누는 설계 방식. 안쪽 계층은 바깥 계층을 모른다 |
| **F-2** | "종결 요건 게이트" — 원래는 "상담을 끝내도 되는가"를 판정하는 기능이었는데, 다산콜센터로 도메인을 좁히며 "필요서류 빠짐없이 안내했는가" 체크리스트로 용도가 바뀌었다 |
| **P1~P7** | 개인정보 패턴 분류 번호(전화번호·주민번호 등 7종). C-5 마스킹이 이 패턴들을 가려야 한다 |

  사전·정규식 규칙으로 탐지한다. C-1~4(상담원 위반 감지)와 **방향이 반대**다. 앞의 셋은 안내 후
  종료(MANUAL-5.1~5.2), distress는 통화를 끊지 않고 전문 기관 연결(MANUAL-5.4)이라 **판정기가
  distress를 먼저 보고**, 채점기는 distress를 폭언으로 잘못 보낸 건수(`distress_misrouted`)를 따로
  센다. 「죽겠네」 같은 관용 표현은 위기 신호로 잡지 않는다.
- **채점값**: 재현율 1.0 · 정밀도 1.0 · n=15(정상 발화 6건 포함) — 류준 커밋(`96d88ac`) 원문:
  *"상한이지 성능이 아니다. 케이스와 규칙을 같은 사람이 같은 날 만들었다... 교차검수 전까지
  「목표 달성」으로 인용하지 않는다."*
- 코드: `ai/apps/call_guard/` · 허브 쪽 DTO·포트(`call_guard_dto.py`·`call_guard_port.py`)도 같은 커밋에 있다.
- **API**: 아직 HTTP로 노출 안 됨(라우터 없음). 지금 대시보드의 고객 위험 배너는 프론트 mock이
  자체 판정한 것이다.
- DB: `call_guard_flag` (09-09 신규 테이블 — id, call_id, segment_id, category, phrase, span_start, span_end, source_doc_id, detected_at)
  — ⚠ **테이블만 있고 저장하는 코드는 아직 없다**(`w4-c6-d5-persistence`, todo).
- ⚠ **프론트-백엔드 카테고리 계약이 갈려 있다**(`jekyll/open-items.markdown` #208, 09-09) — 백엔드는
  4종(`insult`·`threat`·`sexual`·`distress`)인데 프론트 `CallGuardFlag.category`는 한글 3종
  (`폭언`·`욕설`·`위협`)이라 `distress`를 매핑할 수 없다. 단순 타입 불일치가 아니라 **안전 문제로
  이어질 수 있다** — 정신적 고통(distress) 신호를 폭언과 같은 것으로 뭉개면 위기 상황에서
  전화를 끊는 식으로 잘못 처리될 수 있다.

### D. 통화 후 처리 — 요약·유형분류·공백 리포트 + D-5 통화 온도

- **상태**: 🟡 **부분 구현**
- **API**: `POST /hub/calls/{call_id}/close` (통화 종료 처리) — `server/apps/hub`. 허브 쪽 배선만

  만드는 스포크(`server/apps/postcall/`)가 **아직 없어서 지금 이 엔드포인트는 501을 돌려준다**
  (`postcall_provider.py` — "빈 요약을 만들지 않는다", 7주차 항목).
- **D-5 통화 온도**만 판정 로직이 구현됐다(`96d88ac`, `decisions/203`):
  - 무엇을 하나: 화자 **자신의 평소 톤**(통화 안에서 만든 기준선) 대비 목소리가 튀는 구간을
    찾는다. 중앙값·MAD 기반 로버스트 z 점수를 쓰고 절대 임계값은 쓰지 않는다 — "220Hz 넘으면
    흥분" 같은 규칙은 여성 화자를 통화 내내 흥분으로 만들고 저음 남성은 소리를 질러도 안 걸린다.
  - ⚠ **감정을 추정하는 기능이 아니다.** `decisions/203`은 「감정분석」이라는 말을 쓰지 않기로
    했다 — 하지 않는 일(심리 상태 판정)을 한다고 주장하는 말이라서다. 화면에도 점수를 내지
    않고 「이상치 구간이 몇 번 있었다」와 그 구간의 자막까지만 보여준다(203 원문). 이름은 「통화 온도」가
    1안이고 팀이 아직 확정하지 않았다(미결 항목).
  - 코드: `ai/apps/voice_signal/`
  - DB: `voice_outlier`(09-09 신규 테이블) — ⚠ **테이블만 있고 실제로 저장하는 코드는 아직
    없다**(`w4-c6-d5-persistence`, todo). 오디오는 보관하지 않으므로(절대 원칙 7) 저장하지
    않으면 통화가 끝나는 순간 다시 계산할 방법이 없다.
  - 실측 한계: 다산콜DB로 재 보니 발화 안 음높이 흔들림이 상담사(78.7Hz)가 민원인(63.2Hz)보다
    컸다. 류준은 이를 「가설 기각」이 아니라 **「이 데이터로는 못 잰다」**로 적었다 — 연기된 정상
    시나리오라 「격해지는 고객」이 표본에 없다. 다만 "절대 임계값을 쓰면 베테랑 상담사가 통화
    내내 걸린다"는 설계 판단은 이 결과로 뒷받침됐다.
  - 「튀었다」 기준값: `DEFAULT_THRESHOLD = 3.5` — 로버스트 이상치 탐지의 관례값이고 **우리가 재서
    고른 값이 아니다**(코드 주석, 데이터가 쌓이면 다시 정한다). 기준선은 발화가 8건 이상일 때만
    만든다(`MIN_BASELINE_UTTERANCES`).
  - 연결 상태: 이 모듈을 부르는 곳은 측정 스크립트 `scripts/measure_call_temperature.py` 하나뿐이다 —
    **서버 요청 경로에도, 평가 하네스 채점에도 아직 들어가지 않았다**(음성 골든셋이 없다. 미결
    「D-5 통화 온도를 오프라인으로 검증할 방법이 없다」).
  - 하지 않는 것(09-09 검토 대비): **통화 길이 축은 보류**다 — 가진 음성이 발화 단위 클립이라 통화
    전체 길이가 없다(203 선택지 D). **상담 품질과의 관련(가설 4)은 못 잰다** — 품질 라벨이 없다.
  - ⚠ 옛 이름이 코드에 남아 있다 — 대시보드 통화 요약 패널이 mock 모드에서 "감정분석 모델 연동 전 —

받게 설계돼 있어서 맞춘 것인데, **공식 계약 문서(§7.3)는 아직 이 변경을 반영하지 못했다.**

## 4. DB 스키마 (22개 테이블, 2026-09-09 기준)

### 핵심 흐름

```
call (통화, domain 컬럼)
 └─ transcript_segment (발화, PK가 (call_id, segment_id) 복합키로 09-09에 수정됨)
     ├─ masking_event (C-5 마스킹 결과)
     ├─ compliance_flag (C-1~4 위반, 아직 채워지지 않음)
     ├─ call_guard_flag (C-6 폭언 탐지, 09-09 신규)
     └─ voice_outlier (D-5 통화 온도, 09-09 신규)

recommendation → recommendation_card → card_feedback (B 기능)
closure (F-2 종결 판정, append-only)
eval_run → eval_result (E, 평가 하네스 — 통화 데이터와 독립)

blacklist_request → blacklist_entry (J, 09-09 신규)
routing_log (J, 라우팅 이력)
```

### 09-08 대비 바뀐 기존 테이블 6곳

| 테이블 | 변경 | 이유 |
|---|---|---|
| `transcript_segment` | PK를 `segment_id` 단독 → **`(call_id, segment_id)` 복합키**로 수정 | 다른 통화의 자막이 덮어써지던 결함 수정(`fd96adc`, 로컬에서 재현) |
| `masking_event` · `compliance_flag` | `call_id` 추가, `transcript_segment` FK를 `(call_id, segment_id)` 복합키로 변경 | 위 PK 수정에 따른 것 |
| `knowledge_gap` | `call_id_seg` 추가, `segment_id` 단일 FK 제거 | 위 PK 수정에 따른 것. ⚠ 커밋 메시지는 "복합 FK로 이었다"고 하지만 생성된 `db/schema.sql`에는 `knowledge_gap → transcript_segment` FK가 **없다**(09-11 확인) |
| `agent` | `role`(agent/admin CHECK) · `hired_on` 컬럼 추가 | J 블록(관리자 승인)에 관리자 구분이 필요해짐. ⚠ 서버에 인증이 없어 아직 컬럼만 있다 |
| `call` | `summary_confirmed_at` 컬럼 추가 | D(통화 후 요약) 확인 시각 기록용 |

### 09-09 신규 테이블 5개

| 테이블 | 무엇을 담나 | 관련 기능 |
|---|---|---|
| `call_guard_flag` | 폭언 탐지 결과(카테고리·문구·위치) | C-6 |
| `voice_outlier` | 음성 이상치(화자·robust z-score) | D-5 |
| `blacklist_request` | 진상고객 전환 요청(사유·증거·상태) | J |
| `blacklist_entry` | 블랙리스트 등록(만료일·해제 사유) | J |
| `routing_log` | 통화 라우팅 이력(블랙리스트 여부·배정 결과) | J |

DDL 정본은 `db/schema.sql`이지만 **직접 고치는 파일이 아니다** — `db/generate_schema_docs.py`의
`TABLES`를 고치면 이 파일이 자동 생성된다.
