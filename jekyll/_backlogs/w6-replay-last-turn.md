## 2026-09-22 — 코드로 본 원인과 재생기 수정 (류준, 운영 재확인 전)

**원인 — 증명된 것과 가설을 가른다.**

- **증명(코드 읽기): 재생기가 일찍 닫아서 «저장»이 빠질 수는 없다.** 콜 미디에이터 `/dev/text` 는 메시지를 받은 순서대로
  동기 처리한다(`ws_server.ts` `acceptText` → `pushText` → 채널 줄). `{"type":"end"}` 나 소켓 닫힘은 `channel.close()` →
  `drain()` 만 부르고, `drain` 의 10초 상한(`call_registry.ts`)은 기다림을 끊을 뿐 **줄에 든 전사·진행 중인 서버 호출을 취소하지
  않는다.** 재생기 프로세스가 끝나도 콜 미디에이터 → 서버 요청은 계속 간다. 그래서 티켓의 첫 가설(«마지막 확정 직후 닫는 경쟁»)은
  **DB 저장 누락의 원인으로는 틀렸다.** 닫는 시점이 영향을 주는 곳은 재생기 자신의 `/ws` 관찰(자막 수·`--close` 본문)뿐이다.
- **남은 가설 둘(미증명).** 운영에서 DB 도 `/ws` 도 4개였다 — 콜 미디에이터는 서버 `/hub/transcripts` 가 성공한 것만 방송하므로
  마지막 확정은 ① **콜 미디에이터에 닿지 않았거나**(재생기 `send()` 가 소켓이 열려 있지 않으면 **조용히 건너뛰었다** — 흔적이 없다)
  ② **콜 미디에이터 → 서버 전사 요청이 실패했다**(5초 시간 초과 또는 5xx — 콜 미디에이터 로그에 `전사 전달 실패 call=syn-prod-syn-010-20260922`
  가 남는다). ②가 정황에 더 맞다 — SYN-010 은 모델 탑재 뒤 운영이 처음 받은 통화였고 추천이 3,300ms 걸렸다. **가르는 것은 그 시각의
  콜 미디에이터 파드 로그**다(정성윤 님 — 파드가 교체됐으면 못 가른다).

**재생기 수정(원인이 어느 쪽이든 조용히 잃지 않게)** — `replay_persona_call.ts` · `persona_replay/final_echo.ts`

- 보낸 확정이 **화자별로 전부 `/ws` 로 돌아온 뒤에야** `end` 를 보낸다(마스킹본이라 글자 대신 개수로 센다). `--final-timeout`(기본 20초)
  안에 안 돌아오면 **경고 + 종료 코드 1**. `--watch` 가 없어도 뷰 토큰이 있거나 루프백이면 `/ws` 를 열어 확인한다.
- 소켓이 닫혀 확정을 못 보내면 경고 + 종료 코드 1(가설 ①이 이제 보인다). `end` 뒤 15초 안에 콜 미디에이터가 안 닫으면 경고하고 이쪽에서 닫는다.
- 가짜 콜 미디에이터로 확인(스택 없음): 정상 5/5 → `✓ 확정 자막 5건이 전부 /ws 로 돌아왔다`, 마지막 상담원 확정을 버리게 하면
  `⚠ 확정 자막 상담원 1건이 2초 안에 /ws 로 돌아오지 않았다` · 종료 코드 1.
