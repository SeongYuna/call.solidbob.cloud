**원인 — 증명된 것과 가설을 가른다.**

- **증명(코드 읽기): 재생기가 일찍 닫아서 «저장»이 빠질 수는 없다.** 콜 미디에이터 `/dev/text` 는 메시지를 받은 순서대로
  동기 처리한다(`ws_server.ts` `acceptText` → `pushText` → 채널 줄). `{"type":"end"}` 나 소켓 닫힘은 `channel.close()` →
  `drain()` 만 부르고, `drain` 의 10초 상한(`call_registry.ts`)은 기다림을 끊을 뿐 **줄에 든 전사·진행 중인 서버 호출을 취소하지
  않는다.** 재생기 프로세스가 끝나도 콜 미디에이터 → 서버 요청은 계속 간다. 그래서 티켓의 첫 가설(«마지막 확정 직후 닫는 경쟁»)은
  **DB 저장 누락의 원인으로는 틀렸다.** 닫는 시점이 영향을 주는 곳은 재생기 자신의 `/ws` 관찰(자막 수·`--close` 본문)뿐이다.
- **남은 가설 둘(미증명).** 운영에서 DB 도 `/ws` 도 4개였다 — 콜 미디에이터는 서버 `/hub/transcripts` 가 성공한 것만 방송하므로
  마지막 확정은 ① **콜 미디에이터에 닿지 않았거나**(재생기 `send()` 가 소켓이 열려 있지 않으면 **조용히 건너뛰었다** — 흔적이 없다)
  ② **콜 미디에이터 → 서버 전사 요청이 실패했다**(5초 시간 초과 또는 5xx — 콜 미디에이터 로그에 `전사 전달 실패 call=syn-prod-syn-010-20260922`
  가 남는다). ②가 정황에 더 맞다 — SYN-010 은 모델 탑재 뒤 운영이 처음 받은 통화였고 추천이 3,300ms 걸렸다. **가르는 것은 그 시각의
  콜 미디에이터 파드 로그**다(정성윤 님 — 파드가 교체됐으면 못 가른다).

## 2026-09-22 (밤) — 원인 판정: ② 콜 미디에이터 → 서버 전사 요청 실패 · 확정 재시도 (류준, 운영 로그 없이)

**판정 — ② (증명: 코드 + 운영 산출물 소거법).** ①(마지막 확정이 콜 미디에이터에 닿지 않음)은 기각된다. 실패 **종류**(시간 초과 · 5xx · 연결 끊김)는 여전히 미결이다.

- **① 기각 근거.** 운영 명령은 `2>&1 | tee syn-010-watch.txt` 였다(세션 기록) — 옛 재생기(`a866ff4`)는 화자 소켓이 1000 이 아닌 코드로
  닫히면 stderr 에 `[agent] 콜 미디에이터가 닫았다` 를 찍는데 **그 줄이 없다.** 옛 `send()` 가 확정을 건너뛰려면 소켓이 OPEN 이 아니어야 하고,
  콜 미디에이터가 1000 으로 닫는 길은 `{"type":"end"}`(확정 **뒤**에 같은 소켓으로 보낸 것) 하나뿐이다(`ws_server.ts` `acceptText`).
  조용히 끊긴 반쪽 연결이었다면 `end` 도 못 닿아 재생기가 10초 상한 + 3초를 다 기다려 **약 35초**에 끝났어야 하는데, 실제는
  **12:19:59 → 12:20:31(32초)** — 확정 + 10초 타이머 모양이다(로컬 재현도 같은 모양). 즉 콜 미디에이터가 `end` 를 받아 정상으로 닫았고,
  같은 소켓에서 그 앞에 온 확정도 받았다.
- **그러면 남는 길은 하나.** 받은 확정은 `pushText` → 채널 줄 → `forward()` 로 가고, 자막·「검색 중」·추천·필요서류 판정이 **전부
  `hub.ingestTranscript` 성공 뒤**에 있다. 운영 5번은 자막 없음 · pending 없음 · DB 없음 · 5번 뒤 필요서류 판정 행도 없음(옛 규칙이면
  `TERM-2.9` 재판정 행이 하나 더 생겼어야 한다) — 이 서명을 내는 분기는 전사 요청 실패뿐이다. DB 에도 없으므로 서버가 커밋하지 못했다
  (느리기만 했다면 서버가 늦게라도 UPSERT 했을 것) → 서버가 오류로 답했거나 요청이 서버 앱에 닿지 못했다. **어느 쪽인지는 그 시각
  콜 미디에이터 로그의 `전사 전달 실패 call=syn-prod-syn-010-20260922 segment=5 status=…` 로만 가른다(미결).**
- **확정이 저장 없이 사라지는 분기 전부**(`services/call-mediator/src/`): ⓐ 전사 요청 실패 — 시간 초과 5초(`hub_http.ts:105`)·연결 실패·
  5xx·4xx(401 토큰·409 통화 없음·422) → 자막·pending 없음(`call_registry.ts` `forward`) ⓑ 채널이 이미 닫힘(`pushText`, `end`/소켓 닫힘 뒤)
  ⓒ 메시지 형식 위반 → 1008 로 닫힘(뒤 것 전부) ⓓ 채널 열기 실패(통화 시작 실패 등) → 모아 둔 것 전부 ⓔ 빈 글자 ⓕ 연결 유지 ping 실패로
  `terminate`(1006) ⓖ auto 채널의 화자 라벨 없는 확정. 줄의 interim 갈아 끼우기는 확정을 버리지 않고, `drain` 10초 상한은 기다림만 끊는다.
  ⓑ~ⓕ 는 재생기 쪽에 1000 이 아닌 닫힘이 찍히거나 운영 서명과 맞지 않는다.
- **로컬 재현** (`:8002` 서버 · `:8082` 콜 미디에이터 · 검사 DB `callguard_e2e_l`, 끝나고 지움 · 옛 재생기 사본 · 서버 앞 작은 프록시로 5번 확정 전사만 방해):
  (a) **콜드 스타트**(서버 뜨자마자 재생) → **5/5, 재현 안 됨.** (b) 5번 확정 **1회 503** → **4/5**, `/ws` 자막·pending 5번 없음, 재생기 stderr 조용 —
  운영과 같은 서명. (b′) 5번 확정 **1회 6초 멈춤 후 서버에 안 넘김** → 콜 미디에이터 `status=연결 실패`(5초 시간 초과) · **4/5** · 같은 서명.
  수정 뒤 같은 두 주입 → **5/5**(`전사 전달 실패 … 300ms 뒤 다시 보낸다 (1/3)` 한 줄). 계속 503 이면 3회 뒤 `전사 전달 포기 … (3회 시도)` +
  새 재생기 `⚠ 확정 자막 상담원 1건이 … 돌아오지 않았다` · 종료 코드 1.

**수정 — 콜 미디에이터가 확정 전사를 일시 실패에 한 번에 버리지 않는다** (`call_registry.ts` `ingest()`·`INGEST_RETRY_DELAYS_MS`).
확정만, 연결 실패·시간 초과·5xx·429 일 때 300ms · 1,000ms 뒤 다시 보낸다(최대 3회). 4xx·interim 은 다시 보내지 않는다. 다시 보내도 되는 근거는
서버 저장이 `(call_id, segment_id)` UPSERT + 마스킹 구간 지우고 다시 넣기라는 것(`decisions/205`) — 첫 요청이 늦게 서버에서 끝났어도 행은 하나다.
재시도는 채널 줄 안에서 해서 **순서가 뒤집히지 않는다**(그동안 뒤 자막이 늦는다). 경고 로그에는 통화·발화 번호·상태·시도 횟수만(SEC-1).
단위 테스트 6건 추가 — 옛 코드에서 4건 실패, 새 코드 153/153.
