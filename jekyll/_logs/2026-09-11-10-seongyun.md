- **런북의 DB 장을 운영 실물에 맞췄다** — `docs/infra-runbook.md` 6 · 12-2 · 17 · 19장, 같은 이름이 나오는 0장 자원표 ·
  3-2 · 22장 · 문제 해결 표. 이름은 `callguard-pg` · `callguard-db` · 사용자·DB `callguard` · 네임스페이스 `callguard` ·
  시크릿 `server-env`(`decisions/108`). 머리말에 «실물과 다른 곳» 안내를 넣었다 — 13(클론)·16-2(Caddy)는 원안 그대로이고
  클러스터 정본은 `infra/k8s/base/` 다. [w4-rds-prod-db](/backlog/w4-rds-prod-db/) 완료 조건 하나를 체크했다.
- **절차를 바꾼 곳 셋.**
  ① **12-2 시크릿 교체**를 `create` 가 아니라 `patch` 로 — 백업 → 키 이름만 확인 → `DATABASE_URL`·`POSTGRES_*` **둘 다**
  RDS 값 → AWS 정적 키 제거 → 재시작. 암호는 `read -s` 로 받아 명령줄·셸 이력에 남기지 않는다.
  ② **17장 접속 확인·스키마 적용을 `psql` 파드가 아니라 서버 파드 안에서** 서버와 같은 `DATABASE_URL` 로 한다 —
  인스턴스에 클론이 없고(스키마는 `raw.githubusercontent.com` 에서 받는다), **서버가 실제로 보는 값으로 확인**하는 것이
  이번 사고의 교훈이다. 그래서 순서가 6 → 12-2 → 17 → 19 가 된다.
  ③ **19장에 10번(DB 읽기)·11번(DB 쓰기: 통화 → 전사 → 조회)을 넣었다.** 09-08 배포는 9번(`/health`)까지 통과했는데
  DB 는 한 번도 연결되지 않았다.
- **SSL**: RDS PostgreSQL 15+ 는 `rds.force_ssl=1` 이 기본이라 `DATABASE_URL` 에 `?sslmode=require` 를 붙였다(6-7).
  `POSTGRES_*` 경로는 libpq 기본 `prefer` 가 SSL 을 먼저 시도하므로 붙는다. 암호 규칙을 «영문·숫자만»으로 좁혔다 —
  URL(`@ / : ? # %`)과 12-2 의 JSON(`" \`) 양쪽에서 깨지지 않게.
- **`infra/k8s/base/secret.example.yaml`**: `POSTGRES_*` 키 추가, «둘 다 같은 RDS 값» 과 그 이유, `sslmode=require`,
  넣지 않는 키(AWS 정적 키), 이미 있는 시크릿은 런북 12-2 로 바꾸라는 안내. YAML 파싱 확인 · kustomization 에는 여전히 빠져 있다.
- **확인한 것 / 못 한 것.** 로컬 PostgreSQL 16.2(pgserver)에 17장 명령을 `kubectl exec` 만 빼고 그대로 돌렸다 —
  22 테이블 적용, **두 번째 적용은 `DuplicateTable` 로 멈추고 아무것도 안 바뀐다.** 19장 10·11번은 현재 작업 트리 서버를
  로컬로 띄워 그대로 쳤다 — `knowledge-gaps` 200, 전사가 `제 번호는 *********** 입니다`(P4)로 저장·조회됐다.
  12-2 ③ 의 JSON 은 파싱과 연결 문자열(호스트·사용자·DB·`sslmode`)까지 확인했다. **`kubectl patch` 와 RDS 접속 자체는
  못 돌렸다** — 이 머신에 kubectl 도 AWS 자격증명도 없다. RDS 가 실제로 어떤 이름으로 만들어졌는지도 보지 못했다.
- **앞 세션(같은 날) 검증에서 나온 것 — 기록만 한다.** 현재 `schema.sql` 을 적용한 실제 DB 에 `server/` 저장소 클래스를
  돌려 보니 ① 옛 어댑터의 전사 저장이 `ON CONFLICT` 대상 제약 없음으로 전부 실패, ② `POST /hub/cards/{id}/feedback` 이
  `ForeignKeyViolation card_feedback_card_id_fkey` 로 실패했다 — [미결](/open-items/)에 «실행으로는 안 쟀다» 로 올라가 있는
  항목인데 **실행으로도 재현된다.** ③ DB 제약 위반은 전부 500 이다(`main.py` 에 DB 에러 핸들러 없음). ①은 다른 세션이
  고치고 있어 손대지 않았다(`08` 기록). 릴리스 #59·#61 실패 원인은 plan 단계의 «코드 변경 + `newTag` 그대로» 였다.
