- `apps/admin`에서 블랙리스트 요청 반려 시 사유(`note`)를 입력받아 서버에 싣도록 고쳤다.
  서버(`blacklist_decision_interactor.py:40-42`, `decisions/316`)가 반려에 사유를 필수로
  요구하는데, 프론트는 입력 UI 자체가 없어 항상 `null`을 보내고 있었다(422).
- 조사 결과 `hubClient.ts`의 `decideBlacklistRequestApi`는 이미 `note?: string`을 받아
  그대로 실어 보내고 있었다 — 문제는 그 위 `adminStore.ts`의 `decideRequest`가 이 값을
  받지도 넘기지도 않던 것이었다. `hubClient.ts`는 손대지 않았다.
- UI는 승인 흐름의 인라인 필드 패턴(`RequestsTab.tsx`의 `expiryMonths` — 모달 아님,
  카드 안 상시 노출 입력)을 그대로 재사용해 「반려 사유」 입력을 추가했다. 빈 문자열로
  반려를 누르면 서버가 던지는 문구("반려에는 사유가 필요합니다 — ...")를 그대로 인라인
  에러(`header-error`, `role="alert"` — `AdminPanel`·`SettingsTab`이 이미 쓰는 클래스)로
  보여주고 제출을 막는다. 같은 저장소의 `EntriesTab.tsx`(연장·단축·해제 사유 필수,
  `decisions/309`)가 선례였지만 그쪽은 버튼 `disabled`만 하고 에러 텍스트는 안 띄워서,
  이번엔 지시대로 인라인 에러 문구를 추가하는 쪽으로 갔다.
- 체인 전체 수정: `RequestsTab.tsx`(입력 UI + 검증) → `AdminPanel.tsx`(`onReject`에 `reason`
  전달) → `adminStore.ts`(`decideRequest`에 `note?: string` 추가해 전달). 승인 경로는
  `note`를 안 넘겨도(`undefined`) 그대로 동작한다 — 서버도 승인 메모는 선택.
- 빌드 확인: `cd apps/admin && npm run build` (`tsc --noEmit && vite build`) 통과.
  이 앱에도 아직 테스트 러너가 없어(`package.json`에 `test` 스크립트 없음) 새 프레임워크
  도입 없이 빌드로만 검증했다.
- 남은 것: 이번 작업으로 상담원 화면(`closeCall`·`submitCardFeedback`, 09-22 앞선 세션)과
  관리자 화면(반려 사유) 양쪽 다 `decisions/315`·`316`이 요구하는 값을 실제로 보내게
  됐다 — 서버 쪽에서 실 계정으로 401/422가 사라지는지 확인은 배포 후 몫으로 남긴다.
