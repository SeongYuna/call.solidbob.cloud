- **응답 필드를 전부 문자열로 바꿨다.** 앞 기록의 `segment_id` 만으로는 부족했다 — 조서희 파서가 «문자열이 아니면 alert» 로
  만들어져 `is_final`·`utterance_end_ms` 에서 다시 걸렸고, 사용자가 «모든 응답의 모든 필드» 범위를 택했다. 선택지 셋(프론트가 쓰는
  4종만 · 전부 · ID 만)을 놓고 정한 것이라 범위는 의도된 것이다.
- **한 곳에서 바꿨다.** `schemas/_types.py` 의 `StrField`(BeforeValidator) 하나가 불리언 → `"true"`/`"false"`, 숫자 → `str()`,
  `null` 은 그대로 둔다. 응답 스키마 10개 파일의 필드 타입만 `StrField` 로 바꿨고 **라우터·DTO·DB 는 손대지 않았다** — 내부까지
  문자열로 바꾸면 정렬·산술·외래키가 흔들린다. OpenAPI 도 `string` 으로 공표된다.
- **`/health` 만 남겼다.** 스키마 없는 dict 이고 런북 19장 배포 검증 항목이라 불리언을 유지한다. 조서희 화면이 쓰는 곳도 아니다.
- **테스트로 고정했다**: 전사 응답의 말단 값이 전부 문자열인지 · 요청은 문자열도 받는지 · **`/openapi.json` 의 모든 응답 스키마에
  integer/number/boolean 이 없는지**(스키마 트리를 걷는다). 기존 단언 12곳을 문자열로 갱신했다. `server` 290 통과 · 계약 4종 KEPT.
- 확인: 터널 경유로 전사(`"is_final":"true"`, `"span":["6","19"]`)·추천(`"fired":"true"`, `"trigger_at_ms":"9346"`)·종결
  (`evidence` 값 `"true"`/`"false"`) 전부 문자열로 나온다.
- **정직하게**: 이 결정은 §7.3 계약 정본·프론트 `types/contract.ts`(`is_final: boolean`)와 어긋난다. 서버가 계약이 아니라
  파서에 맞춘 것이다. 계약 문서를 고치는 일이 남았고 [미결](/open-items/)에 그렇게 적었다. `ai/` 는 HTTP 표면을 안 쓰므로 영향이 없다.
