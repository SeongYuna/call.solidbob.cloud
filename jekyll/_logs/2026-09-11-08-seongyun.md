- **보고: 운영 서버로는 대시보드에 아무것도 안 뜬다.** 운영에서 새 통화 ID 로 `POST /hub/transcripts` 를
  보내면 500 이 나고, `/openapi.json` 에 통화를 만드는 엔드포인트가 없다. 게이트웨이 쪽은 이 실패를 «마스킹
  안 된 원문은 대시보드로 보내지 않는다» 원칙대로 조용히 버린다.
- **원인은 코드가 아니라 배포였다. 태그만 올리면 되는 것도 아니었다.** `POST /hub/calls` 는 장민석이 09-10 에
  이미 만들었다(`decisions/301`). 운영 이미지가 `0.1.1` 에 멈춰 있어 운영에만 없었다(01·04 기록).
  그런데 `0.1.2` 로 올리기 전에 막히는 것이 하나 있었다 — [w4-schema-qa-followup](/backlog/w4-schema-qa-followup/) ①.
  이것을 [w4-segment-composite-upsert](/backlog/w4-segment-composite-upsert/) 로 떼어 와 고쳤다.
- **실제 PostgreSQL 로 쟀다. 가짜 커서로는 못 잡는 결함이라서다.** 스크래치에 PostgreSQL 16(`pgserver`
  휠의 바이너리)을 띄우고 현재 `db/schema.sql` 을 적용했다(22 테이블). 수정 **전** 어댑터로 integration 테스트를
  돌리면 `InvalidColumnReference: there is no unique or exclusion constraint matching the ON CONFLICT
  specification` — 새 스키마에서는 덮어쓰기가 아니라 **전사 저장 전부가 실패**한다. 티켓은 «UPSERT 가
  터진다»고만 적고 있었는데, 그 말이 정확히 이것이다. 수정 후에는 2 passed.
- 고친 것:
  - `transcript_segment_repository.py` — `ON CONFLICT ("call_id", "segment_id")`. `masking_event` 를 지우고
    넣을 때도 `call_id` 를 함께 쓴다(복합 FK, `call_id` 가 NOT NULL).
  - `transcript_query_repository.py` — **같은 결함의 읽기 쪽이다. 티켓에는 없었다.** 마스킹 구간을
    `segment_id IN (…)` 로만 찾아서 다른 통화의 같은 순번 구간이 섞여 나올 수 있었다 → `call_id` 로 거른다.
  - **통화 시작 전 전사 → 500 대신 409 로 바꿨다**(본문: «`POST /hub/calls` 를 먼저»). 호출 순서 문제인데
    500 이 나가서 «서버 코드가 틀렸다»로 읽혔다 — 오늘 보고가 바로 그렇게 읽었다. 외래키 위반(SQLSTATE `23503`)만
    바꾸고, 다른 DB 오류는 그대로 올린다. 리포지토리는 psycopg 를 import 하지 않는 구조라 `sqlstate` 로 가렸다.
    409 본문에도 원문이 들어가지 않는지 테스트로 고정했다(SEC-1).
  - `infra/k8s/base/kustomization.yaml` `newTag` `0.1.1` → `0.1.2`.
- 확인: 로컬 서버 + 위 DB 로 HTTP 흐름을 끝까지 돌렸다. 통화 둘 시작(`created: "true"`, 재알림은 `"false"`) →
  같은 순번 1 을 두 통화에 전사(P4 마스킹) → 조회하면 각 통화에 제 발화만 남는다. 시작 안 한 통화는 409.
  `server` 315 passed · 3 skipped · 계약 4종 KEPT / `ai` 191 passed · 계약 3종 KEPT.
- **정직하게 적어 둘 것**:
  - integration 테스트는 **CI 에서 돌지 않는다**(`server` job 에 psycopg 도 PostgreSQL 서비스도 없다). 스키마와
    어댑터가 사흘 동안 어긋나 있었는데 초록이었던 이유가 이것이다. 이번 결과는 이 머신에서 한 번 잰 것이다.
  - integration 테스트는 루트 `.env` 에서 DB 를 읽는다. `.env` 가 가리키는 Neon 은 옛 스키마(`segment_id` 단독 PK)라
    **거기서 돌리면 실패한다.** 이번에는 `.env` 를 건드리지 않고 스크래치 플러그인으로 로컬 DB 를 꽂았다.
  - `POST /hub/cards/{id}/feedback` 도 새 스키마에서 늘 외래키 위반(500)이다 — `card_feedback.card_id` 가
    `recommendation_card` 를 참조하는데 그 테이블을 쓰는 코드가 0곳이다(grep 확인, 실행으로는 안 쟀다).
    이번 범위 밖이라 손대지 않고 [미결](/open-items/)에 올렸다. CI integration 테스트 부재도 함께 올렸다.
- 남은 것 — **순서가 중요하다**:
  1. **머지 전에 운영 DB 를 새 스키마로.** 지금 `server-env` 의 `DATABASE_URL` 은 Neon(옛 스키마)이다. 이대로
     머지하면 `0.1.2` 가 Neon 에 붙고 전사 저장은 위 `InvalidColumnReference` 로 **여전히 500** 이다.
     [w4-rds-prod-db](/backlog/w4-rds-prod-db/) 의 RDS 구축 → 스키마 적용 → 시크릿 교체가 먼저다(`decisions/108` 남은 것 1번).
  2. 머지 → `release.yml` 이 `0.1.2` 를 굽고 배포. 검증: `/openapi.json` 에 `POST /hub/calls` · `spokes` 에 `trigger` ·
     통화 시작 → 전사 200 → `GET /hub/calls/{id}/transcript` 에 남음.
  3. 게이트웨이는 **통화를 여는 순간 `POST /hub/calls` 를 먼저** 부른다. 409 가 오면 순서를 어긴 것이다.
  4. CI 에 PostgreSQL 서비스를 붙여 integration 테스트를 돌릴지 — 이번 같은 스키마·어댑터 어긋남을 잡는 유일한 장치다.
  - `_project/STATE.md` 는 손대지 않았다 — 오늘 앞 세션(01~07)이 사용자 지시로 두었던 것을 그대로 따랐다. 「지금 막혀 있는 것」 표의 `UPSERT 복합키 미반영`·
    `call 행 생성 경로 없음` 두 줄은 이제 사실이 아니다.
