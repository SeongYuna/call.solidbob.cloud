- **ERD 를 재생성하고 스키마를 네 관점으로 감리했다** — 정규화 · 역정규화/성능 · 요구사항 커버리지 · 개인정보/보안. **서로 다른 관점이 독립적으로 같은 결함 둘을 짚었고, 그중 하나는 이 저장소에서 재현까지 됐다.** 반영: `_project/decisions/205`
- **⚠ 치명 ① — 두 번째 통화의 자막이 첫 통화 자막을 덮어쓰고 있었다.** `transcript_segment` PK 가 `segment_id` 하나인데, `segment_id` 는 **게이트웨이가 통화 안에서 매기는 순번**이다(§7.3 예시·프론트 mock 둘 다 통화마다 1부터). 리포지토리가 `ON CONFLICT ("segment_id") DO UPDATE` 라 통화 B 의 1번이 통화 A 의 1번 행 텍스트를 갈아끼운다 — **`call_id` 는 그대로 남아서** 다른 사람의 발화가 다른 통화의 자막이 된다. 오류가 없다. **로컬 PostgreSQL 에서 그대로 재현했다**
  ```
   call_id | segment_id |         text
   c_001   |          1 | 수도요금이 왜 이래요   ← c_001 의 "등본 발급 문의드려요" 가 사라졌다
  ```
  PK 를 `(call_id, segment_id)` 로 바꾸고 `masking_event`·`compliance_flag`·`knowledge_gap` 을 복합 FK 로 이었다. 고친 뒤 같은 입력에서 **두 행이 각각 살아 있다.** ⚠ **UPSERT 는 `server/` 라 안 고쳤다** — 스키마만 바꾸면 터지므로 [티켓](/backlog/w4-schema-qa-followup/)으로 넘겼다
- **⚠ 치명 ② — 블랙리스트 해제 후 재등록이 불가능했다.** 내가 어제 만든 것이다. PK 가 `customer_ref` 인데 `released_at` 이 있으니, 같은 고객을 다시 승인하면 INSERT 는 PK 위반이고 UPDATE 는 **첫 등록 이력을 지운다** — 컬럼 주석이 *"지우면 「왜 풀렸는지」가 사라진다"* 고 적어 둔 바로 그 일이 UPDATE 로 일어난다. 등록 **에피소드** 단위로 바꾸고(`entry_id` 서로게이트) 「활성 등록은 고객당 하나」만 **부분 유니크 인덱스**로 막았다. 재등록·중복차단 둘 다 DB 에서 확인
- **⚠ 해제 감사가 반쪽이었다** — 행을 남겨도 `released_by`·해제 사유 컬럼이 없어 **어차피 「왜 풀렸는지」가 기록되지 않았다.** 둘을 더했다
- **⚠ C-5 가 자막에서 지운 값을 옆 테이블에 평문으로 두고 있었다.** `customer_ref` 가 전화번호인데 전화번호는 **P4** 다. 관리자 화면이 그 값을 전체 표시하므로 **캡처 한 장이 폭언 신고된 시민의 전화번호 목록**이 된다. 배정·조회에 필요한 건 동등 비교뿐이라 **HMAC + `display_hint`(뒤 4자리)** 로 갈랐다. 부수 효과로 `customer.customer_id`(해시/난수)와 체계가 같아져 **FK 를 못 걸던 이유가 함께 사라졌다.** `routing_log.customer_ref` 는 **삭제**했다 — 그 표의 목적은 `fell_back` 을 세는 것이고, 두면 「특정 번호의 민원 이력」이 쌓이는데 그건 F-3 을 폐기했던 이유를 뒷문으로 되살리는 것이다
- **⚠ `distress_count` 를 저장하지 않기로 했다.** 자해·극단적 선택 암시 건수는 **정신건강에 관한 정보**다. 그것이 고객 식별자와 같은 행에 반려·해제 뒤에도 무기한 남으면 *"이 번호의 사람이 자해를 N회 암시했다"* 는 레코드가 된다. **내 설계 의도와 정반대였다** — `decisions/204` 는 `distress` 를 「사유가 아니다」로 못 박고 `abuse_total` 에서 뺐는데 정작 DB 에는 건수를 영구 저장하고 있었다. 컬럼을 지웠다. 화면 경고에 필요한 건 불리언 하나이고 프론트가 이미 그렇게 쓴다
- **보존 기간이 없었다.** `blacklist_entry.expires_at` 을 넣고 배정은 `released_at IS NULL AND expires_at > now()` 만 본다. **만료가 없으면 영구 표시**이고, 번호가 재할당되면 다른 사람이 대상이 된다. ⚠ **절대 원칙 8 의 범위를 결정 기록에 못 박았다** — *"실패를 지운 기록은 기록이 아니다"* 는 **실험·지표의 실패**를 지우지 말라는 것이지 **시민의 전화번호를 영구 보관하라**는 원칙이 아니다. 두 뜻이 섞여 있었다
- **오늘 만든 C-6·D-5 의 출력을 담을 테이블이 아예 없었다.** `compliance_flag` 로 대체할 수 없다 — `rule_code` 가 C-1~C-4 카탈로그에 FK 로 묶여 있고 **화자가 반대라** 섞으면 D-4 재학습 데이터가 오염된다. `call_guard_flag`·`voice_outlier` 를 새로 만들었다. **D-5 는 특히 급하다 — 오디오를 보관하지 않으므로 통화가 끝나면 재계산이 불가능하다**([티켓](/backlog/w4-c6-d5-persistence/))
- **`eval_result.module` 에 `call_guard` 가 섹션명 그대로 들어가 있었다.** `_MODULE_ID` 에 C-6 매핑이 없어서다. 다른 행은 `B-2`·`C-5` 인데 이것만 섹션명이고, **10자라 우연히 `VARCHAR(10)` 에 딱 맞아** 에러가 안 났다. `C-6`·`D-5`·`A-5` 를 채웠다
- **생성기에 복합 PK·복합 FK·부분 유니크·인덱스를 넣었다** — 없이는 위 둘을 못 고친다. `db/schema.sql` 은 **생성물**이라 직접 고치면 다음 실행에 지워진다(오늘 한 번 그랬다). **테이블 20 → 22개**, ERD 재생성 완료
- **남긴 것**: `closure` 가 아직 금융·쇼핑 스키마다 — 다산 절차를 넣으면 CHECK 에 걸려 INSERT 가 거부되고 그 앞단에서 `UnknownClosureType` 이 난다. **골든셋 F-2 케이스가 0건인 이유의 절반이 여기다.** `server/` 소관이라 [티켓](/backlog/w4-schema-qa-followup/)으로 넘겼다. `agent.role` 은 컬럼만 만들었고 **서버에 인증이 없어 `decided_by` 가 아직 클라이언트 주장값**이다 — J-4 승인 API 를 열기 전에 붙여야 한다
