- **장민석 님 요청(`w3-cors-dashboard` 완료 기록) — 로컬 연동 확인 결과, 통과.** `cd server && python -m uvicorn main:app --port 8000`으로 로컬 서버를 띄우고, 대시보드가 브라우저에서 보낼 요청을 그대로 흉내 냈다.
  - `OPTIONS /hub/closure-checks` (Origin: `http://localhost:5173`) → `200`, `access-control-allow-origin: http://localhost:5173` 정상.
  - `POST /hub/closure-checks` 같은 origin으로 실제 호출 → 응답 필드(`call_id`·`closure_type`·`evidence`·`verdict`·`missing`·`reason`·`source`)가 프론트 `ClosureEvent` 타입과 그대로 일치.
  - 허용 목록에 없는 origin(`https://call.solidbob.cloud`)으로는 `400` + CORS 헤더 없음 — allow-list가 양방향으로 의도대로 동작.
  - 로컬 서버는 Postgres·ES 없이(`postgres_configured:false`, `elasticsearch_configured:false`) 떴고, `spokes: ["masking","closure_gate"]` — closure-checks는 이 둘에 의존하지 않아 그대로 동작했다.
- **단, `apps/dashboard`에는 아직 이 엔드포인트를 실제로 부르는 코드가 없다.** `coreClient.ts`는 mock 재export만 하고 있어서, `VITE_CORE_API_URL=http://localhost:8000`으로 띄워도 화면상 달라지는 건 없다 — CORS/네트워크 계층은 확인됐고, 실제 연동 코드 작성은 별개 작업으로 남는다.
- **정성윤 님 09-09 기록(카드 점수 필드명 `score`→`similarity_score`)에 대한 회신 — 이미 해결된 상태였다.** 정성윤 님이 찾은 "프론트에 두 필드 다 읽는 방어 코드가 없다"는 관찰은 **본인 저장소(main) 기준으로는 맞았다.** 그 방어 코드(`realGatewayClient.ts`의 `similarity_score ?? score` fallback)는 이 세션 시작 시점에 이미 이 머신에 **미푸시 상태로** 존재했고(누가 언제 작성했는지는 이 세션에서 확인 못 함), 오늘 세션 중 커밋(`5b8f033`)에 같이 실려 PR #53으로 main에 들어갔다. 지금은 서버 필드명도 고쳐졌고 프론트 방어 코드도 merge됐으니 **이중으로 안전한 상태** — 추가 조치 필요 없음.
